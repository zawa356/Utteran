## 2. #30 標準／カスタムセットアップ（P0）

### 2.1 概念と状態

- **表示モード（通常／Expert）とセットアップ方式（標準／カスタム）は独立**。方式は`WizardChoices.method`で、どちらも同じ
  `models`・`primaryModel`・`device`・`engine`を編集する。方式の切替は表示を変えるだけでplanを変えない（承認も無効化しない）。
- 選択値: `device`（gpu=B8 `cuda`、cpu）、`engine`、`models`（そのプロファイルが実行後に持つ全モデル＝B8 `model_refs`、1〜8件）、
  `primaryModel`、`modelsTouched`（未操作の間は推奨に追従）、`diarization`、`credential`（有無フラグのみ）、`acceptedAgreements`。
- Wizardを開いた時点の導入状態を`inventory`（profileごとのready・導入済みモデル）として写す（B8 inventory revisionの代用）。
  planはこの差分だけを入れる: ready profileには実行環境・VADを入れない／導入済みモデルを再DLしない。導入済みモデルは選択から外せない
  （削除はこのWizardの役割ではない）。ready profileの既定モデルは変えない（`wizard-default-kept`）。
- 候補の正本は`domain/setupCatalog.ts`の**合成Fixture1ファイル**。ID・表示名・概算サイズは`src/utteran/models/catalog.py`に合わせた
  （large-v3-turbo 1.6 GiB、large-v3 3.1 GiB、kotoba-whisper-v2.0 1.52 GiB、medium、small）。**デバイス規則（large-v3はGPUのみ、等）は試作の例**で、
  実行経路が実際に動かせることを意味しない（B7 workerの対応範囲は別）。推奨はGPU→large-v3-turbo、CPU→small（例）。
- サイズが不明なものは`null`で、表は「不明」、合計は「約X＋不明分」（0として黙って足さない、B8 `bytes_unknown`相当）。

### 2.2 ブロック（「次へ」「インストールを開始」）

`nextBlock`: 環境画面で`gpuMissing`／`noModel`／`tooManyModels`（>8）／`modelUnavailable`、機能画面で`credential`／`agreement`、
確認画面で上記に加え`nothingToInstall`（追加も修復もない）。`approveAndStart()`は`nextBlock`が`null`でなければ**呼び出し元に関係なく拒否**する。
モデル・デバイス・エンジン・話者分離の変更は`planRevision`を上げ、承認を無効化する（再試行・再開も拒否、§4.3）。

### 2.3 画面フロー

```text
初回: ようこそ（方式を選ぶ）→ 実行環境とモデル（方式切替・デバイス・モデル）→ 使用する機能（話者分離 ON → 同じ画面にトークン/利用条件）
      → インストール内容の確認（表＋必要時のトークン/同意）→「インストールを開始」→ 工程 → 完了（実行環境/モデル/話者分離）
追加: 実行環境とモデル → 使用する機能 → 確認 → …（ready profileはモデル・話者分離だけ追加）
修復: 修復する内容の確認 →「修復を開始」→ 工程 → 完了
```

### 2.4 P1の維持

- **P1-1**: トークンの有無と同意は独立。トークンは有無フラグのみ（値は入力・表示・保存しない）。トークンありでも新しいplanは同意が必要。
  どちらか欠けると「次へ」「インストールを開始」、`approveAndStart()`の直接呼び出し、再試行・再開を拒否。話者分離OFFで両方の行を隠す。
  追加セットアップは同意を空で始める（過去の同意を流用しない）。
- **P1-2**: 成功して`finish()`した時だけ、対象profileの状態と追加モデルを反映（`applySetupOutcome`）。他profile・話者分離・preferred・
  入力・個別override・ジョブ・履歴は変えない。失敗・中断・承認前は何も変えない。

## 4. #33 同一入力の複数ジョブ

### 4.1 入力とジョブ

- 入力（ワークスペース上のファイル）とジョブ（1回の実行要求）を分ける。`submit`＝未投入の入力だけ（従来どおり）。
  `submitAgain`＝投入済みでも現在の設定で**新しいジョブ**（待機・実行中・完了いずれの既存ジョブがあっても可）。未対応形式・設定エラー・
  未設定の話者分離は従来どおり除外し理由を出す。「過去に投入した」ことは永久禁止の理由にしない。
- ジョブ: `id`（一意）、`runNo`（その入力の何回目か）、`snapshot`（投入時に凍結、以後の設定変更は波及しない）、`outputDir`（解決済み、凍結）、
  `outputs`（投入時に決めた出力名）。一覧の2行目は「Job ID · モデル」だけで、プロンプト・用語集の本文は表示しない。

### 4.2 出力名・衝突の規則（試作）

同じファイル名の入力について、同じ保存先へ書く以前のジョブ（状態・キュー整理を問わず）があれば、新ジョブの出力名を
`<拡張子を除いた名前>_<Job ID>.<形式>`にする（例: `sample-meeting-01_demo-job-002.srt`）。保存先が違えば元の名前のまま。
投入結果に「ファイル名にジョブIDを付けます」と表示。**本番ではさらに実フォルダの既存ファイルを確認し、黙って上書きしない**（B7で確認、後続）。

### 4.3 retry と rerun

| | 対象 | Job ID | snapshot | B7 |
|---|---|---|---|---|
| 再試行 | 失敗・取消 | 同じ | 元のまま | `retry` |
| 現在の設定で再実行 | 終了したジョブ（入力が一覧に残っている時） | 新規 | 現在の設定から新規解決 | `POST /jobs/{id}/rerun`（terminal/interrupted対象） |
| もう一度追加 | 選択中の入力（待機・実行中のジョブがあっても可） | 新規 | 現在の設定 | **既存APIの保証外**。同一入力の同時admission制限は後続の設計課題 |

## 5. #35 既定＋ファイル別の出力先

- 出力先は**入力の属性**（B5 `utteran_contracts/editing.py`の`FileInput.output_dir`）で、`ProcessingSettings`のleaf overrideとは別に
  `DemoState.outputDirs[inputId]`で持つ。プリセット・snapshotの設定値には入らない（PC固有の値を共有しない）。
- 解決: 個別指定 ?? 既定（`null`＝入力と同じフォルダ）。既定を後から変えると「既定」の入力は追従し、個別指定は追従しない。
- 投入時に解決済みの保存先をジョブへ凍結。同じ入力の2回目に別の保存先を指定できる。
- フォルダ選択は`SAMPLE_FOLDERS`（`D:\Utteran-demo\output`など3件）の固定リスト。未選択では「選択」不可（空値なし）、同じ値の再指定は
  「保存先は変わっていません」。**本番はOSのフォルダpickerとB7の検証（絶対パス・存在・書き込み可・symlink/ネットワークパスの扱い）へ接続**。

## 6. #36 用語集

- 規則は`domain/glossaryText.ts`に集約し、設定の検証（`validateSettings`、最大1000語・1語256文字・大文字小文字を無視した重複）と一致させた。
  適用で行うのは「行の前後の空白を除く・空行を飛ばす・後から出た重複を飛ばす」だけ。語順・大文字小文字・全角/半角・その他の文字は変えない。
  長すぎる行と1000語超は**切り詰めず適用を拒否**し、入力は保持する。
- 下書きは`DemoState.glossaryDrafts`（対象＝モード＋対象ファイルIDの組）に保持し、カテゴリ切替・モデル変更で消えない。Enterは改行だけで、
  IME変換中も含めキー操作では適用しない。
- 複数選択で用語集が異なる場合は空欄で始め、「ここに入力した内容で、すべての用語集を置き換えます」と表示し、ボタンは「選択中の{n}件すべてに適用」。
  一方の内容を他へ無断で適用しない。
- TXT: UTF-8、BOMは読み飛ばし、CRLF/LF/CRいずれも改行。読み込みはテキスト欄へ入れるだけ（「置き換え／追加」を選択、適用は別）。
  書き出しは適用済みの内容、BOMなし、改行CRLF/LFを選択、保存はしない。CSV/TSVは後続。

## 9. #29 文言の全数点検

### 9.1 方法

### 18.1 P1-1 プラン変更後の再承認で工程の完了を流用しない

- **原因**: `approveAndStart()`が直前の`stages`から「工程ID→状態」を作り、新しいプランでも**IDが同じなら`done`を引き継いでいた**。`asr_model`は
  モデルに関係なく同じIDのため、モデルAの取得完了後に失敗→モデルBへ変更→再承認すると、Bの取得を飛ばして完了扱いにできた。
- **修正**（`domain/setup.ts`）:
  - `approveAndStart()`は**常にそのプランの全工程を未着手で作り直し**、先頭から実行する（旧ステージは一切流用しない）。
  - 承認したプランの同一性を`runPlanKey`（`planKey()` = entry・対象デバイス・エンジン・モデル集合・主モデル・話者分離・プラン項目・工程列）で保持。
  - `continueRun()`（再試行・再開）は、承認revisionの一致・P1-1の要件に加えて**`runPlanKey`が現在のプランと一致する時だけ**完了済み工程を保持して続行する。
  - `changeChoices()`は停止した実行の`stages`と`runPlanKey`を破棄する（戻っただけで何も変えずに再承認しても先頭から）。
  - `finish()`は`runCompleted()`（`succeeded`・承認済み・revision一致・`runPlanKey`一致・現在のプランの全工程が`done`）を満たさない限り何もしない。
    直接呼び出し・未承認・未完了・プラン不一致では環境・設定を変えない。
- 将来、同一プランの成果物を再利用する場合は、プランdigest・工程の対象・実体の検証結果（B8のjournal等）が一致した時だけに限る。試作では実装しない。

### 18.2 P1-2 初回セットアップの主モデルを処理設定の共通既定値へ反映

- **原因**: `finish()`は環境（`EnvState.defaultModel`・モデル一覧）だけを更新し、共通既定値（`DemoState.common`）は`backend: auto` / `demo-model-balanced`のまま。
  新規ジョブのsnapshotは共通既定値から作られるため、選んだモデルと実際のジョブが一致しなかった。また合成候補`MOCK_ENGINE_CANDIDATES['faster-whisper']`に
  `kotoba-whisper-v2.0`が無く、そのまま渡すと`normalizeEngine()`で別モデルへ黙って置換される状態だった。
- **修正**:
  - **初回セットアップ（`first_run`）が完了した時だけ**、`firstRunDefaults()` = `{ backend: エンジン, model: 主モデル, device: cuda|cpu, computeType: auto, diarization: 導入済みか }`
    を**1回のパッチ**で`setCommonPatch()`へ渡す（エンジン群の正規化は1回、途中で`auto`の例へ戻らない）。承認時・実行中・失敗・中断では呼ばれない。
  - 合成候補のfaster-whisperに`kotoba-whisper-v2.0`を追加（ウィザードで選べるモデルはすべて処理設定でも有効）。**互換性の正本はB4で、この表は合成の例**。
  - 追加（`add`）・修復（`repair`）は従来どおり環境だけを変え、共通既定値・個別override・プリセット・ジョブsnapshot・既定モデル・preferredを変えない。
  - 個別overrideは保持され、共通値を継承するファイルだけが新しいモデルを使う。
