## 2. #19 Expertの処理設定

### 2.1 データの形と正本

- 試作の設定は**平坦なキー**（36項目）で持ち、`CONTRACT_PATH`でB5契約（`src/utteran_contracts/settings.py`の`ProcessingSettings`）の
  フィールドへ対応付ける。`toContractShape`は契約の入れ子形を作り、**選んだエンジンの節だけ**を含め、話者数は`num`か`min/max`の**どちらか一方**だけにする
  （契約の`speaker_count_shape`が拒否する組合せをUIから作れない）。既定値は`src/utteran/config.py`にある値（beam 5、VAD 0.5、temperature 0、
  merge_gap 0.5、speaker_switch_penalty 0.75等）を使い、それ以外は試作の例。
- **フィールドが契約に存在すること ≠ 現行GUIから保存・実行できること。** 実行デバイスはProcessingSettingsに無い（B4のprofile/B5のpolicyが決める）ため
  `CONTRACT_PATH.device = null`とし、プリセットの書き出しから常に除外する。`extra_arguments`（whisper.cppの任意引数）は安全審査が要るため出していない。
- エンジン・モデル・デバイス・compute typeの候補は**合成Fixture `MOCK_ENGINE_CANDIDATES`**（`settingsSchema.ts`内に隔離）。UIは静的な互換表を持たず、
  `engineCandidates(backend)`の戻り値を後続でbackend（B4のinventory/resolution）の解決値に差し替えるだけで済む形にした。
  画面には「このPCで使える構成から選びます」以外の互換性の主張を出さない。

### 2.2 カテゴリと表示

| カテゴリ | 項目 | 備考 |
|---|---|---|
| 音声認識 | エンジン（自動/faster-whisper/whisper.cpp/OpenVINO GenAI）、モデル、言語、実行デバイス、計算精度（faster-whisperのみ）、ビームサイズ、単語ごとの時刻、前の文脈、VAD＋しきい値（VADオン時） | 見出し「エンジンとモデル／認識の方法／無音区間」 |

| 話者分離 | 有効/無効、話者数（自動／人数を指定／範囲で指定）、モデル、デバイス、メモリの保護（折りたたみ） | 無効時は他項目を無効化＋1行の理由 |
| 出力 | 形式（SRT/VTT/JSON/MD/TXT、1つ以上）、話者名、改行コード、SRTのBOM（SRT選択時） | |
| 詳細 | whisper.cpp（threads・temperature・増分・DTW、しきい値は折りたたみ）、OpenVINO GenAI（max new tokens）、後処理の調整（折りたたみ） | 選んだエンジンの項目だけ。「自動」・faster-whisperでは1行で理由を表示 |

- カテゴリの切替は**折り返すボタン列**（狭いペインでも全カテゴリが見え、スクロールで隠れない）。カテゴリ名の横に個別設定の数（選択モード）と、
  検証エラーがある場合のアイコン。カテゴリを移っても値は`DemoController`のstoreにあるので消えない（Vitest・E2E）。
- 部品: `SettingsEditor`（カテゴリ・節）→`SettingRow`（`InspectorField`＋種類別の入力）→`NumberField`/`PromptField`/`GlossaryEditor`/`SpeakersField`。
  スキーマ（`FIELDS`）で並べるので、項目を足してもSFCは大きくならない。値の読み書きは`provideSettingAccess`（共通／選択／通常）にまとめた。

### 2.3 継承・適用先の規則（第3案からの変更点）

1. **連動グループ**: エンジン・モデル・デバイス・compute typeと、話者数（mode/num/min/max）は**まとめて**個別になる。ファイルごとにエンジンを変えても、
   共通側のモデルを半分だけ継承して不正な組合せになることがない（`withOverride`・`normalizeEngine`）。「個別に設定」スイッチはグループの先頭項目だけに出し、
   「関連する項目も一緒に個別になります」と1行添える。入力一覧の「個別」数はグループを1と数える。
2. **個別化で他ファイルを上書きしない**: 複数選択で「個別に設定」をオンにすると、**各ファイルが自分の現在値**を個別値として持つ（第3案は1件目の値で全件を上書きしていた）。
   値が異なれば「複数の値」のまま。明示的に値を選んだ時だけ全件が同じ値になる。
3. **通常モードの編集は表示中のファイルだけ**（第3案の懸念点）: `setNormalSetting(inputId, patch)`は常にそのファイルの個別設定を書き、共通既定値を変えない。
   これでExpertで用意した他のファイルへ波及しない。ファイルが1件も無い時だけ共通既定値を変える。代わりに「別のファイルにする」「別のファイルを文字起こし」では、
   **直前に表示していたファイルの個別設定を新しいファイルへ引き継ぐ**（通常の利用者には「設定が次のファイルにも残る」ように見える）。
   古いファイルを一覧から外す条件は「唯一・未投入」（個別設定は新ファイルへ移るので失われない）。投入済みのジョブのsnapshotは変わらない。
4. **投入時snapshot**: 投入した瞬間のeffective設定（プロンプト・用語集・エンジンを含む）を凍結。後から編集しても既存ジョブは変わらない（Vitest・E2E）。
   ジョブ詳細には「プロンプトあり（n文字）」「用語集 n語」だけを出し、**本文はジョブ詳細・ログ・診断・エクスポートに出さない**。
5. **検証と投入**: 範囲外・整数でない・用語の重複等があるファイルは投入対象から外し（「n件は設定に問題があるため追加していません」）、
   全件が該当すれば投入ボタンを無効にして理由を出す。適用されない項目（選んでいないエンジンの項目、話者分離オフ時の話者数）は検証しない。
6. **話者分離が未設定の環境**: 話者分離がオンのファイルは投入しない（理由を表示）。通常モードでは「話者分離をオフにする」と「セットアップ」を並べ、行き止まりにしない。

### 2.4 IME

`initial_prompt`と用語集は`compositionstart`〜`compositionend`の間は値を確定しない。用語集のEnterは`isComposing`/`keyCode 229`の間は追加しない
（変換確定のEnterで語が追加されない）。E2Eでcompositionイベントを発火して確認したが、**実IME（Windows日本語IME・WebView2）では未検証**。

### 3.1 状態と画面

| レビュー帯の例 | 起動時 | 確認できること |
|---|---|---|
| セットアップ済み（既定） | 通常ホーム。Wizardは自動表示しない | 「セットアップ…」で追加（環境の確認から） |
| 初回起動 | Wizardが画面全体。モード切替・ナビなし、メニューはツール/ヘルプのみ | 順送り・戻る（選択保持）・条件付きの認証ステップ・承認・工程・完了→通常ホーム |
| 初回・GPUなし | 同上。GPUは選べない（理由を表示）、CPUが推奨 | CPUで完了できる。GPUを強制しない |
| 途中で中断 | 中断した工程と「続きから再開／設定を変更／詳細ログを確認」 | 再開で完了済み工程を保持して続行 |
| セットアップ失敗 | 失敗した工程・短い理由・詳細コードと同じ3つの出口 | ログ（エクスポート可）→設定変更（再承認）→再試行 |
| 構成に問題（要修復） | 通常ホームは使える（CPU構成）。「GPUの実行環境に問題があるため、CPUで実行します。［修復…］」 | 修復プラン（短い）→完了→GPU利用可 |
| 話者分離のトークンなし | 通常ホームで開始不可の理由と「話者分離をオフにする」「セットアップ」 | カード「話者分離を設定…」→機能選択（話者分離オン）→認証 |

- 画面: 1ページ1ステップ。ボタンの位置は全ページ共通（左＝あとで/閉じる、右＝戻る・次へ/承認して開始）。現在地は「手順 2/4: 環境の確認」の1行だけ。
- 認証ステップ: 話者分離を選び、資格情報が無い時だけ表示。**トークンの値は入力させない**（「トークンを登録…」は存在フラグを立てるだけ。製品では別のマスク入力を設計）。
  利用条件への同意。「話者分離を使わずに続ける」で抜けられる。
- インストール内容の確認: 内容・ダウンロード量・必要なディスク（**例の値**）、実行すること（工程名）、同意済みの条件を1つの表と2行で。
  「『承認して開始』を押すまで、ダウンロードやインストールは行いません」。
- セットアップ中: 工程ごとの状態（待機/実行中/完了/失敗/中断）と実行中工程のバー。デモ操作（工程を進める・失敗させる・中断させる）は破線区画。
  実行中は閉じられない（中断は「アプリ終了を想定」のデモ操作で再現）。
- 完了: 「この試作では、実際には何もダウンロード・インストールしていません。」を1行。「文字起こしを始める」で通常ホームへ（初回のみモードを通常に）。
  話者分離を入れなかった場合は**話者分離オフを既定値**にする（入れていない機能で開始がブロックされない）。
- 閉じる: 選択済みの内容は残る（in-memory。**再読み込みで消える**。Storageは使っていない）。閉じた後は通常ホームとセットアップ画面に
  「セットアップが完了していません／『◯◯』で中断しています［セットアップを続ける］」を1行。

### 3.2 B8との対応（将来の状態モデル）

| 試作 | B8（`docs/architecture/b8/api.md`） | 備考 |
|---|---|---|
| 「インストール内容の確認」の表 | `POST /setup-plans` → SetupPlan（read-only） | 表示する量・工程はplanの値。試作の数値は例 |

| 中断→再開 | `waiting_user`/`interrupted` → `POST …/resume` | アプリ終了・スリープ・認証待ち |
| 設定を変更 | 新しいplanの作成と承認（追加step・容量増加は新planでしか表せない） | 試作は再承認を要求し、完了済み工程は「取得済み」として残す |
| 資格情報 | `credential_required`／`agreement_required` | 試作は存在フラグのみ |
| キャンセル | `POST …/cancel` | **試作は未実装**（中断で代替）。後続で設計 |

- **旧Wizard（`utteran_gui/setup_wizard.py`、`WIZARD_STEPS`・`setup_wizard_*`）とB8を混ぜない。** 試作は旧Wizardの設定を読まず、
  旧Wizardの完了履歴を新フローの成功証跡として扱わない（`api.md`「旧wizardの`completed_stages`等はv1へ移行・信用しない」に従う）。
- 試作のステップは旧Wizardの`welcome/profile/diarization/token/model/confirm`を下敷きにしたが、モデル選択はステップにせず（推奨値を確認表に表示、
  詳細はExpertの処理設定）、操作を最少にした。重い処理の同時実行枠（ジョブとセットアップで共有）は試作では表現していない。

### 3.3 「再検出」と「セットアップ…」

| 操作 | 意味 | 試作の動作 |
|---|---|---|
| 再検出 | 状態の更新（読み取りのみ） | 「確認しています…」→デモ操作で同じ例を再表示。Wizardは開かない |
| セットアップ…（上部） | 追加・変更（未構成なら初回） | Wizardを「環境の確認」から（`add`） |
| カードの「GPUを使うためのセットアップ…」「話者分離を設定…」 | 足りない機能の追加 | `add`で該当の選択を初期値にして開始 |
| カードの「修復…」 | 壊れた構成の入れ直し | `repair`: 確認表から（短いplan） |

GPUの**検出**（「CUDA対応GPU: 1台」）とprofileの**Ready**（状態chip）は別の行に出し、検出だけで「利用できます」と表示しない。

## 4. #17 #15 ログと診断の入出力

- ログの「エクスポート…」→「ログのエクスポート」（保存する内容・ファイル名・形式・UTF-8）→「保存…」→「この試作では保存できません（ファイルは作成されません）。」
  ジョブのログは**選択中の1ジョブ**が対象（`utteran-demo-job-003-20261105.log`）。期間・範囲・複数ジョブの一括は後続の論点。
- 将来のWindows実装: OSの「名前を付けて保存」（WebView2ホスト経由）。ログ自体がトークン・パス・本文を記録しない方針（`maskForDiagnostics`の規則）を維持。
- 診断: 既定は目的1文・プライバシー1文・「保存…」だけ。一覧は「出力内容の詳細」に折りたたむ。診断と通常ログのエクスポートは別機能のまま。

## 5. #21 狭幅とWindowsの最小サイズ（設計のみ）

### 5.1 試作の挙動

| 作業領域の幅 | 配置 | 備考 |
|---|---|---|
| ≥ 936px（260+380+240+区切り＋余白） | 3列（ドラッグ可変） | 自動比率: <1400pxは30/42/28、≥1400pxは22/53/25。手動の幅・固定比率が優先 |
| 688〜935px | 2列: ファイル｜（「2 処理設定」「3 キュー投入」を切替） | 下段にキューを積まない |
| < 688px | 1列: 「1 ファイル／2 処理設定／3 キュー投入」を切替 | |

- 切替はペインを`v-show`で隠すだけなので、入力中の値・スクロール以外の状態は消えない。各ペインは同じ高さで内部スクロール、全体の横スクロールなし。

  「interview-sample-02.wav」が切れないことをE2Eで測った。極端に長い名前は従来どおり省略＋title。

  どれもペインの上端が1行に揃う（縦積み0）、投入ボタンに到達できる、横overflow 0、app bar要素の重なり0。

### 5.2 Windows WebView2ホストへの提案（今回は実装しない）

| モード | 最小（CSS px＝DIP） | 根拠 |
|---|---|---|
| 通常 | 800×550 | 1ファイルの2カラムが成立し、app barが格納形で収まる |
| Expert | 1200×680 | サイドバー200px＋3列（936px）＋余白。これ未満は2列/1列へ自動で切り替わるので**強制はしない**案もある |

## 13. 未検証・残る判断

**未検証（隠さない）**: Windows WebView2での表示・操作、OS DPI実機（125/150/200%）、Windows日本語フォント、**実IME**（E2Eはcompositionイベントの模擬）、

**ownerに判断してほしい点（優先順）**

1. **通常モードの設定の適用先**: 「表示中ファイルだけ＋次のファイルへ引継ぎ」（第4案）でよいか。共通既定値として保存する導線（「この設定を既定にする」）を通常に置くか。
2. **初回ウィザードの粒度**: 4〜5ステップ＋確認表で足りるか。モデル選択をWizardに出さない（推奨値固定・Expertで変更）方針でよいか。トークン入力画面の設計（マスク入力・保存先）をS5で行うか。
3. **Expertの処理設定の範囲**: 5カテゴリと今回の項目で足りるか。whisper.cppの任意引数（`extra_arguments`）や後処理の残り十数項目を出すか（出すなら「上級」区画と安全審査が必要）。
4. **プリセット交換形式**: `utteran-preset` v1（契約の入れ子名）を後続で正式化するか。プロンプト・用語集を既定で含めない方針でよいか。
5. **狭幅と最小サイズ**: 2列（ファイル＋切替）／1列切替でよいか。Windowsの最小サイズ（通常800×550、Expert 1200×680）を強制するか、強制せず自動切替に任せるか。既定のアクセント色（緑/青）。
