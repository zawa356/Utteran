# Release手順

## Versioning policy

utteran follows Semantic Versioning.

- `MAJOR`: incompatible CLI, config, persisted job, or output schema change after 1.0
- `MINOR`: backward-compatible feature or backend addition
- `PATCH`: backward-compatible bug, documentation, packaging, or security fix
- Before 1.0, `0.MINOR.PATCH` is unstable. A breaking change increments `MINOR` and must be called out.

`v0.0.1` is an archived initial development snapshot published on 2026-08-02. Its changelog was not
cut from the Unreleased section, so it is not treated as the first formal supported release. The next
planned release is `v0.1.0`, after Phase 4 acceptance. Version `1.0.0` requires a stable documented CLI,
config and output schema plus release acceptance on the supported hardware classes.

As of Phase 5d (2026-08-19), the `v0.0.1` GitHub Release is still in **Draft** status (confirmed via
`gh release view v0.0.1`), not published/visible despite the tag date above. Judgment: leave it
untouched (do not edit its content, do not publish it, do not delete it) as part of Phase 5d. It
predates all GUI/installer work (Phase 5a-5d) by design - editing its content now would misrepresent
what that snapshot actually contained, and whether to finally publish or discard a year-old draft
predating the current architecture is a repository-owner decision about historical release management,
not something an installer-packaging phase should decide unilaterally. It remains exactly as Phase 4a
left it until the repository owner decides otherwise.

## バージョン更新手順（作業単位ごと）

正式なrelease gate（下記）とは別に、変更を加えた作業単位ごとに次を行う。

1. パッチバージョンを1つ上げる（例: `0.1.9` → `0.1.10`。`0.2.0`へは繰り上げない）。
   マイナーバージョンの繰り上げは利用者が明示的に指示したときのみ行う。
2. 以下の箇所を新しいバージョンへ揃える。

   | ファイル | 内容 |
   |---|---|
   | `pyproject.toml` | `[project]` の `version`（唯一の一次情報源） |
   | `src/utteran/__init__.py` | `__version__` |
   | `src/utteran_gui/__init__.py` | `__version__` |
   | `uv.lock` | `uv lock` を実行して追従させる |

   `packaging/gui.spec`（exeのFileVersion/ProductVersion）と`packaging/installer.iss`
   （installerのAppVersion／出力ファイル名）は`build.ps1`が`pyproject.toml`の値をビルドの
   都度読み取って埋め込むため、手動更新は不要。`tests/test_version.py`が
   `pyproject.toml`・`utteran.__version__`・`utteran_gui.__version__`の一致を検証する。
3. `変更履歴.md`に、そのバージョンの節をKeep a Changelog形式（追加・変更・修正・削除）で
   作成し、実施した作業単位の内容を追記する。複数の作業単位をまたいで最後にまとめて書かない。
   既定値の変更、ジョブの再計算を伴う変更、設定の互換性が失われる変更など破壊的変更は
   **破壊的変更:** のように明示する。
4. `ruff check`・`mypy`・モデル不要のテストを実行して確認する。

この手順は日常のバージョン追跡のためのものであり、tag作成・push・GitHub Release公開を
含む正式なrelease gateそのものではない。両者の関係は要件定義.md 24.1章を参照。

## Release gate

1. Work from a clean release branch. Fetch all branches and tags.
2. Run `tools/public_history_scan.py` over full history and review the redacted report. If a secret is
   found, revoke it first; do not rewrite history as an automatic release step.
3. Confirm GitHub Issues/PR comments, Actions logs, releases/assets, Wiki and Discussions contain no
   private data.
4. Pass Linux and Windows CI. CI does not cover native builds, real models, GPUs, or long audio.
5. Run the integrated acceptance harness on each claimed hardware/profile. Explicitly include required
   long and destructive groups and confirm restoration. Record skipped requirements and do not present
   them as passed.
6. Review `LICENSE`, `THIRD_PARTY_NOTICES.md`, model cards, and gated-model agreements against the
   resolved dependency/model set.
7. Update `pyproject.toml` and `src/utteran/__init__.py` to the same version; run `uv lock` and
   `uv lock --check`.
8. Move the contents of `変更履歴.md`'s `未リリース` section to `## [X.Y.Z] - YYYY-MM-DD`, then create a
   new empty `未リリース` section above it. Do not retroactively edit an already published release.
9. Commit the release metadata, create an annotated `vX.Y.Z` tag, and verify the tag points to the
   reviewed commit.
10. Build the Windows installer on a Windows machine with Inno Setup 6 installed, from the exact
    reviewed/tagged commit: `.\build.ps1` (add `-SignCommand` only if a code-signing certificate is
    actually being used - see 要件定義.md 29.6章 for why this project does not self-sign by default).
    This reads the version from `pyproject.toml` (already updated in step 7), so the installer filename,
    its embedded version, and the tag can never drift apart. The command fails fast with install
    instructions if Inno Setup is missing; see `docs/utteran_Phase5d_指示書.md` and 要件定義.md 29章 for
    the packaging design. Confirm the build-time inference-core check passed (no `torch`/`utteran`/
    `faster_whisper`/`pyannote`/`ctranslate2` in the output) before proceeding.
11. `build.ps1` writes `<installer>.exe.sha256` next to the installer. Record that SHA-256 value in the
    release notes (see step 12) and keep the `.sha256` file itself as a release asset so it can be
    verified independently of the notes text.
12. Push the branch and tag only after human approval. Create release notes from the matching changelog
    section. Attach the installer `.exe` and its `.sha256` file as GitHub Release assets, and include the
    SHA-256 value in the release notes body (not just the sidecar file) so it is visible without
    downloading anything first. Do not upload models, recordings, transcripts, `.env`, logs, jobs, or
    benchmark source WAVs.

## Rollback and hotfixes

- Do not move or replace a published tag. Publish a new patch version.
- If an artifact is wrong, remove the release artifact, document the reason, fix on a branch, and issue
  a new version.
- If private data or a credential is exposed, revoke credentials immediately, preserve a redacted
  incident record, and ask the repository owner to choose whether coordinated history rewriting is
  justified. Force push is never part of the normal hotfix procedure.

## Commit message privacy

Do not add `Co-authored-by`, `Signed-off-by`, or other commit-message trailers containing an email
address. Credit contributors in the pull request or release notes without copying a private address.
Author/committer identity is managed separately by Git and should use the account's intended public
or noreply address.

## Approved history rewrite handoff

The Phase 4a cleanup is an exceptional, owner-approved rewrite and is not a normal release step.
Before pushing, confirm that no one has added remote commits since the backup. The ignored backup
state file records the expected old object ID for every branch and tag. A PowerShell operator can use
it to create an explicit force-with-lease for each ref:

```powershell
$state = Get-Content -Raw output/phase4a-history-backup-pre-rewrite/pre-rewrite-state.json |
  ConvertFrom-Json
foreach ($item in $state.refs | Where-Object { $_.ref -like 'refs/heads/*' }) {
  git push --force-with-lease="$($item.ref):$($item.object)" origin "$($item.ref):$($item.ref)"
}
foreach ($item in $state.refs | Where-Object { $_.ref -like 'refs/tags/*' }) {
  git push --force-with-lease="$($item.ref):$($item.object)" origin "$($item.ref):$($item.ref)"
}
```

Afterward, recreate or rebind the GitHub Release if it does not follow the rewritten tag, require all
existing clones to be replaced, and ask GitHub Support to purge cached/unreachable objects when full
server-side removal is required. As an alternative, create a new empty GitHub repository, set it as a
new remote, push all rewritten branches and tags, recreate the release, and archive the old repository.
