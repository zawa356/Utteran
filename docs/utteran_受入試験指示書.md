# utteran — 受入試験・デバッグ指示書

## あなたへの依頼

実際の会議録音（約2時間の MP4）を用いて、Phase 1 / Phase 2 の実装に対する
受入試験を実施してください。

**この作業は人間の立ち会いなしで進めます。** 判断に迷ったら止まるのではなく、
本書の判定基準に従って合否を記録し、次の試験へ進んでください。
判断できない事項は「保留」として記録し、最後に報告書へまとめてください。

不具合を発見した場合は、本書の手順に従って修正まで実施してください。

## 最重要の制約

### 機密データの取り扱い

**`input/` に置かれている MP4 は実際の社内会議の録音です。**
文字起こし結果には実名、組織名、業務内容が含まれます。

以下を厳守してください。

- 文字起こし結果、話者名、音声から得られたテキストを、
  **`AISTATE.md`、`変更履歴.md`、試験報告書、コミットメッセージ、
  テストコード、コンソールへの長文出力に一切含めない**
- `input/` と `output/` の中身を git の追跡対象にしない
- 実データを使ったテストの assertion は、内容ではなく
  統計量・構造・書式に対して行う
- 元の MP4 を変更・削除・移動しない（読み取りのみ）
- 品質確認のために本文を見る必要がある場合、
  `output/` 配下に置き、報告書には「どのファイルを見れば良いか」だけを書く

**各コミットの直前に、実データが混入していないことを必ず確認してください。**
確認方法は後述します。

### 秘密情報

- `.env` に `HF_TOKEN` が設定されています。**このファイルを読んで内容を表示しない、
  編集しない、コミットしない。**
- トークンの値をログ、報告書、コミットメッセージに出さない
- 「トークン未設定時の挙動」を試験する際も `.env` を編集せず、
  環境変数の上書きか、隔離した作業ディレクトリで行う

### git の運用

- 作業開始前に現在のコミットハッシュを記録し、報告書に書く
- 作業は専用ブランチ `test/acceptance-phase2` で行う
- **試験グループが1つ終わるごとにコミットする**
- 不具合修正は試験実行とは別のコミットに分ける
- `git push` は実行しない
- `git reset --hard`、`git checkout -- .`、`git clean -fd` など、
  未コミットの作業を破棄する操作を行わない
- 履歴を書き換えない（rebase、amend、force 系を使わない）

コミットメッセージの接頭辞:

```
test:  試験の実施、ハーネスの追加
fix:   不具合の修正
docs:  文書の更新
chore: 補助的な変更
```

## 事前準備

### 1. 環境の記録

以下を確認し、報告書の冒頭に記録してください。

- 現在のコミットハッシュ、ブランチ、`git status` の状態
- OS、Python バージョン、uv バージョン
- 現在の uv プロファイル（cpu / cuda / intel のどれか）
- `utteran devices --json` の出力
- ディスクの空き容量
- 物理メモリ容量
- `input/` 内のファイル名、サイズ、`ffprobe` によるコンテナ情報
  （ファイル名は報告書に書いてよいが、内容には触れない）

作業開始時点で `git status` が汚れている場合、まず現状を
`chore: snapshot before acceptance testing` としてコミットしてから始めてください。

### 2. 試験素材の生成

**実ファイルをそのまま全試験に使わないでください。** 2時間音声の処理は長時間を要し、
外出中に完了しません。以下のクリップを ffmpeg で生成し、機能試験に使用します。

保存先は `output/_testdata/`（git 追跡対象外であることを確認すること）。

| 名前 | 内容 | 用途 |
|---|---|---|
| `clip_30s.mp4` | 冒頭から30秒 | 最速の疎通確認 |
| `clip_03m.mp4` | 複数話者が含まれる区間から3分 | 機能試験の主力 |
| `clip_10m.mp4` | 10分 | 中断・再開、時間計測 |
| `clip_03m.wav` | `clip_03m` を wav 化 | 入力形式の差異確認 |
| `clip_03m.m4a` | 音声のみ抽出 | 音声形式の確認 |
| `broken.mp4` | 途中で切断した壊れたファイル | デコード失敗の確認 |
| `empty.mp4` | 0バイトファイル | 異常入力の確認 |
| `notmedia.txt` | テキストファイル | 対象外入力の確認 |

`clip_03m` は、複数の話者が実際に発話している区間から切り出してください。
冒頭は無音や単独話者であることが多く、話者分離の試験に適しません。
区間の選定は、音声レベルの変化を見るなどして機械的に判断して構いません。

### 3. 試験ハーネスの作成

`tools/acceptance/` に試験ハーネスを作成してください。要件は以下のとおりです。

- 各試験ケースを ID 付きで定義し、順に実行する
- **1ケース完了ごとに結果を `output/_acceptance/results.jsonl` へ追記する**
  （セッションが中断しても続きから再開できるようにするため）
- 既に結果があるケースは `--resume` で再実行しない。`--rerun <ID>` で個別に再実行できる
- 各ケースにタイムアウトを設ける。超過したら失敗として記録し、次へ進む
  （プロセスを確実に終了させること。ハングで全体が止まらないようにする）
- 各ケースの記録内容: ID、コマンド、終了コード、所要時間、
  ピークメモリ（取得可能なら）、判定結果、判定理由
- **標準出力・標準エラーの全文を results.jsonl に保存しない。**
  文字起こし本文が混入するため、先頭・末尾の数行と、
  エラー行の抽出のみを記録する

ハーネス自体はコミットしてください。`output/` 配下の結果ファイルはコミットしません。

## 合否判定の基準

人間の主観を排除するため、以下の機械的な基準で判定します。

### ASR 出力の妥当性

| 項目 | 合格条件 |
|---|---|
| 言語判定 | `ja` と判定される（`--language auto` 指定時） |
| セグメント数 | 音声長に対して極端でない（3分音声で 5〜300 程度） |
| タイムスタンプ | すべて単調増加、`start < end`、音声長を超えない |
| 単語タイムスタンプ | セグメント範囲内に収まる |
| テキスト | 空文字のセグメントが全体の 10% 未満 |
| 文字種 | 日本語（かな・漢字）を含む文字が全体の 50% 以上 |
| ハルシネーション | 完全に同一のテキストが 5 回以上連続しない |
| カバレッジ | 発話区間の合計が音声長の 10%〜100% の範囲 |

### 話者分離出力の妥当性

| 項目 | 合格条件 |
|---|---|
| 話者数（自動） | 1 以上、20 以下。会議音声なら 2 以上が期待される |
| 話者数（指定時） | `--num-speakers N` で N 個ちょうどになる |
| 話者数（範囲指定時） | `--min/--max` の範囲に収まる |
| 区間 | 重なりがない（exclusive 使用時）、単調増加 |
| ターン長 | 平均ターン長が 0.5 秒以上（極端な細分化がない） |
| 割当 | `UNKNOWN` の割合が全セグメントの 20% 未満 |
| 分布 | 1話者が全体の 99% を超えない（実質単独話者になっていない） |

上記を外れた場合、**即座に「不具合」と断定せず「要確認」として記録**し、
可能なら原因を調査してください。実音声の性質による可能性もあるためです。
ただし、明らかな異常（話者が1人しか検出されない、タイムスタンプが逆転する、
`UNKNOWN` が過半数）は不具合として扱ってください。

### 出力形式の妥当性

| 形式 | 確認事項 |
|---|---|
| SRT | 連番が 1 から連続、タイムコード書式 `HH:MM:SS,mmm`、空行区切り |
| VTT | `WEBVTT` ヘッダー、タイムコード書式 `HH:MM:SS.mmm` |
| JSON | `schema_version: 1`、必須キーの存在、パース可能 |
| TXT | 話者名の接頭辞が付与されている |
| MD | メタ情報セクションと本文が存在する |
| 文字コード | UTF-8。SRT の BOM オプションが効く |

## 試験項目

以下をグループ単位で実施し、各グループ終了時にコミットしてください。

### G1. 疎通確認（clip_30s）

1. `--no-diarization` で 5 形式すべてを出力
2. 出力ファイルが 5 つ生成される
3. JSON の構造が妥当
4. 終了コード 0

**ここで失敗したら、以降に進まず原因を調査・修正してください。**

### G2. 基本機能（clip_03m）

1. 既定形式での実行
2. 5 形式すべての出力と、書式の妥当性検証
3. `--output-dir` の指定が効く
4. 出力ファイル名の衝突時に連番が付く
5. wav / m4a / mp4 で同等の結果が得られる
6. `--language ja` と `--language auto` の双方が動作する
7. SRT の BOM オプション

### G3. 話者分離（clip_03m）

**この経路は実モデルでの検証が初めてです。重点的に行ってください。**

1. 既定設定（話者数自動）での実行
2. `--num-speakers 2` / `3` / `4`
3. `--min-speakers 2 --max-speakers 5`
4. `--num-speakers` と `--min/--max` の同時指定がエラーになる
5. `--diarization-model` の明示指定
6. exclusive 区間が使われていることを、JSON の話者区間の重なりから確認
7. 話者表示名の置換（`[output].speaker_labels`）
8. 統計量が「話者分離出力の妥当性」を満たす

初回はモデルのロードに時間がかかります。タイムアウトを十分に取ってください。

### G4. レジューム・ジョブ管理（clip_03m / clip_10m）

1. 同一入力・同一設定の 2 回目が全ステージをスキップする
2. 出力形式のみ変更した再実行が export ステージのみで完了する
3. `--output-dir` のみ変更した再実行が export のみで完了する
4. `--asr-model` を変えた再実行が ASR 以降を再計算する
5. `--num-speakers` を変えた再実行が話者分離以降を再計算する
6. `--force` で全ステージが再実行される
7. `--no-resume` の挙動
8. clip_10m の ASR 実行中に SIGINT を送り、終了コード 130 で停止する
9. 中断後の再実行が、中断箇所から再開する
10. 同一ジョブに対する 2 プロセス同時実行がロックで拒否される
11. ロックファイルの PID を存在しない値に書き換えると、古いロックとして回収される
12. `--force-unlock` が動作する
13. `manifest.json` を意図的に破損させたジョブが `corrupt` として一覧に出る
14. `jobs list` / `jobs show` / `jobs clean --failed` / `--older-than` / `--all`
15. ジョブディレクトリに `utteran.log` が生成され、
    **トークンが含まれていない**ことを確認

### G5. バッチ処理

`output/_testdata/batch/` に、正常ファイル 3 つ、`broken.mp4`、`notmedia.txt` を配置。

1. フォルダ指定で全件が名前順に処理される
2. `broken.mp4` の失敗後も処理が継続する
3. 集計（成功・スキップ・失敗）が表示される
4. 一部失敗時の終了コードが 5
5. 全件失敗時の終了コードが 1
6. `--recursive` の動作
7. `--include` / `--exclude` の glob 選別
8. `--dry-run` で対象一覧のみ表示され、処理が走らない
9. バッチ中にモデルの再ロードが発生しない（ログで確認）
10. `output/` や jobs ディレクトリの生成物が、再帰処理の入力候補に含まれない
11. バッチ実行中の SIGINT で終了コード 130

### G6. モデル管理

1. `models list` / `models list --available`
2. `models path`
3. `models verify`
4. `models download` の ID 省略時の番号選択（非対話環境では拒否されること）
5. 曖昧な ID 指定が候補提示付きで拒否される
6. 未登録 ID の指定がエラーになる
7. 小さいモデル（tiny 等が登録されていれば）の取得・検証・削除・再取得
8. **トークンを空にした状態**で gated モデルの取得を試み、
   エラーが「トークン未設定」として分類される
   （`.env` を編集せず、環境変数の上書きで行うこと）
9. 未取得モデルを `transcribe` で指定した際、
   非対話環境で終了コード 3 と取得コマンドの案内が出る

大容量モデルの削除・再取得は時間がかかります。既に取得済みの large-v3-turbo と
pyannote は**削除しないでください。**

### G7. デバイス・プロファイル

1. `devices` の人間向け表示
2. `devices --json` が妥当な JSON を返し、キー構造が安定している
3. 末尾の auto 選択結果の表示
4. `--device cpu` の明示指定
5. `--device cuda` の明示指定（cpu プロファイルではエラーになるはず）
6. `--device cuda:99` のような不正な指定がエラーになる
7. 存在しないバックエンド名の指定がエラーになる

### G8. 設定

1. `config path` / `config init` / `config show`
2. `config init` が既存ファイルを上書きしない
3. `config show` にトークンが含まれない
4. 優先順位の検証: 同一項目を config.toml、`.env`、環境変数、CLI 引数で
   別々に指定し、CLI 引数が勝つこと
5. `config.toml` にトークンを書いた場合に無視され、警告が出ること
   （**実際のトークンではなくダミー値を使うこと**）
6. `[alignment]` の閾値変更が結果に反映される
7. 不正な設定値がエラーコード 2 になる

### G9. エラー処理・終了コード

| ケース | 期待する終了コード |
|---|---|
| 正常終了 | 0 |
| 不正な引数の組み合わせ | 2 |
| ffmpeg が見つからない（PATH を隠して実行） | 3 |
| モデル未取得 | 3 |
| トークン未設定で話者分離を要求 | 2 または 3（実装に合わせて確認） |
| 入力ファイルが存在しない | 4 |
| `empty.mp4` / `notmedia.txt` | 4 |
| SIGINT | 130 |
| バッチ一部失敗 | 5 |

すべてのエラーで、**スタックトレースがそのまま表示されないこと**、
対処方法が示されることを確認してください。
`--verbose` 指定時のみ詳細が出ることも確認します。

### G10. セキュリティ

1. 生成されたすべてのログ、出力、報告書に対し、
   `hf_` で始まる文字列や `.env` の値が含まれていないことを検索で確認
2. `--verbose` 実行時のログにもトークンが出ないこと
3. 例外発生時のメッセージにトークンが混入しないこと
4. `git status` で `.env`、`input/`、`output/` の中身が追跡候補に出ないこと

### G11. 文書整合性

1. README に記載された全コマンドを実際に実行し、動作すること
2. README のオプション一覧と `--help` の出力が一致すること
3. README のトークン優先順位の記述と `要件定義.md` の記述が一致すること
   （**現在、README は3段階、要件定義は5段階と食い違っている可能性があります。
   実装を確認し、正しい方に統一してください**）
4. 終了コード表が実装と一致すること
5. `要件定義.md` に記載された設定項目が実装に存在すること

### G12. `start.ps1`

Windows 対話フロントです。自動試験は限定的にしかできません。

1. PowerShell の Parser API による構文検証
2. 各メニュー項目が組み立てるコマンド文字列の妥当性を、
   コードを読んで確認する
3. 自動実行できない項目は「未実施」として記録する

### G13. 長時間耐久試験（実ファイル・2時間）

**これは最後に実施してください。** ここまでで発見した不具合を修正した後の
コードで実行します。

事前にプロファイルを cuda へ切り替えてください。CPU では時間内に完了しません。

```powershell
.\setup.ps1 -Profile cuda
```

切り替え後、`devices` で CUDA が使用可能になっていることを確認してから実行します。

1. **話者分離なし**で 2 時間ファイルを処理し、所要時間とピークメモリを記録
2. 上記が成功したら、**話者分離あり**で処理し、所要時間とピークメモリを記録
3. 出力の妥当性を「合否判定の基準」で検証
4. 処理中の VRAM 使用量を記録（取得可能なら）
5. 完了後、同一ファイルの再実行が全ステージをスキップすることを確認

**メモリ不足やVRAM不足で失敗した場合、それは既知の課題です**
（`要件定義.md` 13章。分割処理は Phase 4）。
その場合、以下を確認して記録してください。

- エラーメッセージが理解可能な内容か（生の OOM トレースではないか）
- 中間結果が保持され、レジュームが可能な状態か
- CPU での再実行が可能か（時間がかかるため、実行するかは所要時間の見積もり次第）

失敗しても不具合として修正を試みる必要はありません。Phase 4 の課題として
記録してください。ただし**エラーメッセージが不親切な場合は、それは修正対象**です。

タイムアウトは十分に長く設定してください（話者分離ありで最低 4 時間）。
ただし、明らかに進捗が止まっている場合（30分以上ログ更新なし）は
ハングとして中断し、記録してください。

### G14. 事後処理

1. 全試験の結果を集計
2. cuda プロファイルのまま残すか、cpu へ戻すかを判断し、記録
   （利用者は元々 cpu プロファイルでした。cuda が問題なく動作したなら
   cuda のまま残し、その旨を報告書に明記してください）
3. `output/_testdata/` の大きなファイルの整理（結果は残す）
4. jobs ディレクトリの状態を記録（2時間ファイルのジョブは削除しないこと）
5. 最終コミット

## 不具合を発見した場合

### 手順

1. 再現する最小の手順を特定する
2. 原因を調査する
3. **修正前に、その試験の失敗結果をコミットする**（`test:` 接頭辞）
4. 修正を実装する
5. **回帰テストを追加する**（モデル不要でテストできる形にすること）
6. `ruff check`、`mypy`、`pytest -m "not requires_model"` を通す
7. 該当する文書（`README.md` / `要件定義.md` / `変更履歴.md` / `AISTATE.md`）を更新する
8. `fix:` 接頭辞でコミットする
9. 失敗した試験を再実行し、合格することを確認する

### 修正すべきでない場合

以下は修正せず、報告書と `AISTATE.md` に記録してください。

- Phase 3 / Phase 4 の未実装機能に起因するもの
- 仕様の変更を伴い、利用者の判断が必要なもの
- 実音声の性質による可能性があり、不具合と断定できないもの
- 修正の影響範囲が大きく、他の試験結果を無効化するもの

判断に迷う場合は**修正しない**を選び、記録してください。
外出中の利用者に確認できないため、破壊的な変更は避けるべきです。

### 優先順位

複数の不具合を発見した場合、以下の順で対応してください。

1. データ損失、秘密漏洩につながるもの
2. 正常系が動作しないもの
3. エラー処理が不適切なもの（トレースがそのまま出る等）
4. 文書と実装の不一致
5. 表示上の軽微な問題

時間が足りない場合、優先度の低いものは記録のみとして構いません。

## 報告書

`docs/受入試験報告.md` を作成してください。

### 構成

```markdown
# 受入試験報告

## 概要
- 実施日時、所要時間
- 開始時コミット / 終了時コミット / ブランチ
- 実行環境（OS、Python、uv、プロファイル、GPU）
- 総合結果（合格 / 条件付き合格 / 不合格）

## 試験結果サマリー
| グループ | 実施 | 合格 | 失敗 | 未実施 | 保留 |

## 発見した不具合と対応
| ID | 内容 | 深刻度 | 対応 | コミット |

## 未修正のまま残した事項
（理由と、利用者の判断が必要な点）

## 性能測定結果
| 対象 | 音声長 | 構成 | 所要時間 | 実時間比 | ピークメモリ | VRAM |

## 未実施・保留の試験と理由

## 利用者への確認事項
（判断を仰ぎたい点を箇条書き）

## 品質確認用の出力ファイル
（文字起こしの内容を目視確認したい場合に見るべきファイルのパス。
 内容そのものは記載しない）
```

**報告書に文字起こしの本文を含めないでください。**

### 性能測定について

以下は必ず記録してください。利用者が実運用の可否を判断するための情報です。

- 3分音声の処理時間（ASR のみ / 話者分離込み、CPU / CUDA）
- 2時間音声の処理時間（同上）
- 実時間比（音声長 ÷ 処理時間）
- ピークメモリ使用量
- モデルのロード時間

## 時間配分の目安

外出中の実行を想定しています。以下を目安にしてください。

| 区分 | 目安 |
|---|---|
| 準備（G0〜素材生成、ハーネス作成） | 30分 |
| 機能試験（G1〜G12） | 2〜3時間 |
| 不具合修正 | 発見次第、随時 |
| 耐久試験（G13） | 2〜5時間 |
| 報告書作成（G14） | 30分 |

**機能試験を終える前に耐久試験を始めないでください。**
不具合を含んだコードで2時間の処理を回すと、時間が無駄になります。

時間が足りなくなった場合、G13 の「話者分離あり」を省略し、
「話者分離なし」の結果のみを記録してください。

## 禁止事項

- `input/` のファイルを変更・削除すること
- `.env` を読み取り、編集し、内容を出力すること
- 文字起こし結果を報告書、AISTATE、コミットメッセージに含めること
- `git push`、履歴の書き換え、未コミット作業の破棄
- 実データを含むファイルをコミットすること
- 試験を実施していないのに「合格」と記録すること
- 判断に迷う破壊的な変更を、利用者の確認なしに行うこと
- タイムアウトしたケースを放置してハングさせること

## 不明点があった場合

利用者は外出中で確認できません。以下の方針で進めてください。

1. `要件定義.md` に記載があれば、それに従う
2. 記載がなく、安全側に倒せる選択肢があれば、それを選ぶ
3. どちらとも判断できない場合、その試験を「保留」として記録し、次へ進む
4. すべての保留事項を報告書の「利用者への確認事項」にまとめる

**止まらないこと。記録して進むこと。**
