## J-1 — 明示指定した構成が変更される

### 症状

> ASRのモデルを意図的に openvino+vulkan を選択しても、なんか勝手に vulkan に戻る

### 原因

`src/utteran/asr/registry.py` の 22〜24 行:

```python
return WhisperCppBackend(
    ...,
    allow_fallback=True,      # ← 無条件に True
)
```

`WhisperCppBackend.__init__` は本来こう判定します。

```python
self._allow_fallback = (
    self.settings.variant == "auto" if allow_fallback is None else allow_fallback
)
```

**`variant == "auto"` のときだけ退避する**という設計ですが、
レジストリが `allow_fallback=True` を明示的に渡すため、**判定が上書きされています。**

結果として、`openvino_vulkan` を明示指定しても初期化に失敗すると
`vulkan` へ退避します。

**Phase 1 以来の「明示指定時はフォールバックしない」方針に反しています。**

### 実施内容

1. **レジストリの呼び出しを修正する**
   - `allow_fallback` を無条件で渡さない
   - `variant == "auto"` のときだけ退避する設計に戻す
2. **なぜこの呼び出しが入ったのかを確認する**
   - 意図があったなら、その意図を満たす別の方法を検討する
   - 単なる誤りなら、そう記録する
3. **同じ方針が他のバックエンドで守られているかを確認する**
   - faster-whisper、pyannote の device 指定
   - 明示指定時に退避していないか

### 回帰テストを必ず追加すること

- `variant` を明示指定した場合、初期化失敗時に退避せずエラーになる
- `variant = "auto"` の場合、退避する
- **退避が1回だけであること**

**この不具合は、テストが存在しなかったために見過ごされました。**

## J-2 — ログ基盤の整備

### 背景

今回、以下が判断できませんでした。

- OpenVINO エンコーダ IR が実際に読み込まれたか
- どの構成で実行されたか、退避したか
- GUI 経由と CLI で挙動が違うのか

**実行時の事実が記録されていないためです。**

whisper.cpp は OpenVINO エンコーダの初期化結果を標準エラーへ出力しますが、
utteran はそれを保持していません。

### 設計方針

**GUI に表示する必要はありません。**後から追跡できることが目的です。

```
<log_dir>/
├── app.log                                アプリ本体の動作（ローテーション）
├── cli/
│   └── <timestamp>-<command>.jsonl        CLI 実行ごとの構造化ログ
├── raw/
│   └── <job_id>/
│       ├── whisper-cpp.stderr.log         サブプロセスの生出力（既定で無効）
│       └── pyannote.stderr.log
└── diagnostics/
    └── <timestamp>-devices.json           環境スナップショット
```

### 保存場所

**既定はインストール先の `logs` フォルダ**とします。

ただし以下に対応してください。

- **書き込み不可の場合、ユーザーデータ領域へ自動退避する**
  （将来 `C:\Program Files` への導入を許した場合、書き込みが UAC 仮想化に
  回されるため。現在の既定インストール先は書き込み可能ですが、備えておくこと）
- 設定と環境変数で変更可能にする
- **退避した場合、その事実を記録し、`utteran` から場所を確認できるようにする**
- リポジトリから起動した場合、リポジトリ内に `logs/` ができるため、
  **`.gitignore` に追加すること**

### 構造化ログ（既定で有効）

**本文を含めず、実行の事実を記録します。**

最低限、以下を記録してください。イベント名と項目は判断してよいですが、
**「どの構成で実行されたか」が後から確定できること**が要件です。

| 記録すべき事実 | 例 |
|---|---|
| 解決されたバックエンドと構成 | `asr_backend_resolved`（variant、実行ファイル、モデル） |
| **OpenVINO IR のロード結果** | `openvino_ir_loaded`（パス、成否） |
| **構成の退避** | `variant_fallback`（元、先、理由） |
| デバイスの決定 | 話者分離を含む |
| 各ステージの所要時間と実時間比 | |
| モデルの取得、IR の生成 | |
| エラーと分類 | |

**IR のロード判定を、生ログのパースに頼らないでください。**
whisper.cpp の出力からロード成否を判定し、**構造化イベントとして記録**する
実装にしてください。文言が変わっても壊れないよう、判定箇所は1か所に集約すること。

### 生出力（既定で無効）

**サブプロセスの標準エラーには、文字起こし本文が混入する可能性があります。**

これまで「本文をログに残さない」方針を守ってきました。
**この方針を条件付きで緩めることになるため、以下を厳守してください。**

- **既定は無効。**設定で明示的に有効化したときだけ保存する
- 有効化する際、**本文が含まれる可能性がある旨を警告する**
- 保存先は `raw/` 配下に隔離する
- **秘密値のマスクは必ず通す**
- `.gitignore` の対象にする
- **有効になっていることが、GUI から分かるようにする**
  （有効にしたまま忘れる事態を避けるため）

### ローテーションと自動削除

**日数と容量の両方で削除してください。**

- 既定値を決め、根拠を記録する
- 設定で変更可能にする
- `raw/` は容量が大きくなりやすいため、別の上限を設けることを検討する
- 削除の実行タイミングを決める（起動時、定期、など）
- **削除された事実を記録する**

### 確認コマンド

```
utteran logs path      保存場所の表示
utteran logs clean     手動削除
```

GUI からも保存場所を開けるようにしてください。

## J-3 — 文字起こし画面が横に広がる

### 原因

`src/utteran_gui/web/styles.css` の 86 行目:

```css
.stage-list { grid-template-columns: repeat(5, 1fr); }
.stage-list li { border: ...; padding: 10px; font-size: 11px; }
```

**`1fr` は `minmax(auto, 1fr)` と同義**で、列が内容の最小幅より縮みません。

ステージ名（「音声抽出・正規化」「文字起こし (ASR)」など）が5列並ぶため、
5列すべてが折り返さない幅を要求し、**パネルとページ全体を押し広げます。**

`li` に `min-width: 0` も付いていません。

**`.environment-strip` も同じ構造ですが、`article` に `min-width: 0` が
付いているため回避されています。`.stage-list li` だけが対策漏れです。**

「文字起こしページだけ」に出る理由も、`stage-list` が workspace ビューにしか
存在しないためです。

### 修正

```css
.stage-list { grid-template-columns: repeat(5, minmax(0, 1fr)); }
.stage-list li { min-width: 0; }
```

### あわせて確認すること

1. **`1fr` を使っているグリッドをすべて確認し、`min-width: 0` の
   有無を点検してください。**同種の問題が他にないか
2. `@media (max-width: 900px)` に `.stage-list` の調整がありません。
   狭い幅で5列のまま押し込まれるため、調整を検討してください
3. `.token-card input { width: 220px }` が固定幅です。溢れないか確認してください
4. `index.html` に `class="view viewer-view"` とありますが、
   **CSS に `.viewer-view` の規則が存在しません。**
   不要なら削除、必要なら定義してください

### 検証

- 各画面で横スクロールが発生しないこと
- ウィンドウ幅を変えても崩れないこと
- ダーク／ライト両方
- **長いステージ名、長いファイル名、長いモデル名でも崩れないこと**

## J-4 — GUI が CLI より遅い疑い

### 症状

> なんか気のせいかどうかわからないのだけれども、CLIよりGUIのほうが時間かかる気がする

### 調査

**J-1 が原因である可能性があります。**GUI が明示指定した構成が退避していれば、
`openvino_vulkan`（Phase 3d 実測: 24分46秒の音声で65秒）が
`vulkan`（同 110秒）になり、**約1.7倍遅くなります。**

J-1 と J-2 の修正後、以下を実測してください。

- 同一音声を CLI と GUI で処理する
- 同一の構成を明示指定する
- **所要時間と、ログに記録された実際の構成を比較する**
- 差がある場合、ログから原因を特定する

**実データを使う場合、文字起こしの内容を記録しないこと。**
所要時間、実時間比、構成のみを記録します。

差がなければ「差はなかった」と記録して構いません。

## 実装上の注意

### 機密データ

- **構造化ログに本文を含めない**
- 生出力は既定で無効。有効時も秘密値のマスクを通す
- ファイルパスの扱いに注意する（個人情報を含みうる）
- 実データの文字起こし内容を報告に記録しない

### 破壊的変更への配慮

- 既存の venv、モデル、設定、ジョブを壊さない
- ジョブディレクトリの `utteran.log` は維持する
  （新しいログ基盤との関係を整理し、記録すること）
- Phase 5a〜5i の機能を壊さない

### コミット

- ブランチ `fix/phase5j-fallback-and-logging`
- 項目単位でコミットする
- `git push` は実行しない
- **ログファイルをコミットしない**

---

## 禁止事項

- 明示指定された構成でフォールバックすること
- 構造化ログに文字起こし本文を含めること
- 生出力の保存を既定で有効にすること
- IR のロード判定を生ログのパースに散在させること
- 書き込み不可の場所へ黙って書き込みを試み、失敗を握りつぶすこと
- 配布版で確認せずに完了と報告すること
- `要件定義.md` を更新せずに仕様を変えること
