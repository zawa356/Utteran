## Step 1 — 原因の特定

### 有力な仮説

Phase 5k で**デバイスプローブがサブプロセス化**されました。

以前は同一プロセス内で実行していたものが、**プローブごとに別プロセスを起動**する
構造に変わっています。

| 仮説 | 確認方法 |
|---|---|
| A. 起動時にプローブが同期実行され、UI をブロックしている | 起動シーケンスのログ |
| B. キャッシュが効かず、毎回プローブが走る | キャッシュファイルの有無と内容 |
| C. サブプロセスの起動自体が、GUI の exe 環境で失敗・ハングする | プローブ単体の実行 |
| D. `CREATE_NO_WINDOW` とプロセス生成の組み合わせによる問題 | フラグを変えて比較 |
| E. 標準入出力のパイプがブロックしている | `communicate` の使い方 |

**C と E に注意してください。**

PyInstaller で固めた exe から Python のサブプロセスを起動する場合、
**開発環境とは実行のされ方が異なります。**`sys.executable` が
GUI の exe を指すため、意図しない再帰起動が起きる可能性があります。

**開発環境（`gui.ps1`）では再現せず、配布版でのみ発生する**場合、
この線が濃厚です。

### 確認すべきこと

- **開発環境（`gui.ps1`）で再現するか**
- **配布版（exe）でのみ発生するか**
- 0.1.7 の配布版では発生しないか

**この3点の切り分けが、原因の範囲を決めます。**

## Step 2 — 修正

原因に応じて修正してください。**ただし以下は必ず満たすこと。**

### 起動時に UI をブロックしない

**デバイス検出は、起動を止める理由になりません。**

- 起動時に同期実行しない
- 必要になった時点で、非同期に実行する
- 検出中も UI が操作できる
- 検出が終わっていない項目は「確認中」と表示する

**Phase 5k で「タイムアウトを設ける」と指示しましたが、
それ以前に「起動を止めない」ことが前提です。**

### サブプロセスの起動を、配布版で検証する

- PyInstaller 環境で `sys.executable` が何を指すかを確認する
- プローブ用のプロセスを、**確実に Python インタプリタとして起動する**
- 再帰起動が起きないことを確認する
- パイプがブロックしないことを確認する

### キャッシュを確実に効かせる

- 2回目以降の起動で、プローブが走らないこと
- キャッシュの保存先が、配布版でも書き込み可能なこと
- キャッシュが壊れていても起動できること

## Step 3 — Phase 5k の完了

### 3-A. 回帰テストの修正

`tests/test_faster_whisper.py::test_auto_device_falls_back_to_cpu` が
サブプロセス分離により失敗しています。

**このテストが守っていた挙動は重要です。**
「CUDA が使えない環境で CPU へ退避する」という、まさに Core i7 機で
問題になっている経路です。

- サブプロセス分離に対応したテストへ書き換える
- **monkeypatch が届かないなら、プローブ結果を注入できる形にする**
- 挙動そのものは変えないこと

### 3-B. `test_native.py` の3件

`openvino` extras の有無に依存するテストです。

- **パッケージの有無に依存しない形へ書き換える**
- 「入っていない前提」を、注入や skip 条件で表現する
- どの extras 構成でも通ることを確認する

### 3-C. 文書の更新

Phase 5k の指示書が要求していた更新が未完です。

- `README.md`: デバイス検出の挙動、タイムアウト、キャッシュ
- `要件定義.md`: プローブの分離とタイムアウトの仕様、キャッシュ、推奨ロジック
- `変更履歴.md`: 0.1.8 の内容と、今回の修正

## 実装上の注意

### この不具合が生まれた経緯を記録すること

`AISTATE.md` に以下を記録してください。

> Phase 5k が実機未検証（WIP）のまま main へマージされ、

> 実行環境の影響を強く受けるため、配布版での検証を経ずに

- Phase 5k の意図（タイムアウトによるハング回避）は維持する
