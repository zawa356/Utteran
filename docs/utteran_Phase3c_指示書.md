### 利用可能になったもの

**`.env` に pyannote community-1 の有効な Hugging Face トークンが設定されています。**

Phase 3a / 3b では本機にトークンとモデルがなく、以下が保留になっていました。

**`.env` の内容を読み取って表示しないでください。**

### Phase 3a で確認済みの事実

- `torch.xpu.is_available()` は `True`、デバイス名は `Intel(R) Arc(TM) 140T GPU (32GB)`
- pyannote の segmentation が使う代表的な層（`Conv1d`、双方向 `LSTM`、`InstanceNorm1d`）は
  XPU 上で forward 計算と CPU への転送に成功している
- **ただし community-1 の実パイプライン全体での動作は未確認**

つまり「基本演算は通るが、実モデルで通るかは不明」という状態です。
**本フェーズの最初の作業は、この確認です。**

## Step 0 — 実モデルでの XPU 動作確認

**実装より先に、これを確認してください。** 結果によって以降の設計が変わります。

1. community-1 のモデルを取得する（`utteran models download`）
2. pyannote のパイプラインを XPU デバイスへ載せ、短い音声で実行を試みる
3. 結果を `AISTATE.md` に記録する

確認すべき点:

- `Pipeline.to(torch.device("xpu"))` が成功するか
  （pyannote 内部に CUDA 前提の分岐がないか）
- segmentation モデルと話者埋め込みモデルの双方が XPU 上で動作するか
- 未対応オペレーターによる例外が出ないか
- 出る場合、`PYTORCH_ENABLE_XPU_FALLBACK` 等の環境変数で回避できるか
  （回避できる場合、その代償として速度がどうなるかも確認すること）
- CPU 実行と XPU 実行で、話者数や話者区間に有意な差が出ないか

### 結果に応じた分岐

**A. 問題なく動作する場合** → Step 1 以降を予定どおり実装する

**B. 一部のオペレーターが未対応で、フォールバック環境変数で動作する場合**
→ 実装するが、環境変数の設定をバックエンド側で行い、速度への影響を記録する。
既定で有効にするかは実測に基づいて判断し、要件定義へ記載する

**C. 実用にならない、または動作しない場合**
→ **無理に実装しないでください。** 以下を行い、本フェーズを終了します

- 失敗の内容と原因を詳細に記録する
- XPU を選択肢として提示しない実装にする（`devices` で「未対応」と表示する）
- Intel 環境では話者分離が CPU 実行になることを README に明記する
- 代替案（sherpa-onnx を OpenVINO Execution Provider で動かす経路）を
  次フェーズの候補として記録する

判断は実測に基づいて行い、根拠を必ず記録してください。

## Step 1 — デバイス指定の拡張

### 設定

```toml
[diarization]
device = "auto"    # auto | cpu | cuda | cuda:N | xpu | xpu:N
```

### auto の優先順位

```
1. CUDA が利用可能           → cuda:0
2. XPU が利用可能            → xpu:0
3. いずれもなし              → cpu
```

ASR 側の auto 選択（Phase 3b で実装済み）と組み合わさるため、
Intel 環境では以下の構成になります。

```
ASR:        whisper-cpp / openvino_vulkan
話者分離:   pyannote / xpu:0
```

この組み合わせが `devices` の末尾に理由付きで表示されることを確認してください。

### プロファイルとの整合

torch XPU 版は `intel` プロファイル（`xpu` extras）にのみ含まれます。

- `cpu` / `cuda` プロファイルで `xpu` を明示指定された場合、
  「このプロファイルでは利用できない」と分かるエラーを出す
- 必要なプロファイルと `setup.ps1` の実行を案内する
- 単に「デバイスが見つからない」で終わらせないこと

## Step 2 — pyannote バックエンドの XPU 対応

### 実装方針

Phase 1 以来の方針を維持します。

- **`auto` のときのみフォールバックする。** XPU の初期化に失敗した場合、
  CPU へ 1 回だけ退避し、理由を表示・記録する
- **明示的に `xpu` を指定された場合は退避せず、エラーとする**
- 退避が発生したことを、処理結果にも記録する（ジョブログと `merged.json`）

### 実装上の注意

- Phase 2 で CUDA に対して行っている「最小テンソル確保による初期化確認」と
  同等の probe を XPU にも実装する
- XPU のメモリ不足を検出し、CUDA の VRAM 不足と同様に分かりやすいエラーにする
- **Arc 140T は共有メモリ構成のため、VRAM の考え方が dGPU と異なります。**
  システム RAM を消費するので、長時間音声では RAM 側の枯渇として現れる可能性があります。
  この違いを踏まえたエラーメッセージにしてください
- 処理後に XPU のメモリを解放する（`unload()` で明示的に解放すること）

### 数値差の扱い

CPU 実行と XPU 実行で、浮動小数の演算順序の違いから結果が完全一致しない可能性があります。

- ステージ別 `config_hash` に device が含まれるため、
  デバイスを変えると話者分離が再計算されます。これは仕様として正しい挙動です
- ただし、**同一デバイスでの再実行が毎回異なる結果になる**場合は問題です。
  同一条件で 2 回実行し、話者数と区間が一致することを確認してください

## Step 4 — 実機検証

以下は Phase 1 以来の宿題を含みます。すべて実施し、結果を記録してください。

### 機能確認

- [ ] community-1 が XPU で動作する（または動作しない理由が明確に記録されている）
- [ ] CPU 実行と XPU 実行で、話者数と話者区間に有意な差がない
- [ ] 同一条件の 2 回実行で結果が一致する
- [ ] `auto` が Intel 環境で `xpu:0` を選ぶ
- [ ] XPU 失敗時に CPU へ退避し、明示指定時は退避しない
- [ ] `cpu` / `cuda` プロファイルで `xpu` を指定した際、分かりやすいエラーが出る

### 結合検証（Phase 3b の保留事項）

whisper-cpp の単語タイムスタンプと pyannote を結合した結果の妥当性を確認します。

同一音声に対して以下を実行し、比較してください。

| ASR | 話者分離 |
|---|---|
| faster-whisper / cpu | pyannote / cpu |
| whisper-cpp / openvino_vulkan | pyannote / cpu |
| whisper-cpp / openvino_vulkan | pyannote / xpu |

比較する指標（受入試験と同じ機械的基準を使うこと）:

- 検出された話者数
- 話者ごとの発話時間の分布
- 平均ターン長
- `UNKNOWN` の割合
- セグメント数

**whisper-cpp 経由の話者割当が、faster-whisper 経由と同等の妥当性を持つこと**が
確認の目的です。単語数が 18% 多いことが `align.py` の閾値に悪影響を与えていないかを、
ここで最終確認します。

差が出た場合、`align.py` の閾値をバックエンド別に調整する必要があるかを判断し、
判断と理由を記録してください。

### 性能測定

3 分程度のクリップで測定してください。

| 構成 | 所要時間 | ピーク RAM |
|---|---|---|
| pyannote / cpu | | |
| pyannote / xpu | | |

さらに、**Intel 環境での最速構成による通し測定**を行ってください。

```
ASR: whisper-cpp / openvino_vulkan
話者分離: pyannote / xpu（動作する場合）
```

`input/` の実ファイル（約 2 時間 20 分）で実測し、以下を記録します。

- 総所要時間と実時間比
- ステージ別の所要時間
- ピーク RAM
- 出力の妥当性（受入試験と同じ統計的基準）

**実データの文字起こし内容は記録しないこと。**

参考として、CUDA 機での実測値は以下でした（GTX 1070 Ti）。

| 対象 | 構成 | 所要時間 | 実時間比 |
|---|---|---:|---:|
| 2時間19分 | CUDA、ASR＋話者分離 | 770.6秒 | 10.85x |

Intel 機でこれと比較できる数値が得られると、環境選択の判断材料になります。

### 長時間音声でのメモリ

Arc 140T は共有メモリ構成のため、2 時間超の音声で pyannote を XPU 実行した際に
システム RAM を大量消費する可能性があります。

- ピーク RAM を測定する
- 不足した場合、エラーメッセージが理解可能かを確認する
- 中間結果が保持され、CPU での再実行が可能かを確認する

**メモリ不足で失敗しても、それ自体は不具合ではありません**
（`要件定義.md` 13章の既知課題）。ただしエラーメッセージが不親切なら修正対象です。

## 実装上の注意

### 破壊的変更への配慮

- 既存の CPU / CUDA 経路の挙動を変えない
- 既存のジョブ、モデル、設定を無効化しない
- CLI は追加のみとし、既存の引数体系を変えない

### トークンの扱い

- `.env` の内容を読み取って表示しない
- ログ、例外、報告に token 形式の値が出ないことを確認する
- これまでのマスク処理が新しい経路でも機能することを確認する

### コミット

- ブランチ `feature/phase3c-xpu-diarization`
- Step 単位でコミットする
- `git push` は実行しない
- 実データ（`input/`、`output/` の中身）をコミットしない
