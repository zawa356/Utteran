着手前に必ず以下を読んでください。

## Step 0 — 公開リポジトリの安全確認（最優先）

### 背景

**リポジトリは既に GitHub で公開されています。**

一方、開発では実際の社内会議の録音を使用しており、**その入力ファイル名には
個人のメールアドレスと組織名が含まれています。**

ファイル名は、コミットされた音声ファイルがなくても以下の経路で履歴に残りえます。

- テストフィクスチャやログに記録されたパス文字列
- ドキュメント内のコマンド例
- 受入試験の結果ファイル
- 過去のブランチ、マージ済みブランチ、削除されたコミット

**これらが公開履歴に含まれていないことを確認するのが Step 0 の目的です。**

### 実施内容

**全ブランチ・全コミット・全オブジェクトを対象に走査してください。**
現在のワーキングツリーだけを見ても意味がありません。

走査対象:

1. 全コミットのファイルパス（`git log --all --name-only`、`git rev-list --objects --all`）
2. 全コミットの差分内容
3. コミットメッセージ
4. タグ、リモート追跡ブランチ
5. 到達不能なオブジェクト（`git fsck --unreachable`）

検出すべきパターン:

| 分類 | 内容 |
|---|---|
| 個人情報 | メールアドレス形式、組織ドメイン、人名らしき文字列 |
| 秘密値 | `hf_` 形式のトークン、その他 API キー形式 |
| メディア | 音声・動画の拡張子を持つファイル |
| 成果物 | 文字起こし出力（srt / vtt / json / txt / md のうち、実データ由来のもの） |
| 環境 | `.env`、認証情報を含む設定 |
| パス | 実データのファイル名を含む文字列 |

**メールアドレスの検出は正規表現で機械的に行ってください。**
特定のアドレスを探すのではなく、形式に一致するものをすべて洗い出す方式にします。
検出結果を報告する際も、**アドレスそのものを報告書やコミットに書かないこと。**
「どのコミットのどのファイルに何件」という形で報告してください。

可能であれば `gitleaks` などの既製ツールも併用してください。
導入が難しい場合は、自前の走査スクリプトで構いません。
いずれの場合も、走査スクリプトは `tools/` に残し、再実行可能にしてください。

### GitHub 側の確認

ローカルの履歴だけでなく、以下も確認対象です。ネットワークアクセスが可能なら
確認し、不能なら「未確認」として利用者に確認を促してください。

- Issues、Pull Request の本文とコメント
- GitHub Actions の実行ログ
- リリースアセット
- Wiki、Discussions

### 検出された場合の対応

**検出しても、勝手に履歴を書き換えないでください。**

履歴の書き換え（`git filter-repo` 等）と force push は破壊的な操作であり、
公開済みリポジトリの clone を壊します。実施の可否は利用者が判断します。

以下を行ってください。

1. 検出内容を分類して報告する（コミットハッシュ、ファイル、件数、種別）
2. **秘密値（トークン等）が含まれていた場合、その旨を最優先で報告する**
   （履歴の書き換えより、当該トークンの失効が先です）
3. 対処方針の選択肢と、それぞれの影響を整理して提示する
4. 作業を止めず、Step 1 以降を継続する

### 検出されなかった場合

1. 走査範囲と方法を記録する
2. **再発防止の仕組みを追加する**
   - `.gitignore` の実効性を検証するテストケース
   - コミット前に実データの混入を検出する仕組み（pre-commit フック、または CI）
   - 走査スクリプトを CI に組み込む

## Step 1 — CI の整備

### 対象

GitHub Actions で以下を実行します。

| 検査 | 対象 OS |
|---|---|
| `ruff check` / `ruff format --check` | Linux |
| `mypy` | Linux |
| モデル不要テスト（`pytest -m "not requires_model"`） | Linux / Windows |
| `uv lock --check` | Linux |
| PowerShell スクリプトの構文検証 | Windows |
| **PowerShell スクリプトの BOM 検証** | Linux |
| 実データ混入の走査（Step 0 のスクリプト） | Linux |

### BOM 検証を必ず入れること

Phase 3d で、`setup.ps1` と `run.ps1` に UTF-8 BOM がないため、
Windows PowerShell 5.1 から実行すると構文エラーで即死する不具合が見つかりました。

**過去の Parser API による静的構文検証は、これを検出できませんでした。**
Parser API はファイルを直接読み込むため、`powershell.exe` 起動時の
エンコーディング解決とは経路が異なるためです。

したがって以下の両方を実施してください。

1. **BOM の有無をファイルバイト列で直接検証する**（Linux でも実行可能）
2. **Windows PowerShell 5.1 から実際に起動して、構文エラーにならないことを確認する**
   （`-List` など、副作用のないパラメータを使うこと）

対象は追跡対象のすべての `.ps1` ファイルです。

### 制約の明記

**CI で守れる範囲は限定的です。**

- ネイティブビルド（Vulkan SDK、OpenVINO）は CI で実行しない
- 実モデルを使うテストは CI で実行しない
- GPU を使うテストは CI で実行しない

**実質的な品質保証は受入試験ハーネスが担う**という位置づけを、
`要件定義.md` と `tools/acceptance/README.md` に明記してください。

### Linux での動作確認

`要件定義.md` は Linux を副対象としていますが、実際の動作確認は
ほとんど行われていません。CI の Linux ジョブが通ることで、
最低限のインポートとテストの実行は保証されます。

CI で判明した Linux 固有の問題は修正してください。
ただし、GPU やネイティブビルドに関わるものは対象外とし、記録にとどめます。

## Step 2 — ベンチマーク素材の是正

### 背景

Phase 3d の R-7 で、**構成の優劣が音声長で逆転する**ことが判明しました。

| 素材 | Vulkan | ovvk |
|---|---:|---:|
| 180秒 fixture | 15.4秒 | 19.6秒 |
| 24分46秒 実音声 | 110.7秒 | **65.1秒** |

180秒からの単純外挿では Vulkan 約127秒・ovvk 約162秒のはずが、
実測は ovvk が 65秒でした。OpenVINO エンコーダの初期化コストが
長い音声で償却されるためと推測されています。

**utteran の主用途は30分〜3時間の会議録音です。**
180秒の素材で測った結果は、本番の性能を代表していません。
現在の `benchmark` の既定素材が短いままだと、利用者が誤った判断をします。

### 実施内容

1. **`benchmark` の既定素材の長さを見直す**
   - 主用途を代表する長さにする
   - ただし測定時間が長くなりすぎないよう、現実的な妥協点を決める
   - 判断と根拠を記録する
2. **複数の長さで測定できるようにする**
   - 短い素材と長い素材で順位が変わりうることを、機能として扱う
   - 複数長での測定を1コマンドで実行できると望ましい
3. **短い素材で測定した場合、結果に警告を含める**
   - 「この長さの結果は長時間音声を代表しない可能性がある」旨
   - 具体的に、Phase 3d で逆転が観測された事実を根拠として示す
4. `--apply` で構成を書き込む際、**どの長さで測定した結果かを記録する**
5. README の記載を更新する
   - 長さによって最適構成が変わること
   - 主用途に近い長さで測ることを推奨

### auto 選択の改善（任意）

Phase 3d で、auto が `vulkan` 優先を維持した理由として
「`_choose_variant` はネイティブビルドの有無しか見ず、モデル別の IR 生成状態を
判定しないため、既定を ovvk にすると IR 未生成環境で初期化失敗を誘発しうる」
と記録されています。

**IR の生成状態を判定できるようにすれば、この制約は解消します。**
実装が過大にならない範囲で対応できるなら実施してください。
過大と判断した場合、Phase 4b 以降の候補として記録し、実施しないこと。

対応する場合でも、**auto の既定順序を変更するかは別途判断**してください。
長時間音声で ovvk が有利という観測は1点測定であり、
順序を変えるには追加の実測が必要です。

## Step 3 — 公開体裁の整備

リポジトリは公開済みですが、外部の利用者を迎える体裁が整っていません。

### 必須

1. **README の構成見直し**
   - 冒頭で「何ができるツールか」が3行以内で分かること
   - 現在の README は詳細だが長い。導入部と詳細を分離し、
     詳細は `docs/` へ移すことを検討する
   - **英語版（`README.en.md`）の作成を検討する**
     GitHub 公開である以上、英語話者が最初に見る可能性がある。
     全訳が過大なら、概要・対応環境・インストールのみの短縮版でよい
2. **`LICENSE` と `THIRD_PARTY_NOTICES.md` の最終確認**
   - 現在の依存とモデルがすべて記載されているか
   - Phase 3 で追加されたもの（whisper.cpp、ggml モデル、Silero VAD、
     OpenVINO、Vulkan 関連）が漏れていないか
   - **モデルのライセンスと利用条件への同意が必要な旨が明記されているか**
3. **バージョニングとリリース手順**
   - セマンティックバージョニングの方針を決める
   - 現在は未リリース状態。最初のリリースをどう定義するか
   - `変更履歴.md` の「未リリース」節をリリース版へ整理する手順
4. **`.gitignore` の再検証**
   - Step 0 の走査結果を踏まえ、漏れがないか確認する
   - 特に `input/`、`output/`、`.venvs/`、モデル、ジョブ、ログ

### 任意（判断して実施の可否を決める）

- `CONTRIBUTING.md`
- Issue / Pull Request テンプレート
- `SECURITY.md`（トークンの扱いに関する注意を含む）
- GitHub のリポジトリ説明、トピック、README のバッジ

過剰に整備する必要はありません。**実施しなかったものは理由を記録**してください。

## 実装上の注意

### 機密データ

- **検出した個人情報・秘密値そのものを、報告書、AISTATE、
  コミットメッセージ、走査結果ファイルに書かないこと**
- 位置（コミット、ファイル、行数）と件数、種別のみを記録する
- 走査結果ファイル自体も、`output/` など git 追跡外に置くこと
- `.env` を読み取らない

### 破壊的操作の禁止

- 履歴の書き換え、force push、ブランチの削除を行わない
- `git push` を実行しない（利用者が判断します）
- 既存の venv、モデル、ジョブを削除しない

### コミット

- ブランチ `chore/phase4a-public-readiness`
- Step 単位でコミットする
- `git push` は実行しない

---

## 禁止事項

- ワーキングツリーだけを走査して「問題なし」と結論すること
- 検出した個人情報や秘密値を、そのまま記録すること
- 履歴の書き換えを利用者の判断なしに実施すること
- BOM 検証を静的構文検証だけで済ませること
- 短い素材の測定結果を、長時間音声の性能として提示すること
- 動作確認していない CI 設定を「完了」と報告すること
- `要件定義.md` を更新せずに仕様を変えること

---

## 不明点があった場合

1. `要件定義.md` と `AISTATE.md` の記録を優先する
2. 判断できない場合、安全側（何もしない側）に倒し、判断と理由を記録する
3. 破壊的操作に関わる判断は、必ず利用者へ委ねる
4. 設計の変更を伴う判断は、実装前に `要件定義.md` へ反映する
