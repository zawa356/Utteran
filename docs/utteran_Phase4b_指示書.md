## 背景

`要件定義.md` 13 章は、長時間音声で pyannote のメモリ消費が問題になると想定し、
「分割処理＋全体クラスタリング」を Phase 4 の課題としていました。

Phase 3d の R-5 で、実測データが得られています。

| 構成 | 25分 | 50分 | 100分 |
|---|---:|---:|---:|
| pyannote / XPU | 5.407 GB | 5.584 GB | 6.097 GB |
| pyannote / CPU | 2.753 GB | 2.907 GB | — |
| Vulkan ASR | 1.470 GB | 1.738 GB | 2.277 GB |

**重要な性質**: 音声長を 4 倍にしてもメモリは 13% しか増えていません。
線形回帰すると以下の形になります。

```
推定ピーク = 基礎量 + 係数 × 音声長
```

| 構成 | 基礎量 | 係数 |
|---|---:|---:|
| pyannote / XPU | 約 5.3 GB | 約 0.008 GB/分 |
| pyannote / CPU | 約 2.6 GB | 約 0.006 GB/分 |
| pyannote / CUDA | 1点のみ（2時間19分で 7.31 GiB） |

**基礎量が支配的で、係数は極めて小さい。**

これは設計に直結します。**分割で減らせるのは係数側だけで、基礎量は減りません。**
基礎量が既に予算を超える環境では、分割しても救えません。
その場合は CPU への退避か、より軽い構成の提案が正しい対処です。

したがって、分割の発動条件は「予算を超えそうか」ではなく
**「分割すれば収まるか」**でなければなりません。

### 実際に危険な環境

GTX 1070 Ti（VRAM 8 GiB）では、2時間19分の処理で **7.31 GiB** を使っていました。
**上限の 91%** です。他のアプリが VRAM を使っていれば OOM です。
8 GB の dGPU、16 GB RAM のノート PC などは危険域にあります。

## Step 0 — pyannote 4.x のパイプライン分解可否

### 調査内容

分割処理の実装には、以下が必要です。

1. 音声をチャンクに分けて segmentation と話者埋め込みの抽出を行う
2. **全チャンクの埋め込みを保持する**
3. **クラスタリングを全体で 1 回だけ実行する**

3 が満たされないと、チャンクごとに話者 ID が振り直され、
`SPEAKER_00` が別人を指します。

pyannote 4.x（community-1 パイプライン）で、以下が可能かを調査してください。

- segmentation の結果を中間データとして取り出せるか
- 話者埋め込みを中間データとして取り出せるか
- クラスタリングだけを、外部から与えた埋め込みに対して実行できるか
- exclusive diarization は、クラスタリング後に再構成できるか
  （utteran はこれを話者割当に使っているため、失われると精度が落ちます）
- チャンク境界をまたぐ発話の扱い

**実際にコードを読み、可能なら小さな音声で試して確認してください。**
ドキュメントの記述だけで判断しないこと。

### 判定と報告

以下のいずれかに分類し、**根拠とともに報告してください。**

| 分岐 | 条件 |
|---|---|
| **A** | 公開 API または安定した内部構造で分解できる |
| **B** | 分解できない、または内部実装への強い依存が必要で脆い |

**分岐 A と明確に判断できる場合のみ、Step 3 へ進んでください。**

**分岐 B、または判断が微妙な場合は、Step 3 を実施せず、
Step 1・Step 2・Step 4 の該当部分まで完了させて報告してください。**
利用者が実装方針を判断します。

分岐 B の場合、以下も併せて報告してください。

- 自前で segmentation → embedding → clustering を組む場合の実装量の見積もり
- その実装が pyannote のバージョン更新で壊れるリスク
- 分割なしで救える範囲（Step 2 の退避だけでどこまで対応できるか）

## Step 1 — メモリ予算とピーク推定

**この Step は分岐に依存しません。必ず実施してください。**

### 1-A. メモリ予算の算出

**dGPU と iGPU では、メモリの意味がまったく違います。**
種別ごとに算出方法を分けてください。

| 種別 | 予算の算出 | 安全率の考え方 |
|---|---|---|
| 専用 VRAM（CUDA） | 空き VRAM を取得 | 他プロセスの占有は取得値に反映済み。安全率は小さめ |
| 共有メモリ（XPU / iGPU） | GPU が報告する上限と、システム RAM の空きの**小さいほう** | OS・他アプリと常時競合するため安全率は大きめ |
| システム RAM（CPU） | 空きメモリ | 中間 |

- 安全率は設定で変更可能にする
- 取得できない環境（API 非対応など）では「不明」として扱い、
  推定による判定を行わず、警告のみとする
- **「不明」を「十分ある」と解釈しないこと**

### 1-B. ピーク推定

上記の線形式を実装します。

- 係数は `(バックエンド, デバイス種別)` ごとに持つ
- **同梱の既定値は R-5 の実測から導出し、測定条件をコード内コメントと
  要件定義に明記する**（単一環境・3点の測定であることを含めて）
- ASR と話者分離を別々に推定する（ステージごとにピークが立つため）
- 推定は「この環境では外れうる」前提で扱う

### 1-C. キャリブレーション

推定式は環境依存です。**実測で補正する仕組みを持たせてください。**

- 各実行の実測ピークを記録する
  記録項目: バックエンド、デバイス種別、音声長、ピーク、日時
- 保存先は `platformdirs` 配下。ジョブディレクトリではない
  （プロファイルをまたいで蓄積するため）
- データ点が少ないうちは同梱の既定値、蓄積したら実測を優先する
  切り替えの基準（何点以上で実測優先か）を決め、根拠を記録する
- 外れ値の扱いを決める（他プロセスの影響で異常値が入りうる）
- 利用者が確認・リセットできるコマンドを用意する

```
utteran memory show      推定式と蓄積データの状況
utteran memory reset     蓄積データの削除
```

**測定した音声の内容に関する情報を保存しないこと。**
音声長のみを記録し、ファイル名やパスは記録しないでください。

ピーク測定は、Phase 3d の受入試験ハーネスが実装している
プロセスツリーの working set 集計を再利用してください。

## Step 2 — 事前警告と自動退避

**この Step も分岐に依存しません。**

### 2-A. 判定と動作

処理開始前に推定と予算を比較し、3 段階で扱います。

| 判定 | 条件 | 動作 |
|---|---|---|
| 安全 | 推定 < 予算 | そのまま実行 |
| 危険 | 推定 ≈ 予算、または超過するが基礎量は収まる | 警告。`auto` なら退避を検討 |
| 不可 | **基礎量が予算を超える** | 実行前にエラー。対処案を提示 |

**「不可」の判定が重要です。**基礎量が入らない環境では、分割しても救えません。
この場合、以下の対処案を提示してください。

- より軽いデバイスへの切り替え（XPU → CPU はメモリ効率が良い）
- 話者分離を省略する（`--no-diarization`）
- 音声を短く区切って個別に処理する

### 2-B. 退避の方針

Phase 1 以来の方針を維持します。

- **`auto` のときのみ退避する**
- 明示的にデバイスを指定された場合は退避せず、警告のうえ実行するか、
  「不可」判定ならエラーとする
- 退避先の優先順位を決める（XPU → CPU、CUDA → CPU）
- 退避したことと理由を表示・記録する（ジョブログと `merged.json`）

### 2-C. OOM の捕捉

**推定は必ず外れます。保険として実行時の OOM 捕捉を実装してください。**

- OOM を捕捉し、`auto` の場合は退避して再試行する
- 再試行は 1 回まで
- 明示指定時は退避せず、理解可能なエラーとする
- 中間結果（音声抽出、ASR）が保持され、再開可能であることを確認する
- 共有メモリ環境では、GPU の OOM ではなくシステム RAM の枯渇として
  現れる可能性がある。両方を扱えるようにすること

### 2-D. 設定

```toml
[diarization]
memory_guard = "auto"      # auto | warn | off
memory_safety_margin = 0.0 # 0.0 なら種別ごとの既定値を使う
```

- `warn` は警告のみで退避しない
- `off` は判定自体を行わない
- **`off` を既定にしないこと**

### 2-E. デバッグ用の予算上書き

**本機（68 GB RAM）では、自然な条件で危険判定が発生しません。**
検証のため、予算の上限を強制的に小さく設定できる手段を用意してください。

- 環境変数または隠しオプションで構いません
- 利用者向けの機能として文書化する必要はありません
- **Step 4 の検証で必須になります**

## Step 3 — 分割処理（分岐 A の場合のみ）

### 設計要件

1. **全チャンクの話者埋め込みを保持し、クラスタリングを全体で 1 回だけ実行する**
   これを満たさない実装は受け入れられません
2. チャンクには重なり（オーバーラップ）を持たせ、境界の発話が失われないようにする
   - 重なり区間で重複する結果の統合方法を決める
   - チャンク長と重なり長は設定可能にする
3. `--num-speakers` / `--min-speakers` / `--max-speakers` は
   **全体に対する制約**として扱う（チャンクごとではない）
4. exclusive diarization を、分割なしと同等に再構成する
   できない場合、話者割当の精度への影響を実測し、記録する
5. 進捗をチャンク単位で通知し、キャンセルに応答する
6. **同一入力・同一設定で同一結果になること**（決定性）

### 発動条件

- Step 2 の判定が「危険」で、**分割すれば収まると推定される**場合に発動する
- 設定で強制的に有効・無効にできるようにする
- 発動したことと理由を表示・記録する

### 中間結果

- チャンク単位の結果を保存し、レジュームに対応する
  （長時間処理の途中で中断した場合に、最初からやり直さないため）
- `schema_version` を持たせる
- ジョブディレクトリの構造変更は、既存ジョブを壊さない形にする

## Step 4 — 検証

**この Step は長時間の計測を含みます。端末を空ける必要があります。**

### 4-A. 推定精度の検証

Phase 3d で生成した連結音声（25 / 50 / 100 分）を使用します。

1. 各長さで実測ピークを測定し、推定値と比較する
2. 推定の誤差を記録する
3. キャリブレーションが蓄積により改善することを確認する

### 4-B. 判定と退避の検証

**Step 2-E のデバッグ手段で予算を絞り、各判定を人工的に発生させます。**

| 検証 | 方法 |
|---|---|
| 安全判定 | 通常実行 |
| 危険判定・退避 | 予算を推定ピーク付近に設定し、`auto` で実行 |
| 危険判定・警告のみ | 同上、明示デバイス指定で実行 |
| 不可判定 | 予算を基礎量未満に設定 |
| OOM 捕捉 | 予算判定を `off` にし、実際に OOM を発生させる |

- 退避後に処理が完走すること
- 中間結果が保持され、再開可能であること
- エラーメッセージが理解可能であること

### 4-C. 分割処理の検証（分岐 A の場合）

1. **分割あり／なしで結果を比較する**（分割なしを基準とする）

| 指標 | 期待 |
|---|---|
| 話者数 | 完全一致 |
| 話者区間の数 | 近い（差を記録） |
| 各区間の境界時刻 | 差を記録し、許容範囲を判断 |
| 話者ごとの発話時間分布 | 近い |
| `UNKNOWN` の割合 | 悪化しない |

2. **チャンク境界付近の話者 ID が一貫していることを確認する**
   （最終クラスタリングが正しく機能している証拠）
3. 同一条件 2 回実行で結果が一致すること
4. 25 / 50 / 100 分での処理時間とメモリを測定し、分割なしと比較する
5. チャンク長と重なり長を変えた場合の影響を測定する
6. 中断・再開が機能すること

### 4-D. 回帰確認

- 既存の CPU / XPU 経路が従来どおり動作すること
- 受入試験ハーネスが引き続き合格すること
- faster-whisper 経路が変わっていないこと

## 実装上の注意

### 機密データ

- 実データの文字起こし内容を記録しない
- キャリブレーションデータに音声のパスやファイル名を保存しない
- `.env` を読み取らない

### 破壊的変更への配慮

- 既存の CPU / CUDA / XPU 経路の挙動を、判定が「安全」の場合は変えない
- 既存のジョブ、モデル、設定を無効化しない
- ジョブディレクトリの構造変更は、既存ジョブを読めなくしないこと

### コミット

- ブランチ `feature/phase4b-memory-management`
- Step 単位でコミットする
- 調査結果と測定結果は独立したコミットとする
- `git push` は実行しない
- 実データをコミットしない

## 禁止事項

- Step 0 の調査を省略して分割処理を実装すること
- 分岐 B または判断が微妙な状態で、Step 3 を独断で進めること
- チャンクごとにクラスタリングを行う実装（話者 ID が不整合になる）
- メモリ取得不能を「十分ある」と解釈すること
- `memory_guard` の既定を `off` にすること
- 明示指定されたデバイスで退避すること
- 人工的な検証を行わず「動作する」と報告すること
- `要件定義.md` を更新せずに仕様を変えること

2. 判断できない場合、安全側に倒し、判断と理由を記録する
3. **分割処理の実装方針に迷った場合は、実装せず報告する**
4. 設計の変更を伴う判断は、実装前に `要件定義.md` へ反映する
