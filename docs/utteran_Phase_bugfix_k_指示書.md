## 症状

0.1.26 のインストーラー版 GUI で、faster-whisper による文字起こしが失敗します。

```
job_resolved: 7be37b2d3fc10277
文字起こしを開始します
faster-whisper の推論に失敗しました。入力音声、モデル、実行デバイスを確認してください。
ERROR: ステージ失敗: asr: faster-whisper の推論に失敗しました。...
ERROR: stage_error
```

**発生した機体は未特定です。Step 0 で確認してください。**

---

## 調査済みの事実（再調査は不要）

### 1. 失敗しているのは `transcribe()` の内部

出力の順序が根拠です。

| 出力 | 対応箇所 |
|---|---|
| `文字起こしを開始します` | `faster_whisper.py:162` の `ProgressEvent` |
| 推論に失敗しました | `_raise_inference_error` による例外 |

`faster_whisper.py:162` は `load()` の**完了後**に実行されます。
また `load()` の失敗は `_raise_load_error` が扱い、
**「faster-whisper モデルを初期化できません」という別のメッセージ**になります。

**したがって以下は原因から除外されます。**

- モデルが未取得・破損している
- デバイスを初期化できない
- faster-whisper が導入されていない

### 2. 原因が特定できないのは、コードが例外を捨てているため

`src/utteran/asr/faster_whisper.py` の末尾です。

```python
def _raise_inference_error(error: Exception) -> None:
    detail = str(error).casefold()
    if "out of memory" in detail or "cuda_error_out_of_memory" in detail:
        raise VramExhaustedError(...) from None
    raise BackendUnavailableError(
        "faster-whisper の推論に失敗しました。入力音声、モデル、実行デバイスを確認してください。"
    ) from None
```

**VRAM 不足以外のすべての例外が、この1文に潰されます。**

- `from None` で例外連鎖が切られる
- **元の例外はログにも記録されない**
- したがって**根本原因は復元できない**

`_raise_load_error`（同ファイル 244行目）も同じ構造です。

### 3. `--verbose` では原因が出ない

`BackendUnavailableError` は `DependencyError` を経て `UtteranError` を継承します。

`cli.py` の受け口では、

- `except UtteranError` → **例外を記録せずに終了**（796行目付近）
- `except Exception` → `verbose` 時のみ `logging.exception`（804行目付近）

**`UtteranError` は前者に入るため、`--verbose` を付けても原因は出ません。**

### 4. 検証して**否定された**仮説

`uv.lock` では依存が次の版になっています。

| パッケージ | 版 | 公開日 |
|---|---|---|
| faster-whisper | 1.2.1 | 2025-10-31 |
| **av（PyAV）** | **18.0.0** | **2026-07-02** |
| ctranslate2 | 4.8.1 | — |
| onnxruntime | 1.28.0 | — |

faster-whisper 側の制約が `av>=11` で上限なしのため、
**8か月新しい PyAV がメジャー3つ分ぶん先行して入っています。**

音声デコードの API 破壊を疑いましたが、**実際に試したところ正常に動作しました。**

```
faster_whisper.audio.decode_audio() → DECODE OK (32000,) float32
```

**PyAV は原因ではありません。この線を再調査しないでください。**

ただし、**上限なしの制約で新しいメジャー版が入る構造そのものは記録対象**です（Step 5）。

### 5. 未検証の有力候補

**Silero VAD（onnxruntime 経由）です。**

- `vad_filter` は既定で `true`（`config.py:48`、`types.py:147`）
- faster-whisper 1.2.1 は `assets/silero_vad_v6.onnx` を onnxruntime でロードする
- **この処理は `transcribe()` の内部で走る**ため、失敗箇所と一致する

**仮説です。Step 2 で確認してください。**

## Step 1 — 診断能力の回復（本作業の中核）

**根本原因の修正より先に、これを行ってください。**

原因が見えない状態で修正に進むのは、
**「推測での修正を禁止し、原因の特定を必須にする」という運用ルールに反します。**

### 求める挙動

**例外を捨てないでください。**

| 出力先 | 内容 |
|---|---|
| 利用者向けメッセージ | **簡潔さを保つ。**現在の文面に、原因の要約とログの場所を加える |
| ログ | **完全なトレースバック**（例外の型、メッセージ、発生箇所） |
| `--verbose` | 画面にも詳細を出す |

### 中間の設計にすること（重要）

このプロジェクトは**「片方の極から反対の極へ振れる」**という失敗を繰り返しています。

- **生のトレースバックを利用者の画面へそのまま出さないこと**
- **同時に、原因を完全に隠す現状も維持しないこと**

**利用者が報告できる情報**（例外の型と要約、ログの場所）**が画面に出ること**が条件です。

### 実装上の要求

- `_raise_inference_error` と `_raise_load_error` の**両方**を直す
- 元の例外を、**`structured_event` またはロガー経由で記録する**
- 例外連鎖を残す（`from None` をやめ、`from error` にするかを検討する）
  **ただし利用者の画面に長大な連鎖を出さないこと**
- **`UtteranError` 系でも原因がログに残る**ようにする
  （`cli.py` の受け口を直すか、送出側で記録するかは判断に任せる）

### 機密への配慮（必須）

**例外テキストに、利用者の環境の情報が含まれ得ます。**

- `logging.py` の `RedactingFormatter` は、**フォーマット時に例外テキストもマスクします**
  （`mask_secrets(super().format(record))`）
- **ただしマスクされるのはトークン形状と登録済みの秘密のみです。**
  ファイルパスや `input/` 由来の名前はマスクされません

**確認すること**

- 記録経路が `RedactingFormatter` を通ることを**実際に検証する**
- **文字起こしの本文、固有名詞、話者名が記録されないこと**
- パスを記録する場合、`input/` 配下の**元ファイル名が含まれないこと**
  （ジョブの WAV は `<jobs>/<job_id>/audio.wav` で元名を含まないはずだが、確認すること）

**判断に迷う場合、記録しない側に倒してください。**

## Step 2 — 実機での再現と根本原因の特定

**Step 1 を適用した版で再現させ、本来の例外を取得してください。**

### 切り分けの手順

原因の候補ごとに、独立して確認できます。

**1. Silero VAD / onnxruntime の単体ロード**

```python
import faster_whisper, onnxruntime
from pathlib import Path
asset = Path(faster_whisper.__file__).parent / "assets" / "silero_vad_v6.onnx"
onnxruntime.InferenceSession(str(asset), providers=["CPUExecutionProvider"])
```

**2. VAD を無効にした推論**

`vad_filter=False` で `transcribe()` が通るかを確認します。
**通るなら原因は VAD 側で確定します。**

**3. 音声デコードの単体確認**

`faster_whisper.audio.decode_audio()` をジョブの `audio.wav` に対して実行します。

**4. 各パッケージの実際の版数**

`faster_whisper` / `ctranslate2` / `av` / `onnxruntime` / `numpy`。
**`uv.lock` の版と実環境の版が一致するかを確認してください。**

### 補足 — 握りつぶしを一時的に外す手法

Step 1 の実装前に原因を見たい場合、
**`_raise_inference_error` を差し替えて元の例外を再送出する**方法が使えます。

```python
from utteran.asr import faster_whisper as m
m._raise_inference_error = lambda error: (_ for _ in ()).throw(error)
```

**これは調査用の手段です。この差し替えをリポジトリへ残さないでください。**

### 判定

結果を以下に分類し、**根拠とともに `AISTATE.md` へ記録**してください。

| 判定 | 条件 | Step 3 の扱い |
|---|---|---|
| **A** | 再現し、**utteran 側の不具合**だった | 修正する |
| **B** | 再現し、**依存または環境側の問題**だった（onnxruntime、SAC、ドライバ等） | **回避策と案内を実装する** |
| **C** | **開発機で再現しない** | **Step 1 の成果のみを出荷し、利用者に実機で再取得させる** |

**判定 C は失敗ではありません。**

発生機が開発機と異なる可能性があります。
**Step 1 によって、利用者が原因を報告できる状態になること自体が成果です。**

**`faster_whisper.py` だけを直して終わらせないでください。**

`src/` 配下に `from None` が **73箇所**あります。
**すべてが問題ではありません**（CLI の終了処理など、妥当なものが多数含まれます）。

### 点検する範囲

**バックエンドの読み込み・推論経路に限定してください。**

- 捨てている → **記録するよう直す**

## Step 5 — 依存の版ずれの記録（記録のみ・実装しない）

**今回の原因ではありませんでしたが、構造的な問題として記録してください。**

> faster-whisper 1.2.1（2025-10-31）に対し、その依存である av（PyAV）が
> 18.0.0（2026-07-02）で解決されている。faster-whisper 側の制約が
> `av>=11` で上限がないため、**8か月新しいメジャー3つ分先の版**が入る。
>
> 今回は正常に動作することを実測で確認したが、
> **上流がテストしていない組み合わせが lock に入り得る構造**である。
>
> 同様の構造は ctranslate2、onnxruntime、tokenizers にも存在する。

**対処は本作業では行いません。**

`uv.lock` の更新方針（どの単位で依存を上げるか、上げた後に何を確認するか）を
**別途検討する課題として、B グループへ追加**してください。
番号は空いているものを使い、その旨を記録すること。
