# utteran — Phase 1 実装指示

## あなたへの依頼

`utteran` という、音声・動画から話者を区別した文字起こしを生成する Python 製 CLI ツールを
新規開発します。あなたには Phase 1（骨格と最小動作）の実装をお願いします。

添付の `utteran_設計書.md` が仕様の唯一の情報源です。**着手前に必ず全体を読んでください。**
設計書に書かれていない判断が必要になった場合は、勝手に決めずに質問するか、
やむを得ず決めた場合はその判断と理由を `AISTATE.md` に記録してください。

---

## 最初にやること（順守）

1. `utteran_設計書.md` を読む。
2. リポジトリ直下に以下の4文書を作成する。**これはコードより先に行う。**
   - `README.md`
   - `変更履歴.md`
   - `要件定義.md`（設計書の内容をそのまま配置）
   - `AISTATE.md`
3. 実装計画を `AISTATE.md` に記述し、着手する。

## Phase 1 の実装範囲

### 含むもの

- プロジェクト構成一式（`pyproject.toml`、uv 前提、src レイアウト）
- `config.py`: pydantic-settings による設定。設定の優先順位を設計書どおりに実装
- `types.py`: 共通データモデル
- `errors.py`: 例外定義
- `logging.py`: ログ設定。トークンのマスク処理を含む
- `audio.py`: ffmpeg による音声抽出・正規化（16kHz / mono / PCM 16bit）
  - ffmpeg の探索ロジックを含む
- `asr/base.py` + `asr/faster_whisper.py`: faster-whisper バックエンド（CPU / CUDA）
- `diarization/base.py` + `diarization/pyannote.py`: pyannote.audio 4.x バックエンド
- `align.py`: 突き合わせ・話者割当（設計書 7 章のアルゴリズムを実装）
- `exporters/`: SRT, VTT, JSON, TXT, Markdown
- `pipeline.py`: 単一ファイルの一気通貫処理
- `cli.py`: `transcribe` サブコマンドのみ
- テスト一式

### 含まないもの（Phase 2 以降）

- ジョブ管理・レジューム（`jobs.py`）
- フォルダ一括・キュー処理
- モデル管理コマンド、`setup.ps1`
- `devices` コマンド、デバイス自動判定の詳細実装
- OpenVINO / sherpa-onnx バックエンド
- 長時間音声の分割処理

ただし**Phase 2 以降で追加する箇所には、拡張ポイントを用意しておいてください**。
特に以下は Phase 1 の時点で守ること。

- バックエンドは抽象基底クラス経由でのみ呼び出す。`pipeline.py` から
  faster-whisper や pyannote を直接 import しない。
- 進捗コールバックとキャンセルトークンのインターフェースを最初から通す。
  Phase 1 では実際に使われなくてもよいが、シグネチャは定義しておく。
- 中間結果を JSON にシリアライズできる形にしておく（Phase 2 のレジューム用）。

## 完了条件

以下がすべて満たされた状態を Phase 1 完了とします。

- [ ] `uv sync` で開発環境が構築できる
- [ ] `utteran transcribe <音声ファイル>` が動作し、話者付きの文字起こしが出力される
- [ ] mp4 などの動画ファイルを入力にできる
- [ ] SRT / VTT / JSON / TXT / MD の5形式が出力できる

- [ ] `--no-diarization` で話者分離を省略できる

      （スタックトレースをそのまま出さない）

- [ ] ログにトークンが出力されない
- [ ] `ruff check` と `mypy` がエラーなく通る
- [ ] モデル不要のテストが `pytest -m "not requires_model"` で通る
- [ ] 4文書が作成され、実装内容と一致している

## ドキュメント運用の義務

**これは任意ではなく、実装と同格の必須作業です。**

以下の4文書を常に最新に保ってください。コードを変更したのにドキュメントを更新していない
状態で「完了しました」と報告することを禁止します。

### `README.md`

- プロジェクトの概要と目的
- 対応環境（OS、Python バージョン、ハードウェア）
- インストール手順（uv、extras の使い分け）
- Hugging Face トークンの取得手順とモデル利用条件への同意手順
- ffmpeg の準備方法
- 基本的な使い方（コマンド例つき）
- 対応する入力形式・出力形式
- ライセンス（MIT）と、依存モデルのライセンスに関する注意

**更新タイミング**: CLI、インストール手順、対応機能に変更があるたび。

### `変更履歴.md`

Keep a Changelog 形式に準拠。日本語で記述。

```markdown
# 変更履歴

## [未リリース]

### 追加
- ...

### 変更
- ...

### 修正
- ...

### 削除
- ...
```

**更新タイミング**: すべての作業単位で。「実装した内容を後でまとめて書く」ことを禁止します。

### `要件定義.md`

設計書の内容をそのまま配置し、以降の仕様変更を反映していく。
実装の都合で仕様を変えた場合、コードだけ変えて本書を放置してはならない。
本書と実装が食い違っている状態を作らないこと。

**更新タイミング**: 仕様に変更があるたび。

### `AISTATE.md`

AI 作業者がセッションをまたいで作業するための状態記録。
**新しいセッションを開始した AI が、これを読むだけで作業を再開できる状態を維持すること。**

含めるべき内容:

- 現在のフェーズと進捗状況
- 直近の作業内容とその結果
- 未解決の課題、判断を保留している事項
- 設計上の判断とその理由（なぜその選択をしたか）
- 次に着手すべきこと
- 既知の落とし穴、ハマった箇所とその回避方法
- 動作確認に使った環境や手順

人間向けの体裁は不要です。箇条書き、断片的なメモ、構造化データ、何でも構いません。
読み手が AI であることを前提に、情報の密度を優先してください。
逆に、冗長な前置きや挨拶文のような無駄な記述は入れないでください。

**更新タイミング**: すべての作業単位の終わり。特にセッションを終える前には必ず更新すること。

## 作業の進め方

1. まず4文書を作成し、実装計画を `AISTATE.md` に記述する
2. プロジェクト構成と `pyproject.toml` を作る
3. `types.py` / `errors.py` / `config.py` / `logging.py` の基盤を作る
4. `audio.py`（ffmpeg）を作り、動作確認する
5. ASR バックエンドを作り、単体で動作確認する
6. 話者分離バックエンドを作り、単体で動作確認する
7. `align.py` を作り、テストを書く（ここは実モデル不要でテストできる）
8. exporters を作り、テストを書く
9. `pipeline.py` と `cli.py` で結合する
10. 全体の動作確認
11. 4文書を最終更新する

各ステップの区切りで `変更履歴.md` と `AISTATE.md` を更新してください。

## 実装上の注意

### 型と品質

- すべての関数に型ヒントを付ける
- `pathlib.Path` を使う。文字列でパスを組み立てない
- `subprocess` はリスト形式で呼ぶ。`shell=True` を使わない
- Windows / Linux の差異は標準ライブラリで吸収する

### エラー処理

想定される失敗には専用の例外型を定義し、ユーザーが次に何をすべきか分かる
メッセージを出してください。以下は必ず個別に扱うこと。

- Hugging Face トークンが未設定
- Hugging Face のモデル利用条件に未同意
- ffmpeg が見つからない
- モデルが未取得
- VRAM 不足
- 対応外の入力形式、デコード失敗

### セキュリティ

- トークンを `config.toml` に書かせない。書かれていても読まず、警告を出す
- ログ、例外メッセージ、スタックトレースにトークンが混入しないようにする
- `.env` を `.gitignore` に含める。`.env.example` は追跡対象にする

### テスト

- `align.py` の突き合わせロジックは、実モデルなしでテストできる。
  境界ケース（話者の重なり、極短セグメント、未割当）を重点的にテストすること
- exporters もモデル不要でテストできる。タイムスタンプの書式を重点的に
- モデルを必要とするテストは `@pytest.mark.requires_model` を付けて分離する

## 禁止事項

- 設計書に反する実装を、断りなく行うこと
- ドキュメントを更新しないまま完了報告をすること
- バックエンド固有の型（faster-whisper や pyannote の戻り値オブジェクト）を
  `pipeline.py` や `exporters/` に漏らすこと
- 動作確認していないコードを「完成した」と報告すること
- 使われていないコードや、将来使うかもしれないという理由だけの抽象化を追加すること
  （拡張ポイントとして設計書に明記されているものは除く）
