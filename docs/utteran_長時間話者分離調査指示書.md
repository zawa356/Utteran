# utteran — 長時間音声における話者分離の破綻 調査・修正指示書

## あなたへの依頼

**長時間の会議音声で、話者分離の結果が異常に粗くなる問題**を調査し、
修正してください。

作業ブランチは `fix/long-audio-diarization` を新規作成して使用します。

---

## 報告された症状

約116分の日本語会議音声を処理した結果です。

| 項目 | 値 |
|---|---|
| 音声長 | 約116分 |
| **最終セグメント数** | **18** |
| SPEAKER_00 | 約95分 |
| SPEAKER_01 | 約21分 |
| UNKNOWN | ごくわずか |
| **最長の連続同一話者区間** | **約61分** |

**61分間、話者が一度も交代していないことになっています。**

しかし文字起こし本文には、その区間内に以下が含まれています。

- 「確かにね」
- 「まあそうですね」
- 「え？」
- 短い相槌
- 質問と回答と思われる会話

**明らかに複数話者が交代している内容です。**

---

## 参考: 短い音声では正常です

Phase 3 の受入試験（P10、結合検証）では、3分のクリップで以下でした。

| 構成 | 話者数 | セグメント | 平均ターン長 | UNKNOWN |
|---|---:|---:|---:|---:|
| faster-whisper + pyannote/CPU | 4 | 31 | 3.71秒 | 0% |
| whisper.cpp/ovvk + pyannote/CPU | 4 | 25 | 4.58秒 | 0% |

**3分で25〜31セグメント**です。単純に外挿すれば116分で約1000セグメント。
実際は18でした。

**短い音声では正常だったものが、長時間音声で破綻しています。**

---

## 受入試験の判定基準に穴があります

Phase 3 の受入試験は、以下を話者分離の合格基準としていました。

| 項目 | 基準 |
|---|---|
| 平均ターン長 | **0.5秒以上** |
| `UNKNOWN` の割合 | 20%未満 |
| 1話者の占有 | 99%未満 |

**今回の症状は、この基準をすべて通過します。**

- 平均ターン長: 約6.4分（長いほど良いとされる）
- UNKNOWN: ごくわずか
- 1話者の占有: 82%（99%未満）

**「細分化しすぎ」は検出できますが、「粗すぎる」は検出できません。**

**判定基準の見直しも本作業に含めてください。**

## Step 1 — どこで潰れているかの特定

**最終出力を見るだけでは、原因を切り分けられません。**

以下のどこで話者情報が失われたのかを特定してください。

```
音声
  ↓
[1] pyannote の生出力（diarization.json）
  ↓
[2] exclusive diarization の適用
  ↓
[3] align.py による単語への話者割当
  ↓
[4] セグメントの分割
  ↓
[5] 極短セグメントの吸収
  ↓
[6] 連続する同一話者の結合
  ↓
最終出力（18セグメント）
```

### 中間結果は既に保存されています

utteran はジョブディレクトリに中間結果を保存しています。

```
<job_dir>/<job_id>/
├── asr.json            単語レベルの ASR 結果
├── diarization.json    話者区間（通常 + exclusive）
├── merged.json         統合結果
```

**既存のジョブがあれば、そこから調査できます。**
無ければ再実行してください。

### 確認すべき項目

各段階で以下を数えてください。

| 段階 | 確認項目 |
|---|---|
| **[1] pyannote 生出力** | **話者交代の回数、話者数、最長連続区間、各話者の合計時間** |
| [2] exclusive 適用後 | 同上。通常版との差 |
| [3] 割当後 | 話者が変わった単語の数 |
| [4] 分割後 | セグメント数 |
| [5] 吸収後 | セグメント数、吸収された数 |
| [6] 結合後 | セグメント数、結合された数 |

**[1] が既に粗いなら pyannote 側の問題、
[1] が正常で [4]〜[6] で減るなら `align.py` の問題です。**

**この切り分けを最優先で行ってください。**

### 調査手段

段階ごとの統計を出す手段が無ければ、**作ってください。**

- 既存の中間 JSON から統計を算出するツール
- あるいは、Phase 5j のログ基盤に段階ごとの統計を記録する

**後者が望ましい**です。今後も同種の問題を検出できるようになります。

**文字起こしの本文を出力しないこと。**統計のみを扱ってください。

## Step 2 — 仮説の検証

Step 1 の結果に応じて、以下を検証してください。

### 仮説 A — pyannote が長時間音声でクラスタリングに失敗している

**該当する場合**: [1] の段階で既に話者交代が少ない

確認方法:

- **同じ音声の一部（10分程度）を切り出して処理し、比較する**
  短い区間で正常なら、長時間特有の問題です
- `num_speakers` / `min_speakers` / `max_speakers` の指定による差
- CPU 実行と XPU 実行の差
  （Phase 3c では3分で完全一致を確認済みですが、長時間では未確認）

**長時間音声で話者埋め込みのクラスタリングが破綻する**のは、
pyannote に限らず起こりうる現象です。

### 仮説 B — exclusive diarization が話者交代を潰している

**該当する場合**: 通常版と exclusive 版で [1] と [2] に大きな差がある

utteran は exclusive を優先して使用しています。
これは「その瞬間に最も文字起こしされやすい話者だけをアクティブにする」
機能ですが、**長時間では過剰に働く可能性があります。**

確認方法:

- 通常版の diarization で同じ処理を行い、結果を比較する
- どちらを使うべきか、実測で判断する

### 仮説 C — `align.py` の結合処理が過剰に効いている

**該当する場合**: [4] から [6] にかけてセグメントが大幅に減る

`align.py` には以下の処理があります。

- 極短セグメントの吸収（既定 0.3秒未満、または2単語未満）
- **連続する同一話者の結合（既定 0.5秒以下の間隔）**

**特に後者が疑わしいです。**

会議では「間」が頻繁に発生します。0.5秒の閾値で結合し続けると、
**同一話者と判定された区間が際限なく繋がります。**

確認方法:

- 閾値を変えて再実行し、セグメント数の変化を見る
- **結合された区間の間隔の分布**を確認する
- 61分の区間が、何回の結合の結果なのかを数える

### 仮説 D — 単語レベルの割当が機能していない

**該当する場合**: [3] で話者が変わる単語がほとんどない

utteran は単語の中心時刻で話者を割り当てています。
Phase 3b で whisper.cpp の DTW タイムスタンプを実装済みです。

確認方法:

- 単語タイムスタンプが実際に取得されているか
  （`word_timestamps` が `auto` なら、話者分離時は取得されるはず）
- 単語時刻が妥当か（セグメント範囲内に収まっているか）
- **`t_dtw` が全て -1 になっていないか**（Phase 3b の既知の罠）

## Step 3 — 修正

原因に応じて修正してください。**以下を満たすこと。**

### 妥当な粒度になること

**目標**: 3分クリップでの実測（25〜31セグメント）から外挿して、
**極端に外れない**セグメント数になること。

厳密な数値目標は立てられませんが、**116分で18は明らかに異常**です。

### 閾値の見直し

仮説 C が原因なら、閾値の設計自体を見直してください。

- **固定の秒数閾値が、長時間音声に適しているか**
- 結合の連鎖に上限を設けるべきか
  （「何回まで結合してよいか」「結合後の最大長」など）
- 音声長に応じて閾値を変えるべきか

**判断と根拠を記録してください。**

### 既存の挙動を壊さないこと

- **3分クリップでの結果が悪化しないこと**
- Phase 3 の受入試験（P10）と同等の結果が得られること
- 短い音声で細分化しすぎないこと

**長時間を直して短時間を壊す、という事態を避けてください。**

## Step 4 — 判定基準の見直し

**受入試験の話者分離判定に、「粗すぎる」を検出する基準を追加してください。**

現在の基準は「細分化しすぎ」しか検出できません。

追加すべき観点の例:

- **最長連続同一話者区間の割合**（音声長に対して何%まで許容するか）
- **音声長あたりのセグメント数の下限**
- 話者交代の回数

**具体的な閾値は、実測に基づいて決めてください。**
3分クリップの実測（25〜31セグメント）と、今回の116分の結果が
判定材料になります。

判定基準を `tools/acceptance/` のケースに反映してください。

- 元のファイルを変更・削除・移動しない

長さの異なるクリップが必要な場合、`output/_testdata/` に生成してください。

## 実装上の注意

### 破壊的変更への配慮

- 既存の venv、モデル、設定を壊さない
- **閾値の変更により、既存ジョブの `config_hash` が変わります**
- Phase 5a〜5l の機能を壊さない

### コミット

- ブランチ `fix/long-audio-diarization`
- Step 単位でコミットする
- `git push` は実行しない
- **実データ、生成したクリップをコミットしない**

---

## 禁止事項

- 段階ごとの切り分けを省略して修正すること
- 最終出力だけを見て原因を推測すること
- 長時間を直して短時間を壊すこと
- 文字起こしの本文を記録すること
- 実測せずに閾値を決めること
- マイナーバージョンを独断で上げること
- `要件定義.md` を更新せずに仕様を変えること

---

## 不明点があった場合

1. `要件定義.md` と Phase 3 の実測記録を優先する
2. 閾値の設計は判断してよい。**根拠となる実測を必ず示すこと**
3. 判断できない場合、安全側に倒し、記録する
