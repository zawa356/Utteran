## R-1 — whisper.cpp のハルシネーション対策

**本フェーズで最も重要な項目です。**

### 問題の所在

受入試験で `P3-U-006` として「長時間・単語TSなしの whisper.cpp が同一セグメントを
最大72回連続生成する」不具合が報告され、「5回目以降を抑制して最大4回に制限」という
修正が入りました。

**これは症状を隠しただけで、原因を潰していません。**

Phase 3b Step 4 の記録によれば、whisper.cpp バックエンドが使用している引数は
以下だけです。

```
-m -f -l -bs -ojf -of -pp -t --prompt -oved --device --no-gpu --dtw --no-flash-attn
```

**ハルシネーション対策に相当する引数が1つも含まれていません。**

一方、`要件定義.md` は faster-whisper 経路に対して
`vad_filter = true` と `condition_on_previous_text = false` を既定として定めています。
つまり**バックエンド間で機能パリティが取れていない**状態です。

反復ループは典型的に「無音区間で前文脈に引きずられる」ことで発生します。
前文脈の遮断と無音除去が効いていないことが直接の原因である可能性が高いと考えられます。

### 裏付けとなる観測

受入試験の P14 で、同一音声の処理結果が経路によって大きく分かれています。

| 条件 | セグメント数 | 最大連続反復 |
|---|---:|---:|
| 単語TSなし | 372 | 4（抑制が作動） |
| 単語TSあり | 210 | 2 |

同じ音声でセグメント数が 43% 異なり、反復が出るのは単語TSなしの経路だけです。
単語TSありは `--no-flash-attn` が付くため実行経路が異なります。
**特定の経路だけが品質不良を起こしており、抑制ロジックがそれを覆い隠しています。**

### 実施内容

**Step 1-A. 再現と原因の特定**

1. 抑制ロジックを一時的に無効化できるようにする（設定またはデバッグフラグ）
2. 受入試験で反復が発生した条件を再現する
3. **なぜ単語TSの有無で結果が変わるのかを特定する**
   - `--no-flash-attn` の有無による数値差か
   - `--dtw` 有効時のセグメント分割の違いか
   - それ以外か
4. 特定できない場合も、観測した事実を詳細に記録すること

**Step 1-B. 利用可能な対策の調査**

whisper.cpp v1.9.1 の `cli.cpp` と `--help` を確認し、以下に相当する手段の有無と
正確なオプション名を調べてください。**推測で実装しないこと。**

| 目的 | faster-whisper での対応 | whisper.cpp での対応 |
|---|---|---|
| 前文脈による条件付けの遮断 | `condition_on_previous_text=False` | 要調査 |
| 無音区間の除去 | `vad_filter=True` | 要調査 |
| 低確度・高エントロピー出力の抑制 | 内部既定 | 要調査 |
| 無音判定の閾値 | 内部既定 | 要調査 |
| 温度フォールバック | 内部既定 | 要調査 |

**VAD について特に注意**: whisper.cpp の VAD 機能は、別途 VAD モデルファイルを
必要とする可能性があります。必要な場合、以下も併せて実装してください。

- モデルカタログへの VAD モデルの登録
- `models download` での取得
- VAD モデル未取得時の分かりやすいエラーと取得案内
- `models verify` での検証

**Step 1-C. 対策の適用と効果測定**

1. 調査で判明した対策を**1つずつ**適用し、それぞれの効果を測定する
   （まとめて適用すると、どれが効いたか分からなくなる）
2. 測定項目: 最大連続反復回数、セグメント数、処理時間、日本語文字比、
   空セグメント比、総文字数
3. 測定素材は、反復が再現する長さの音声を使うこと
4. 効果と副作用（処理時間の増加など）を記録する

**Step 1-D. 既定値の決定と設定化**

1. 測定結果に基づき、whisper.cpp 経路の既定値を決定する
2. **faster-whisper 経路との機能パリティ表を作成し、`要件定義.md` に記載する**
3. 各対策を設定で無効化できるようにする
4. 抑制ロジックは**保険として残す**が、以下を満たすこと
   - 閾値を設定可能にする
   - **抑制が発生したことをログに記録する**（黙って削らない）
   - 既定の閾値を、根本対策後の実測に基づいて見直す
   - 会議音声の相槌など、正当な繰り返しを削る可能性がある旨を要件定義に明記する

**faster-whisper 経路の挙動は変えないでください。** 既存の出力が変わらないことを
確認してから完了としてください。

## R-2 — auto 選択の優先順位

### 問題の所在

性能測定で、`openvino_vulkan` が `vulkan` 単独より遅い結果になっています。

| 構成 | TSなし | 実時間比 |
|---|---:|---:|
| whisper.cpp / Vulkan | 17.194秒 | 10.469x |
| whisper.cpp / OpenVINO+Vulkan | 18.403秒 | 9.781x |

現在の auto は `ovvk` を `vulkan` より上位に置いています。これは参考実装の
ベンチマーク（別ハードウェアでの実測）を根拠に決めた順序ですが、
**本機・この音声では逆転しています。**

差は約 7% と小さいものの、`ovvk` は OpenVINO IR の変換作業と追加のディスク容量を
必要とします。**その手間を払ってまで既定にする根拠が、この環境では失われています。**

### 実施内容

1. **測定の信頼性を上げる。** ウォームアップ 1 回のあと、3 回以上繰り返して
   中央値を取る形で再測定する。初回はモデルロードとシェーダーキャッシュの生成で
   遅くなるため、単発測定では判定できない
2. 複数の音声長（30秒、3分、10分程度）で測定する。
   短い音声ではモデルロードの比率が高く、傾向が変わる可能性がある
3. 有意な差があるかを判断する
4. **有意差がない場合、IR 変換が不要な `vulkan` を上位に置くことを検討する。**
   利用者の手間が少ないほうを既定にするのが妥当です
5. 決定した順序と根拠を `要件定義.md` に記載する
6. **README の性能表に、本機での実測値を併記する。**
   参考実装の別環境での数値と混同されないよう、測定環境を明記すること

順序を変更する場合、`devices` の auto 表示と理由の文言も追従させてください。

## R-3 — `benchmark` サブコマンド

R-2 で明らかになったとおり、**最適な構成はハードウェアと音声によって変わります。**
利用者が自分の環境で測定できる手段が必要です。

当初「移植範囲外」としていましたが、優先度が上がったため本フェーズで実装します。

### 仕様

```
utteran benchmark [--audio <パス>] [--variants <名前,...>]
                  [--word-timestamps auto|always|never]
                  [--repeat N] [--warmup N]
                  [--json <出力パス>] [--apply]
```

要件:

- 対象は whisper.cpp の各構成と faster-whisper。利用可能なものだけを測定する
- **ウォームアップを既定 1 回、計測を既定 3 回**とし、中央値を報告する
- 測定項目: 総所要時間、モデルロード時間、実時間比、ピーク RAM。
  可能なら whisper.cpp の内部内訳（encode / decode）も取得する
- 結果を表で表示し、`--json` で構造化出力する
- `--audio` 省略時の既定素材を決める。**実データを既定にしないこと。**
  合成音声を生成するか、明示指定を必須にするかを判断し、要件定義に記載する
- `--apply` は、最速だった構成を `config.toml` の
  `[asr.whisper_cpp].variant` に書き込む
- 話者分離の CPU / XPU 比較も測定対象に含めるか判断する
  （含める場合、モデルの取得状況に依存する点に注意）

### 注意

- 測定中に他の処理が動いていると結果が歪みます。その旨を実行前に表示してください
- 測定結果はジョブとして保存しないこと（ジョブ管理を汚さない）
- 実データを指定された場合も、文字起こし内容を結果に含めないこと

## R-4 — 受入試験ハーネスの追従

### 問題の所在

Phase 3 の受入試験で、Phase 1/2 のハーネス 98 ケース中 **47 件が「受入器不整合」で
失敗**しています。分類自体は妥当ですが、**このままでは Phase 1/2 の回帰試験が
二度と使えません。**次に大きな変更を入れたとき、既存機能の回帰を検出できなくなります。

報告されている不整合の原因:

- 旧ジョブルートの固定前提
- `auto` が CPU を選ぶ前提
- 旧 `--device` オプションの前提
- 旧終了コードの期待値
- 文字化けした期待文字列

### 実施内容

1. 47 件の失敗を個別に確認し、修正する
2. **環境依存の値を固定で持たず、実行時に取得する形へ改める**
   - ジョブルート、モデル保存先、既定プロファイルなど
   - `utteran config show --json` や `devices --json` から取得する
3. `auto` の選択結果に依存する期待値を、環境非依存の判定に置き換える
4. 文字化けした期待文字列を修正し、**UTF-8 で扱われることを保証する**
5. **Phase 3 の試験ケース（P0〜P16）と統合し、単一のハーネスから
   グループ指定で実行できるようにする**
6. 統合後、全ケースを Intel 機で実行し、合格することを確認する
   （NVIDIA 依存のケースはスキップ扱いとし、その旨を明示する）

修正後のハーネスは、**次のフェーズ以降で回帰試験として使えること**が完了条件です。

## R-5 — 長時間音声でのメモリ挙動

### 問題の所在

受入試験の長時間耐久は、実ファイルが約 24分46秒に変わったため、その長さでの
確認にとどまっています。ピーク RAM は 8.48 GiB でした。

**Arc 140T は共有メモリ構成であり、2時間級の音声でメモリがどう推移するかは
依然として不明です。**24分での値が線形に伸びる保証はありません。
`要件定義.md` 13章の既知課題（長時間音声での pyannote のメモリ消費）が
この環境で顕在化するかどうかが未確認です。

### 実施内容

1. 実ファイルを連結して、**約 25分 / 50分 / 100分 / 150分**の音声を生成する
   （`output/_testdata/` に置き、git 追跡対象外であることを確認すること）
2. 各長さで、以下を測定する
   - ASR のピーク RAM と所要時間
   - 話者分離のピーク RAM と所要時間（XPU / CPU 両方）
   - ステージ別の内訳
3. **メモリ消費が音声長に対してどう推移するかを記録する**
   （線形か、それ以上か、頭打ちになるか）
4. 2時間級で問題が発生する見込みがあるかを判断し、記録する
5. 実際にメモリ不足が発生した場合
   - エラーメッセージが理解可能か確認する
   - 中間結果が保持され、再開が可能か確認する
   - **不具合としては扱わない**（要件定義13章の既知課題）。
     ただしエラーメッセージが不親切なら修正する
6. 結果を README に記載する（利用者が自環境の限界を判断できるように）

**連結した音声は実データです。文字起こし内容を記録しないこと。**

時間が不足する場合、150分を省略し、100分までの傾向から外挿してください。
