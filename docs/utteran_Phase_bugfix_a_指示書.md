## 判明している事実

### 切り分け結果

| 操作 | 結果 |
|---|---|
| `gui.ps1` で起動 | **UI は正常に表示される** |
| **セットアップウィザードを開く** | **フリーズし、復帰しない** |

配布版（インストーラー）では、初回起動時に自動でウィザードが開くため、
**起動直後にフリーズしたように見えていました。**

### 症状の詳細

- 画面は一瞬表示され、その後白くなる
- プロセスは生存（`Responding: False`）
- サーバーのポートは `Listen` のままだが、リクエストに応答しない
- 接続が `CloseWait` のまま残る
- 待っても復帰しない

### コンソールに出力されたエラー

```
[pywebview] Error while processing
window.native.AccessibilityObject.Bounds.Empty.Empty.Empty.Empty.Empty
...（数百回の繰り返し）...
: maximum recursion depth exceeded
--- Logging error ---
```

```
[pywebview] Error while processing
window.native.ActiveForm.ModifierKeys.A.A.A.A.A.A.A.A.A.A.A...
: maximum recursion depth exceeded
```

```
[pywebview] Error while processing window.native.browser.webview.AllowExternalDrop:
CoreWebView2Controller members can only be accessed from the UI thread.
System.InvalidCastException: ... E_NOINTERFACE
```

## 原因の分析

### 主原因: `window.native` の再帰的プロパティ走査

**pywebview が `window.native`（.NET のフォームオブジェクト）以下の
プロパティを再帰的に辿り、無限ループに陥っています。**

`.NET` のプロパティは相互参照するため、
`AccessibilityObject.Bounds.Empty.Empty.Empty...` のように無限に辿れます。

- CPU を消費し尽くし、UI スレッドが応答しなくなる
- 大量の `--- Logging error ---` が出ており、**ログ出力も詰まっている**
- WebView2 のオブジェクトへ UI スレッド外からアクセスし、COM 例外が発生している

### 引き金の候補

**ウィザードのどの操作が `window` に触れているかを特定してください。**

| 候補 | 根拠 |
|---|---|
| A. **ファイル・フォルダ選択ダイアログ** | Phase 5h で `create_file_dialog` を実装。ウィザードでも入出力先を選ぶ |
| B. **ドラッグ＆ドロップの `file.path`** | 下記参照 |
| C. pywebview の他の API 呼び出し | ウィザード固有の処理 |
| D. `window` オブジェクトの列挙・シリアライズ | デバッグ目的のコードなど |

**B について補足します。**`index.html` に以下があります。

```javascript
const file = event.dataTransfer.files[0];
if (file) $("input-path").value = file.path || file.name;
```

**`file.path` は標準の File オブジェクトには存在しません。**
pywebview 環境で拡張されている可能性があり、
プロパティ解決の過程で `window.native` の走査を誘発しうる箇所です。

**これは以前から報告されている「ドラッグ＆ドロップでファイル名しか入らない」
問題と同じ箇所です。**あわせて対処してください。

## Step 2 — 修正

### 原則

**`window.native` に触れないこと。**

pywebview の内部オブジェクトを JavaScript から辿ると、
再帰走査が発生します。**必要な機能は、Python 側で明示的に公開した
API を経由して呼び出してください。**

### ファイル選択ダイアログ

Phase 5h で実装済みの機能です。**`window` を直接触らない方式へ改めてください。**

- Python 側に専用のハンドラを用意し、そこから `create_file_dialog` を呼ぶ
- JavaScript からは、その関数だけを呼ぶ
- **`window.native` を経由しない**

### ドラッグ＆ドロップ

**`file.path` の使用をやめてください。**

以前の調査で判明したとおり、**Web のドラッグ＆ドロップではフルパスが
取得できません。**現状は `file.name`（ファイル名のみ）が入力欄に入り、
実行時に ffmpeg で失敗します。

以下のいずれかを選び、**判断と理由を記録してください。**

| 案 | 内容 |
|---|---|
| A | pywebview の drag & drop 対応機能で、Python 側からパスを取得する |
| B | **ドラッグ＆ドロップを廃止し、選択ダイアログに一本化する** |

**B も妥当な選択です。**「できると書いてあるのに動かない」より、
「できない」ほうが誠実です。廃止する場合、**案内文も削除**してください。

**いかなる場合も、ファイル名だけを入力欄に入れないでください。**
利用者が「入った」と誤解し、実行して失敗します。

### WebView2 のスレッド違反

```
CoreWebView2 can only be accessed from the UI thread
```

これも再帰走査の副作用ですが、**根本を直しても残る場合は個別に対処**してください。

### ログの詰まり

`--- Logging error ---` が大量に出ています。

- ログ出力が例外を起こしても、**アプリの動作を妨げないこと**
- 大量出力時にブロックしないこと
- Phase 5j のログ基盤で、この保護がされているかを確認する

## Step 3 — 再発防止

**同じ問題が再発しないよう、以下を検討してください。**

1. **pywebview の内部オブジェクトへのアクセスを禁止する規約**
   - `要件定義.md` に記載する
   - 可能なら、静的検査で検出する
2. **JavaScript のエラーを Python 側へ転送する**
   - Step 1 で用意した場合、恒久的な機能として残すか判断する
   - **今回、フロントの例外が一切記録されていなかった**ことが
     調査を困難にしました
3. **ウィザードの起動を自動テストで守る**
   - フロントエンドのテスト手段がない場合、
     どう守るかを判断して記録する
