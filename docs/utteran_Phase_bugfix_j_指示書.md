## 症状

**Arc 機でアンインストール後に再インストールしたところ、
セットアップウィザードの検証が失敗しました。**

```
ステージ開始: asr
ERROR: ステージ失敗: asr: ネイティブビルドがありません。
       `utteran native build`を実行してください。
```

ウィザードの表示は次のとおりでした。

> この手順でエラーが発生しました
> 必要な依存関係、ffmpeg、モデルの導入状態を確認してください。

---

## 原因（推定・確認すること）

**ac-2（0.1.22）で、アンインストール時に `~/.utteran/native` を削除対象にしました。**
「再生成可能なランタイムは削除する」という方針に沿った正しい動作です。

**問題は、再生成する経路が存在しないことです。**

セットアップウィザードは、依存関係・ffmpeg・モデルの導入と検証を行いますが、
**ネイティブビルドを実行しません。**Intel 機の推奨構成は whisper.cpp の
OpenVINO / Vulkan 経路であり、**ネイティブビルドが必須**です。

### この不具合は以前から存在した可能性が高い

**bugfix-i（0.1.27）でアンインストールが完走するようになるまで、
この経路が踏まれていませんでした。**

手動でビルドしたものが残っていたため表面化せず、
**アンインストールが初めて成功したことで露呈した**と推定されます。

**推定であり、確認してください。**

---

## 重要な認識 — 「前提不足」ではない

**この機は、以前 utteran が動作していました。**

つまり、その時点で cmake / MSVC Build Tools / Vulkan SDK が揃っており、
ビルドできる環境でした。**マシンからそれらが消えたわけではありません。**

**消えたのはビルド成果物だけです。**

したがって、これは「前提条件が足りない」問題ではなく、
**「ビルドできる環境なのに、ビルドし直す仕組みがない」**問題です。

**ウィザードの表示「必要な依存関係、ffmpeg、モデルの導入状態を確認してください」は、
原因を誤って示しています。**利用者は導入し直そうとして、時間を無駄にします。

---

## 確定した方針

**ビルドできる環境なら、ビルドする。**

- **前提条件が揃っていれば、確認を挟まず再構築する**
  以前動いていたものが動かなくなった状況で、確認は摩擦にしかなりません
- **ただし、時間がかかることを表示しながら進める**
  黙って数十分固まらせないこと
- 前提条件が足りない場合、**何が足りないかを具体的に示す**

## Step 0 — 前提条件の実態調査

**「Vulkan SDK が必要」という記述が文書に存在しますが、検証されていません。**

**将来的に、利用者が事前導入すべきものを極限まで減らしたい**という方針があります。
そのために、まず実態を確認します。

### 調査すること

**1. cmake を PyPI 版で代替できるか**

PyPI に `cmake` パッケージが存在します（公式バイナリを wheel に包んだもの）。
`ninja` も同様です。

- **これで whisper.cpp のビルドが実際に通るか**
- 通る場合、**uv 経由で導入できるため、利用者の手作業から外せる**
- 通らない場合、その理由

**2. Vulkan は SDK が必要か、ランタイムで足りるか**

| | 用途 | 含むもの |
|---|---|---|
| Vulkan Runtime | 実行 | ローダー（`vulkan-1.dll`）。**GPU ドライバに同梱される** |
| Vulkan SDK | ビルド | ヘッダ、`vulkan-1.lib`、検証レイヤ、`glslc` など |

一般にはビルドに SDK が必要ですが、**whisper.cpp / ggml の構成次第です。**

- ggml がヘッダを vendoring していないか
- **シェーダのコンパイルに `glslc` が必要か**（事前コンパイル済みでないか）
- **実際に SDK なしでビルドを試して確認する**

**3. MSVC Build Tools**

Microsoft のインストーラー経由でしか入りません。**これは減らせない前提**です。
**そう確認できれば、その旨を記録してください。**

**4. 経路ごとの差**

| 経路 | 必要なもの |
|---|---|
| `cpu` | ? |
| `vulkan` | ? |
| `openvino` | ? |
| `openvino_vulkan` | ? |

**OpenVINO のランタイムは pip で入ります。**
Vulkan 側だけが問題である可能性があります。**経路ごとに整理してください。**

### 記録すること

- 各項目の調査結果
- **利用者の手作業が必須なものの、最終的な一覧**
- 減らせる可能性があるものと、その方法

**推測で結論しないでください。実際に試して確認します。**

## Step 1 — 欠落の検出（ステージ失敗より前に）

### 現状の問題

**ネイティブビルドの欠落が、ASR ステージの実行時に初めて発覚します。**

ウィザードは検証まで進んでから失敗し、しかも**原因を誤って案内**します。

### 求める挙動

- **選択された構成がネイティブビルドを必要とするかを判定する**
- **必要なのに存在しない場合、ステージを開始する前に検出する**
- ac-1 の原則に従い、**「未整備」を「失敗」として扱わない**

### 注意

**構成によっては不要です。**

`faster-whisper` や OpenVINO GenAI はネイティブビルドを使いません。
**必要な構成でのみ判定してください。**

## Step 2 — 再構築

### 求める挙動

- 前提条件が揃っていれば、**再構築を実行する**
- **確認を挟まない**（復旧の文脈では摩擦になる）
- **進行状況を表示する**
- **所要時間の目安を示す**（数分から数十分かかる）

### ac-1 の原則を適用する（重要）

> 進行中を失敗としない。未知を不明とする。

**ビルド中を失敗として表示しないこと。**

ac-1 では、プローブのタイムアウトが短すぎて進行中が失敗扱いされる問題を直しました。
**ビルドはプローブよりはるかに時間がかかります。同じ問題を再発させないでください。**

- タイムアウトを設ける場合、**根拠のある値にする**
- **極端な値へ振らないこと**（撤廃も、無制限も避ける）
- 途中経過が分かる形にする

### 失敗した場合

- **何が失敗したかを具体的に示す**
- ログの場所を伝える
- **部分的に生成されたものが残らないようにする**、または残ったことを記録する

**「データを捨てる処理は、何をどれだけ捨てたかを記録する」**という原則に従います。
