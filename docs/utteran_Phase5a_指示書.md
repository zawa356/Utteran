# utteran — Phase 5a 実装指示（GUI の骨格と実行機能）

## あなたへの依頼

Phase 5a として、**GUI の骨格、環境検出、文字起こしの実行と進捗表示**を実装してください。

着手前に必ず以下を読んでください。

1. `AISTATE.md`
2. `要件定義.md`
3. `README.md`
4. `tools/acceptance/README.md`（環境判定の仕組みが参考になります）

作業ブランチは `feature/phase5a-gui-foundation` を使用します（作成済み）。

---

## 作業環境について

**今回の作業機は NVIDIA GPU 搭載機（GTX 1070 Ti）です。**
これまで Phase 3 以降の作業は Intel 機で行われていました。

したがって以下に注意してください。

- **CUDA 機でのプロファイル分離は未検証です。**
  GUI の前に `setup.ps1 -Profile cuda` で環境を構築し、動作を確認してください
- 旧 `.venv-windows` が残っている場合、削除せず放置してください
  （動作確認後に利用者が判断します）
- `intel` / `vulkan` プロファイルはこの機では検証できません。
  GUI がそれらを扱えることは、コード上の対応にとどめて構いません
- 構築時に問題が出たら、それ自体が成果です。修正して記録してください

## アーキテクチャ

```
[GUI プロセス]  独立した Python 環境
   │  FastAPI (127.0.0.1、OS 割当ポート、セッション鍵で保護)
   │  フロントは HTML/CSS/JS、pywebview のネイティブウィンドウで表示
   ↓  subprocess + JSON
[CLI プロセス]  プロファイル venv 内の utteran
```

### 原則

**GUI は utteran のコアパッケージを import しないでください。**

理由は2つです。

1. GUI は初回セットアップ（5c）を担うため、**プロファイル venv が存在しない状態でも
   起動できる必要がある**
2. GUI の venv には torch や faster-whisper を入れない。
   入れると配布サイズが数 GB になり、5d のインストーラー化が破綻する

**GUI が依存してよいのは CLI の JSON 出力の契約だけです。**
型定義の共有のためであっても、`utteran` パッケージを import しないこと。

### GUI 環境

- 新しい extras `gui` を追加する（fastapi、uvicorn、pywebview など軽量なもののみ）
- venv は `.venvs/<os>-gui` とする
- `setup.ps1` に `-Profile gui` を追加するか、別の導入手段を用意するかは判断してよい
  （5c でセットアップウィザードを作るため、暫定でよい）
- 起動手段を用意する（`gui.ps1` またはコンソールスクリプト）

## Step 1 — CLI 側の変更: 機械可読な進捗出力

GUI が進捗を表示するには、構造化された進捗が必要です。
現在の進捗は Rich によるコンソール表示で、GUI からは読めません。

### 仕様

`--progress-json` オプションを追加し、**標準エラー出力へ JSON Lines で進捗を流します。**

イベントの種別は以下を想定しますが、実装に合わせて調整して構いません。
**決定した契約を `要件定義.md` に記載してください。**

| イベント | 内容 |
|---|---|
| `job_resolved` | job_id、レジュームの有無、実行予定のステージ |
| `stage_start` | ステージ名 |
| `progress` | ステージ内の進捗（比率または現在値／総数） |
| `stage_done` | ステージ名、所要時間、スキップか実行か |
| `output_written` | 生成された出力ファイルのパスと形式 |
| `warning` | 警告（フォールバック、抑制の発生など） |
| `error` | エラー種別とメッセージ |
| `done` | 総所要時間、終了コード |

各イベントに `schema_version` とタイムスタンプを含めてください。

### 必須要件

- **文字起こしの本文をイベントに含めないこと。**
  GUI がログとして表示・保存する可能性があるため
- 秘密値のマスクを通すこと
- 既存のコンソール表示と併用できること（`--quiet` との組み合わせを含む）
- バッチ処理では、ファイル単位のイベントも出すこと
- **1行1 JSON を厳守すること。**途中で改行を含めない
- Phase 4a で導入した UTF-8 固定が効いていることを確認する
  （日本語を含む出力がパイプ経由で壊れないこと）

## Step 2 — バックエンド（FastAPI）

### セキュリティ

ローカルに HTTP サーバーを立てるため、**同一マシンの他プロセスやブラウザから
アクセスできてしまいます。**以下を必ず実装してください。

- `127.0.0.1` のみにバインドする（`0.0.0.0` は禁止）
- ポートは OS に割り当てさせる（固定ポートを使わない）
- **起動ごとにセッション鍵を生成し、全 API リクエストで検証する**
- CORS を有効にしない
- 鍵の不一致を検出したら記録する

### 提供する機能

**環境情報**

- プロファイルの一覧と状態（`utteran profiles list`）
- デバイスとバックエンドの検出結果（`utteran devices --json`）
- モデルの一覧と導入状況（`utteran models list --json`）
- ネイティブビルドの状態（`utteran native status`）

**実行**

- 文字起こしの開始（設定を受け取り、CLI をサブプロセスで起動）
- 進捗のストリーミング（Server-Sent Events または WebSocket）
- キャンセル
- 実行結果の取得（出力ファイルの一覧、終了コード）

**設定**

- GUI の設定の読み書き（テーマ、言語、既定のプロファイル、入出力先）
- Hugging Face トークンの保存と有無の確認

### サブプロセスの制御

- 実行対象はプロファイル venv 内の実行ファイルを直接指定する
  （`run.ps1` を経由すると制御が複雑になる）
- **キャンセルはプロセスツリーの終了で行う。**
  Phase 2 の受入試験で解決した Windows 固有の問題（U-002）と同じ手法を使うこと
- 標準エラー出力を1行ずつ読み、JSON として解釈できる行はイベントとして扱う
- **JSON として解釈できない行も破棄せず保持する**（エラー時の詳細表示に必要）
- 長時間処理のためタイムアウトは設けない。
  ただし一定時間イベントが来ない場合の検出は行う
- 同時実行は1件に制限する（キューは 5b 以降）

### トークンの扱い

- **保存先は OS キーリングのみ。**`config.toml` には書かない
- 設定画面では入力を受け付けるが、**保存済みの値を画面に表示しない**
  （「設定済み」「未設定」の状態のみ表示する）
- API のレスポンスにトークンを含めない
- ログに出さない

## Step 3 — フロントエンド

### 画面構成

**起動時: 環境の確認**

- 検出されたハードウェア、利用可能なプロファイル、導入済みモデルを表示する
- **プロファイルが1つも無い場合、その旨と対処を案内する**（ウィザードは 5c）
- 現在選択されているプロファイルと、その環境で何が使えるかを示す

**メイン: 実行設定**

- 入力ファイル／フォルダの選択（ドラッグ＆ドロップに対応できると望ましい）
- 出力先の選択
- プロファイルの選択
- ASR バックエンド、モデル、デバイス
- 話者分離の有無、モデル、デバイス、話者数
- 言語
- 出力形式
- レジュームの扱い

**重要**: 選択肢は**すべて検出結果から動的に生成**してください。
利用できないバックエンド・デバイス・モデルを提示しないこと。
Phase 3c で `start.ps1` が NVIDIA 不在の環境で `cuda:0` を提示していた問題と
同じ轍を踏まないでください。

**実行中: 進捗**

- ステージ別の進捗（音声抽出、ASR、話者分離、統合、出力）
- 経過時間と、可能なら残り時間の目安
- ログの表示（折りたたみ可）
- キャンセルボタン

**完了**

- 生成された出力ファイルの一覧
- 出力フォルダを開くボタン
- （結果の閲覧は 5b で実装します）

**設定**

- テーマ（ダーク／ライト）
- 表示言語（日本語／英語）
- Hugging Face トークン
- 既定のプロファイル、既定の入出力先

### デザイン

**既定はダーク、ライトへ切り替え可能とします。**

方向性は「落ち着いた業務向けのモダン」です。具体的には以下を指針としてください。

- 彩度を抑えた配色。アクセントカラーは1色に絞る
- 階層は影ではなく、**背景の明度差と境界線**で表現する
- 余白を十分に取る。情報を詰め込まない
- 角丸は控えめに統一する
- アニメーションは最小限（状態遷移が分かる程度）
- **フォントは日本語が美しく出るものを指定する**
  Windows では Yu Gothic UI や Meiryo を優先し、フォールバックを用意する
- 等幅が必要な箇所（ログ、パス、タイムスタンプ）は等幅フォントを使う

**テーマは CSS 変数で定義**し、切り替えが色の再定義だけで済む構造にしてください。
色をコンポーネントに直書きしないこと。

### 国際化

**日本語と英語の切り替えを 5a の時点で実装してください。**
後から入れるとコストが高くなります。

- 文言を辞書として外部化する
- UI から切り替えられる
- 設定に保存する
- 既定は日本語
- **CLI からの出力（エラーメッセージなど）は翻訳対象外**とし、
  そのまま表示してよい（無理に翻訳しようとしないこと）

### 状態の保存

- GUI の設定は `platformdirs` 配下に保存する
- ジョブディレクトリや config.toml とは別にする
- **入力ファイルのパスを履歴として保存する場合、
  ファイル名に個人情報が含まれうる点に注意してください。**
  保存するかどうかを判断し、理由を記録すること

## Step 4 — エラー処理

CLI の終了コードを解釈し、利用者に分かる形で提示してください。

| コード | 意味 |
|---|---|
| 0 | 正常終了 |
| 1 | 一般エラー |
| 2 | 設定エラー |
| 3 | 依存エラー（ffmpeg 未検出、モデル未取得など） |
| 4 | 入力エラー |
| 5 | バッチ一部失敗 |
| 130 | 中断 |

- **対処方法を併せて示すこと。**「エラーが発生しました」だけにしない
- モデル未取得なら取得手順、トークン未設定なら設定画面への導線を示す
- 詳細（標準エラー出力の内容）は折りたたみで表示する
- **秘密値のマスクを通すこと**

## テスト

モデルなしでテストできるものを重点的に書いてください。

- 進捗イベントの生成（各ステージ、バッチ）
- 進捗イベントのパース（不正な行、途中で切れた行の扱い）
- セッション鍵の検証（正しい鍵、誤った鍵、鍵なし）
- サブプロセスの起動引数の組み立て（設定から CLI 引数への変換）
- キャンセル処理（フェイクプロセスを注入可能にすること）
- 終了コードからメッセージへの変換
- 検出結果から選択肢を生成するロジック
- テーマと言語の切り替え、設定の保存と復元
- 秘密値のマスク

**サブプロセスの起動はフェイクに差し替えられる構造にしてください。**
テストで実際に CLI を起動しないこと。

GUI の見た目や操作は自動テストが困難です。
**`docs/` に手動確認手順書を作成**し、何を目視で確認すべきかを記録してください。

## 実装上の注意

### 機密データ

- 進捗イベント、GUI のログ、設定に文字起こし本文を含めない
- 入力ファイル名の扱いに注意する（個人情報を含みうる）
- `.env` を読み取らない
- トークンをログ、API レスポンス、画面に出さない

### 破壊的変更への配慮

- **既存の CLI の挙動を変えない。**`--progress-json` は追加のみ
- 既存のジョブ、モデル、設定を無効化しない
- `start.ps1` は当面残す（GUI が成熟するまで並存させる）

### 参考実装

`_tmp/` に参考実装（TranscriptTool）がある場合、Web GUI の
ディレクトリ構成が参考になります。**コードをコピーせず、構成の考え方のみ**
参考にしてください。存在しない場合は無視して構いません。

### コミット

- ブランチ `feature/phase5a-gui-foundation`
- Step 単位でコミットする
- `git push` は実行しない
- 実データをコミットしない

## 禁止事項

- GUI から `utteran` パッケージを import すること
- GUI の venv に torch や faster-whisper を入れること
- サーバーを `0.0.0.0` にバインドすること
- セッション鍵の検証を省略すること
- 進捗イベントに文字起こし本文を含めること
- トークンを `config.toml` に書く、画面に表示する、ログに出すこと
- 利用できないデバイス・モデルを選択肢に出すこと
- 色をコンポーネントに直書きすること（テーマ切り替えが破綻します）
- 実機で動作確認せずに「完了」と報告すること
- `要件定義.md` を更新せずに仕様を変えること
