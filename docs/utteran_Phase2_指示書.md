## 設計書の修正が必要な箇所

以下は Phase 2 の着手時に `要件定義.md` を修正してから実装してください。
修正内容は `変更履歴.md` と `AISTATE.md` にも記録すること。

### 1. job_id の算出方法（設計書 6.2 の誤り）

現行の記述は `job_id = sha256(入力ハッシュ + 設定ハッシュ)` だが、これでは
出力形式を変えただけで別ジョブになり、6.3 が意図する「export のみ再実行」が成立しない。

**修正後の仕様**:

```
job_id = sha256(入力ファイルのハッシュ)[:16]
```

設定は job_id に含めない。再実行の要否は、ステージごとに保存した `config_hash` を
現在の設定から算出した値と比較して判定する。

同一入力に対するジョブは1つだけ存在し、設定を変えて再実行すると
影響のあるステージ以降のみが再計算される。

### 2. ステージごとの config_hash の算出対象

設計書 6.3 の表を、以下のとおり具体化して追記すること。

| ステージ | config_hash の算出対象 |
|---|---|
| audio | 入力ファイルハッシュ、サンプリングレート、チャンネル数、サンプル形式 |
| asr | audio の config_hash、`[asr]` セクション全体 |
| diarization | audio の config_hash、`[diarization]` セクション全体 |
| merge | asr / diarization の config_hash、`[alignment]` セクション全体 |
| export | merge の config_hash、`[output]` セクション全体 |

算出は、対象の設定値をキー順にソートした正規形（JSON、キーソート、
浮動小数は固定桁で文字列化）にしてから SHA-256 を取る。
Python の `dict` の順序やロケールに依存しない実装にすること。

### 3. バッチ処理の終了コード

設計書 9 章の終了コード表に以下を追加する。

| コード | 意味 |
|---|---|
| 5 | 一括処理で一部のファイルが失敗した（全滅ではない） |

全ファイルが失敗した場合は 1 とする。

### 4. ジョブディレクトリのロック

同一ジョブに対する多重実行を防ぐため、ジョブディレクトリにロックファイルを置く仕様を
6 章に追記する。

- ロックファイルには PID と開始時刻を記録する
- 既存のロックがある場合、当該プロセスの生存を確認する
- プロセスが存在しなければ古いロックとみなして取得する
- 存在する場合はエラー（終了コード 1）とし、`--force-unlock` で強制解除できる

### 5. `devices` の機械可読出力

`utteran devices --json` で構造化データを出力できる仕様を 9 章に追記する。
将来 GUI がデバイス一覧を取得するために使う。

## 各機能の要求仕様

### ジョブ管理・レジューム（`jobs.py`）

- ジョブディレクトリは設計書 6.1 のとおり。既定の場所は
  `platformdirs.user_cache_dir("utteran") / "jobs"`。設定 `[general].job_dir` で上書き可能
- Phase 1 で `TemporaryDirectory` に置いていた正規化 WAV は、ジョブディレクトリに移す
- `manifest.json` は設計書 6.4 のスキーマに従う。`version` フィールドで将来の変更に備える
- ステージの状態は `pending | running | done | failed`。
  異常終了で `running` のまま残ったものは、次回実行時に `pending` として扱う
- `--resume` は既定で有効。`--force` で全ステージを強制再実行
- 各ステージの完了時に `manifest.json` を更新する。途中でプロセスが落ちても
  完了済みステージの情報が失われないこと（書き込みは一時ファイル経由で `Path.replace`）
- `merged.json` からの再 export が、ASR を再実行せずに完了することを確認できるようにする

`utteran jobs` サブコマンド:

```
utteran jobs list                     ジョブ一覧（入力名、状態、更新日時、サイズ）
utteran jobs show <job_id>            ステージごとの状態と設定ハッシュ
utteran jobs clean --all              全削除
utteran jobs clean --failed           失敗ジョブのみ削除
utteran jobs clean --older-than <日数>
```

削除系は実行前に対象を表示し、確認を求める。`--yes` で省略可能。

### フォルダ一括・キュー処理

- `--recursive` でディレクトリを再帰的に処理
- 処理対象の選別は拡張子ではなく ffmpeg のデコード可否で判断する方針を維持する。
  ただし全ファイルを ffmpeg に投げるのは非効率なので、明らかに対象外のもの
  （設計書 8.1 に列挙された拡張子以外）は既定で除外し、`--include`/`--exclude` の
  glob パターンで調整できるようにする
- 処理順は名前順（安定した順序であること）
- **1ファイルの失敗で全体を止めない。** 失敗を記録して次に進む
- 処理後に集計を表示する（成功数、スキップ数、失敗数、失敗ファイルの一覧と理由）
- スキップの理由も表示する（既に完了しているジョブ、デコード不可、など）
- `Ctrl+C` で安全に中断できること。実行中のステージを可能な限り安全に終了させ、
  `manifest.json` を整合した状態にしてから終了する（終了コード 130）
- モデルのロード・アンロードをファイルごとに繰り返さない。
  バックエンドは一度ロードしたら、バッチ全体で使い回す

### モデル管理

`models/catalog.py` にカタログを定義する。各エントリが持つ情報:

- モデル ID（utteran 内での識別子）
- 対応バックエンド
- モデル形式（CTranslate2 / OpenVINO IR / pyannote pipeline / ONNX）
- Hugging Face のリポジトリ ID、またはダウンロード URL
- 概算サイズ
- ライセンス
- gated（利用条件への同意が必要か）

最低限、設計書 10.2 の表にあるものを登録する。同じモデル名でもバックエンドごとに
別エントリになる点に注意すること。

`models/manager.py` の責務:

- 導入済みモデルの検出（Phase 1 の `local_files_only` による解決ロジックと整合させる）
- ダウンロード（`huggingface_hub` を使用。進捗表示あり）
- 削除
- 整合性検証（ファイルの存在とサイズ。可能ならハッシュ）
- 保存先の解決（`UTTERAN_MODEL_DIR` による上書きを含む）

```
utteran models list              導入状況、サイズ、ライセンス、gated 表示
utteran models list --available  カタログ全体
utteran models download <ID>     取得
utteran models remove <ID>
utteran models verify [<ID>]
utteran models path
```

gated モデルの取得に失敗した場合は、原因（トークン未設定 / 未同意 / 無効なトークン）を
切り分けて、同意ページの URL を含むメッセージを出すこと。
Phase 1 の pyannote バックエンドが同様の切り分けを実装しているので、そのロジックを流用する。

**`transcribe` 実行時に未取得のモデルが指定された場合**、対話環境では取得の確認を求め、
非対話環境では終了コード 3 で明確なエラーとする。`--yes` で確認を省略できる。
暗黙のうちに数GBをダウンロードしないこと。

### `devices` コマンドとデバイス自動判定

検出項目:

- CPU: 論理コア数、物理コア数、対応命令セット（AVX2 / AVX-512）
- CTranslate2: CUDA デバイス数、各デバイス名、VRAM、
  `ctranslate2.get_supported_compute_types()` による対応 compute_type
- cuDNN / cuBLAS: 共有ライブラリまたは DLL が解決可能か
  （Phase 1 で「CUDA デバイスは見えるが float16 が使えない」環境が確認されている。
  この状態を検出して表示すること）
- PyTorch: CUDA 利用可否、VRAM（pyannote 用）
- OpenVINO: 導入済みなら `Core().available_devices`（Phase 3 の準備として検出のみ行う）
- ONNX Runtime: 導入済みなら利用可能な Execution Provider
- ffmpeg: 検出したパスとバージョン

出力:

- 既定は人間向けのテーブル表示
- `--json` で機械可読な構造化出力
- 末尾に「現在の設定で `auto` を選んだ場合に実際に使われるバックエンドとデバイス」を表示する
- Intel GPU / NPU が検出され、かつ CUDA が使えない環境では、
  「ASR は GPU/NPU で高速化できるが、話者分離は pyannote のため CPU 実行になる」旨を
  警告として表示する

自動判定ロジックは設計書 4.5 に従う。Phase 1 の暫定実装
（CTranslate2 が CUDA を報告すれば `cuda:0`）を、以下のように拡張する。

1. CUDA デバイスが報告されるだけでなく、**実際に初期化と推論が可能か**を検証する
2. compute_type の `auto` は、対応状況を確認したうえで決定する
   （float16 非対応なら int8_float16 や int8 にフォールバック）
3. フォールバックが発生した場合、その旨を情報として表示する
4. 明示的にデバイスを指定された場合はフォールバックせず、エラーとする
   （Phase 1 の判断を維持する）

### `setup.ps1`

Windows 環境の初期設定を自動化する PowerShell スクリプト。

要件:

- **冪等であること。** 何度実行しても安全
- 実行前に、何を行うかを表示する
- ネットワークに接続できない環境でも、可能な部分だけ実行して残りを案内する
- 管理者権限を必要としない（ユーザー領域にインストールする）

実行内容:

1. Python バージョンの確認（3.11 / 3.12）
2. uv の存在確認と、未導入時の導入案内
3. `uv sync` の実行（プロファイル指定に応じて extras を切り替える）
4. ffmpeg の探索。見つからない場合、公式配布物を取得して
   `<user_data_dir>/utteran/bin/` に配置する
5. CUDA 利用時、cuDNN / cuBLAS の解決可否を確認し、不足時は対処方法を案内する
6. `.env` の作成補助（`.env.example` からのコピーと、トークン入力の案内）
7. モデルの事前取得（対話的に選択、または引数で指定）
8. `utteran devices` を実行して結果を表示し、セットアップ結果を確認する

パラメータ:

```powershell
.\setup.ps1 -Profile cpu|cuda|intel        # 導入する extras を決定
            -SkipModels                     # モデル取得を省略
            -SkipFfmpeg                     # ffmpeg 取得を省略
            -ModelDir <パス>                # モデル保存先の指定
```

ffmpeg はリポジトリに含めない。取得したバイナリのライセンス情報を表示すること。

Linux 向けの同等スクリプト（`setup.sh`）は任意とする。作成する場合は
README に記載し、しない場合は Linux での手動手順を README に書くこと。

## 実装上の注意

### Phase 1 の資産を壊さないこと

- バックエンド固有の型を `pipeline.py` や `exporters/` に漏らさない原則を維持する
- トークンのマスク処理を維持する。新規追加するコマンドとエラー経路にも適用すること
  特に `models download` はトークンを扱うため、ログと例外の両方を確認する
- 進捗コールバックとキャンセルトークンのインターフェースを、
  ジョブ層・バッチ層にも一貫して通す
- Phase 1 で追加した `pytest` の `--capture=sys` 設定など、環境固有の回避策は維持する

### 中間ファイルの互換性

`asr.json` / `diarization.json` / `merged.json` には `schema_version` を持たせ、
将来スキーマが変わった際に古いジョブを検出して再計算できるようにしてください。
バージョン不一致のジョブは、警告のうえ該当ステージを `pending` として扱います。

### 並行処理

Phase 2 では**ファイル単位の並列処理を実装しないでください。**
GPU メモリの競合と、進捗表示の複雑化に見合いません。
逐次処理で、モデルを使い回す方式にとどめてください。

### プラットフォーム差異

Phase 1 の記録によれば、開発環境は WSL 上の Linux で、Windows 側のバイナリとの
相互運用に制約があります。以下に注意してください。

- `setup.ps1` は WSL 上で直接検証できない可能性が高い。
  検証できなかった場合は、その旨を `AISTATE.md` に明記すること
- パス処理は `pathlib` に統一し、WSL / Windows の差異をコード内で分岐しない
- ジョブディレクトリの既定位置は `platformdirs` に委ねる

### テスト

以下はモデルなしでテストできます。重点的に書いてください。

- config_hash の算出（設定変更が正しいステージの再実行を引き起こすか）
- マニフェストの読み書き、破損時の扱い、バージョン不一致時の扱い
- ステージ依存関係の解決
- ロックの取得・解放、古いロックの検出
- 一括処理のファイル選別（`--include` / `--exclude`）
- 一括処理の集計と終了コード
- モデルカタログの解決ロジック

デバイス検出は環境依存なので、検出結果を注入できる形にしてテスト可能にしてください。
