## 背景 — 不具合 A-11

CUDA 機（GTX 1070 Ti）でのベンチマーク実行時、以下が観測されました。

```json
"target": {
  "backend": "faster-whisper",
  "device": "cpu",
  "compute_type": "auto"
}
```

**同じ実行のデバイス検出は `auto: ASR=faster-whisper/cuda:0/int8` と正しく判定していました。**
環境は CUDA を利用可能な状態でしたが、benchmark が cpu で実行しています。

### 症状の性質

- 環境側の問題**ではありません**
- **フォールバックでもありません**（最初から cpu を渡しています）
- `--variants` 経路がデバイス解決に接続されていない、という欠落と推定されます
- `--targets` 経路には `backend/device/model/quantization` の指定があるため、
  **片方の経路だけが取り残されている**可能性が高い

**ただし、これは症状からの推定です。実装を読んで原因を特定してください。**

### なぜ先に直すか

この状態でマトリクスを取得すると、**誤った auto 順序を確定させます。**
6c-2 の再測定より前に、確実に修正する必要があります。

## Step 1 — 原因の特定

`benchmark.py` と、そこから呼ばれるデバイス解決の経路を読み、
**cpu が渡る具体的な箇所を特定してください。**

### 確認すること

- `--variants` 経路でデバイスがどう決定されるか
- `--targets` 経路との違い
- デバイス検出（`auto` 判定）の結果が、benchmark へ渡っているか
- **既定値として `cpu` が埋め込まれている箇所がないか**
- ASR 以外（話者分離など）にも同じ欠落がないか

### 記録すること

- 原因と、該当するファイル・関数
- **`--variants` と `--targets` 以外に、デバイス指定を受け取る経路が存在するか**
- 影響範囲（どのバックエンド、どのデバイスが影響を受けるか）

**推定で修正に進まないでください。**原因を特定してから Step 2 へ進みます。

---

## Step 2 — 修正

### 方針

**すべての経路で、同一のデバイス解決を通すようにしてください。**

経路ごとに別々の解決処理を持たせないこと。
片方だけ直すと、今回と同じ形の欠落が再発します。

### 守るべき原則

- **明示指定されたデバイスは、そのまま使う**（フォールバックしない）
- **`auto` の場合のみ**、デバイス検出の結果に従う
- 指定されたデバイスが利用できない場合、**黙って別のデバイスへ切り替えない**
  明確なエラーで停止し、理由を示す

**Phase 5j で `registry.py` が `allow_fallback=True` を無条件に渡し、
「明示指定時はフォールバックしない」という原則が破られていた前例があります。**
今回の A-11 も、同じ「原則が一部の経路で守られていない」という類型です。

### 記録に残すこと

実行結果の JSON に、**デバイスがどう決定されたか**を記録してください。

- 明示指定によるものか、`auto` 判定によるものか
- `auto` の場合、何を根拠にそのデバイスを選んだか

**これは今回のような取り違えを、後から検出可能にするためです。**

---

## Step 3 — 回帰テスト（本作業の要）

**修正そのものより、テストのほうが重要です。**

このプロジェクトでは、**「原則そのものへの回帰テストが欠落する」**という失敗を
繰り返しています。A-11 も、`--targets` 経路にはデバイス指定があるのに
`--variants` 経路には無い、という非対称が検出されずに残った結果です。

### 必須のテスト

- **すべての指定経路で、指定したデバイスが実際に使われること**
  （経路ごとに個別のテストを書く。1経路だけのテストにしない）
- **`auto` 指定時、デバイス検出の結果が使われること**
- **明示指定したデバイスが、別のデバイスへ置き換わらないこと**
- **利用できないデバイスを明示指定した場合、エラーで停止すること**
- 結果 JSON に、記録された `device` が実際の実行デバイスと一致すること

### 設計上の要求

**新しい経路を追加したときに、テストが自動的に不足を検出する形が望ましい。**

経路の一覧を定義し、そこから網羅的にテストを生成する構造にできないかを検討してください。
できない場合、その理由を記録してください。

**モデルを必要としないテストとして書いてください。**
デバイス解決の検証に、実際の推論は不要なはずです。

## Step 4 — 既存測定値の汚染判定

**これは修正と同等に重要です。**

A-11 の影響で、**過去の測定値のうちどれが無効かを判定する必要があります。**

### 判定対象

| 出典 | 該当値 |
|---|---|
| `変更履歴.md` 0.1.18 | faster-whisper CPU 98、whisper.cpp CPU 106、他 |
| `AISTATE.md` Phase 6a の測定 | 全構成 |
| `AISTATE.md` Phase 6b の測定 | GenAI の CPU/GPU/NPU |
| CUDA 機での測定 | faster-whisper（cpu と記録されている） |

### 判定の方法

**結果 JSON に記録された `device` を確認してください。**
`"device": "cpu"` と記録されているのに CPU 以外を意図していたものが、汚染された値です。

- **意図して CPU を測ったもの**と、**A-11 により CPU になったもの**を区別する
- 区別できない場合、**「判定不能」として記録する**（推測で有効と判断しない）

### 注意

**Intel 機の値も無条件に有効とはみなさないでください。**

Intel 機では faster-whisper を主対象にしていなかったため表面化していませんが、
同じ経路を使う以上、同様の影響を受けている可能性があります。

### 記録すること

`AISTATE.md` に、以下を表形式で記録してください。

- どの測定値が有効か
- どれが無効（A-11 の影響を受けた）か
- どれが判定不能か
- **無効・判定不能な値は、6c-3 の auto 判断に使わない**旨

## Step 5 — 6c-2 への申し送り（記録のみ・実装しない）

**6c-2 で解決すべき課題を `AISTATE.md` へ記録してください。本作業では対応しません。**

### 課題1: 単語 timestamp 設定が揃っていない

`変更履歴.md` 0.1.18 の測定は**単語 timestamp なし**、
0.1.19 の GenAI 測定は**単語 timestamp あり**で行われています。

Phase 6b の J ライン（timestamp なし）と実装後（timestamp あり）の比較から、
timestamp のコストは **CPU 約12%、GPU 約4%** と推定されます。

**実運用では話者分離のため timestamp が必須であるため、
6c-2 は timestamp ありで統一することを想定しています。**

### 課題2: Phase 6a の基準値が2系統存在する

同じ Phase 6a の値として、異なる数値が流通しています。

| 出典 | 180秒 vulkan | 180秒 ovvk |
|---|---:|---:|
| `docs/utteran_Phase6b_指示書.md` | 1149 | 827 |
| `変更履歴.md` 0.1.18 | 777 | 712 |

**素材・量子化・timestamp 設定のいずれかが異なるはずですが、文書から判別できません。**
6c-2 で、どちらが何の条件下の値かを特定するか、両方を破棄して測り直すかを決めます。

**本作業で判別可能であれば、記録してください。**（調査は任意）

### 課題3: 量子化を揃えられない

- whisper.cpp / vulkan は GGML 形式
- whisper.cpp / openvino・ovvk は OpenVINO IR
- GenAI は OpenVINO IR の **int8**

**GenAI 用の公開モデルは int8 のみで、f16 版は自前変換が必要です。**

**揃えることを断念し、代わりに CER を必ず併記する方針とします。**
速度と精度をセットで見ることで、量子化の違いを構成の特性として扱います。

### 課題4: CER に差が出る fixture が必要

現在の CER fixture（25.825秒の合成音声）は、**全構成で 0.0%** です。
差が出ない指標は判断材料になりません。

6c-2 では、長尺・複数話者・専門用語などを含む fixture の用意が必要です。

### 課題5: 長尺測定の所要時間

6c-2 では 180 / 900 / 3600 / 10363秒を測定します。

10363秒（約2時間53分）を GenAI CPU（スコア約350）で処理すると約50分です。
**全構成を1回ずつ回すだけで数時間から半日規模になります。**

**Phase 6a の schema v3 逐次保存を使い、中断しても途中結果が残る形を前提とします。**

## 不明点があった場合

1. `要件定義.md` と既存実装を優先する
2. 判断できない場合、**安全側に倒し、記録する**
