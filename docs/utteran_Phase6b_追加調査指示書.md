## 背景 — なぜ切り分けが必要か

報告された「日本語130文字が全体で1語」という症状は、
**モデルの能力ではなく、単語分割の実装に起因する可能性があります。**

Whisper の単語タイムスタンプは2段構成です。

1. cross-attention の DTW で**トークン単位**の時刻を得る
2. そのトークンを**単語へマージ**する

本家 openai/whisper は 2 のマージに2つの経路を持ちます。
スペースで区切られる言語ではスペース分割を使い、
**日本語・中国語・タイ語などスペースを持たない言語では Unicode 境界で分割する経路**を使います。

**OpenVINO GenAI がスペース分割の経路しか実装していない場合、
日本語の発話全体が1語へ融合します。今回の症状と一致します。**

この仮説が正しければ、**トークン単位の時刻は内部に存在している**ことになります。
utteran は既に SudachiPy による形態素境界スナップを持っているため、
**トークン時刻さえ取得できれば、単語境界は自前で構成できます。**

その場合、判定は C ではなく A または B へ変わります。

**したがって、J-1 が本調査の中心です。**

## 調査項目

### J-1 — トークン単位の時刻を取得できるか（最重要）

**utteran が必要とするもの**を先に明確にします。

`align.py` は**単語の中心時刻**で話者を割り当てます。
必要なのは「日本語として正しい単語区切り」ではなく、
**テキストの部分文字列と時刻の対応**です。区切りは SudachiPy で作り直せます。

したがって、**以下のいずれかが取得できれば足ります。**

- トークン単位の時刻（トークンと文字列の対応がつくこと）
- 文字単位の時刻
- 十分に細かい chunk 単位の時刻（**目安として1チャンクあたり10文字未満**）

**確認すること**

- `WhisperPipeline` の戻り値オブジェクトの**実際の構造を出力して確認する**
  （ドキュメントの記述だけで判断しない。`dir()`、フィールドの列挙、実値のダンプ）
- `WhisperGenerationConfig` に、時刻の粒度を制御する設定があるか
  （`return_timestamps` の他に、トークン粒度・chunk 粒度の指定が存在しないか）
- **より低レベルの API 経路が存在しないか**
  デコード結果のトークン列と、それに対応する時刻を個別に取得できないか
- 取得できた場合、**その時刻が単調増加しているか**、音声と対応しているか

**報告に含めること**

- 取得可否
- 取得できる場合、その粒度（1要素あたりの平均文字数）
- 取得できる場合、**トークンと文字列の対応がつくか**
  （つかない場合、時刻があっても `align.py` では使えません）
- 取得できない場合、**何を試して取得できなかったか**を具体的に

**推測で「取得できない」と結論しないでください。**
API ドキュメントに記載がないことと、実装上取得できないことは別です。

### J-2 — 英語音声で単語分割が機能するか

**J-1 の仮説（スペース分割しか実装されていない）を裏取りします。**

- **同一のコード**で、英語音声を処理する
- 単語が正しく分割されるか
- 分割される場合、1語あたりの平均文字数

**判断への影響**

| 結果 | 意味 |
|---|---|
| 英語は分割される / 日本語は1語 | **実装の言語対応の問題**。将来の版で解決する可能性がある |
| 英語も1語になる | 単語時刻の実装そのものが機能していない。より根本的 |

**使用する音声**

`input/` の実データを使わないでください。
Phase 6a のベンチマーク素材、または合成音声を使用します。
英語素材がない場合、**その旨を記録し、合成で用意してください。**

### J-3 — 実時間比の測定

**Step 0 の報告には、対象音声の長さが記載されていませんでした。**

CPU 6.28秒 / GPU 3.95秒 / NPU 4.60秒という数値は、
音声長が不明なため**実時間比を算出できず、他バックエンドと比較できません。**

**確認すること**

- **Step 0 で使用した音声の長さを明記する**
- Phase 6a のベンチマーク素材で、**180秒と900秒**を最低限測定する
  （10363秒までは本調査では不要。判定が A/B になった時点で Step 4 が行う）
- **デバイス（CPU / GPU / NPU）ごとに測定する**
- **モデルのロード時間と推論時間を分けて記録する**
  （NPU はロードが支配的なため、合算すると実態を見誤ります）

**スコアの定義**

Phase 6a と同じく **スコア = 実時間比 × 100** です。
既存の測定基盤があるなら、そちらを使ってください。

**比較対象（Intel 機・Phase 6a 実測）**

| 構成 | 180秒 | 900秒 |
|---|---:|---:|
| whisper.cpp / openvino_vulkan | 827 | **1733** |
| whisper.cpp / vulkan | **1149** | 1594 |
| whisper.cpp / openvino | 624 | 988 |

### J-4 — NPU の初回ロード 277秒はキャッシュされるか

**277秒は、そのままでは実用外です。**
ただし OpenVINO にはコンパイル結果のキャッシュ機構があり、
2回目以降が短縮されるなら許容できます。

**NPU は他のバックエンドが使えない領域**であるため、
ここが解決するかどうかは 6b の価値を左右します。

**確認すること**

- `CACHE_DIR` 相当の設定を適用し、**1回目 / 2回目 / 3回目のロード時間**を測定する
- キャッシュの**保存先とサイズ**
- **キャッシュの保存先を utteran の管理下に置けるか**
  （「利用者の環境を汚さない」という設計方針があります。
  ユーザープロファイル直下や既定の一時領域へ勝手に置く実装であれば、その旨を記録）
- ドライバ更新やモデル変更でキャッシュが無効化される条件が分かれば記録する
