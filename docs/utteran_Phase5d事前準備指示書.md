## 作業 A — cp932 関連 flaky の調査

### 背景

Phase 5c の報告に以下があります。

> pytest 279 passed（既知のcp932関連flaky 1件のみ、無関係）

**この領域は過去に実害を出しています。**

Phase 4a で、`sys.stdout` の既定が cp932 になることにより、
コンソール非接続時（パイプ経由）に `devices --json` の日本語出力が破損する
不具合が見つかりました。場合によっては不正な JSON になり、
**GUI が CLI を呼び出す構成では致命的**でした。

Phase 5c の環境ではまた別の要因かもしれませんが、
**「無関係」と断定する根拠が示されていません。**

### 実施内容

1. **どのテストが、どういう条件で失敗するかを特定する**
   - テスト名、失敗するアサーション、エラーの内容
   - 失敗する条件（実行順序、並列度、環境変数、コンソールの有無など）
   - 再現率（何回中何回失敗するか）
2. **原因を特定する**
   - テスト側の問題か、製品コードの問題か
   - Phase 4a で修正した UTF-8 固定が及んでいない経路がないか
3. **判定する**

| 判定 | 対応 |
|---|---|
| 製品コードの問題 | 修正する。回帰テストを追加する |
| テスト側の問題 | テストを修正する |
| 環境依存で製品に影響しない | **その根拠を明示して記録する。** flaky のまま放置しない |

**「flaky なので無視」で終わらせないでください。**
不安定なテストは、本物の不具合を隠します。

### 確認すべき経路

Phase 5c で GUI と CLI のやり取りが増えています。以下を重点的に確認してください。

- `--progress-json` の出力（JSON Lines、UTF-8）
- `setup.ps1` のステージマーカーの出力とパース
- `jobs list --json` / `jobs show --json` / `devices --json`
- ウィザードが `setup.ps1` の出力を読む経路
- 日本語を含むパス、モデル名、エラーメッセージ

**これらのいずれかが、コンソール非接続時に破損しないことを確認してください。**

### CI との関係

Phase 4a で CI に BOM 検証と UTF-8 の検査を入れています。
**CI がこの問題を検出できるかを確認**し、できないなら検査の追加を検討してください。

## 作業 B — クリーン環境での初回フロー検証

### 背景

Phase 5c の未検証項目は以下です。

- `cuda` プロファイル（本機に NVIDIA GPU がないため検証不能）
- **真に空の `.venvs` からの初回起動フロー全体**

**後者は 5d にとって重大です。**インストーラーは「何も無い環境に導入する」ものなので、
初回フローが通らなければインストーラーの意味がありません。

5d の作業中にここで詰まると、インストーラーの問題なのか初回フローの問題なのか、
切り分けが困難になります。**先に切り離して検証します。**

### 検証環境の作り方

**既存の作業環境を壊さないでください。**

以下を検討し、方針を決めてください。

| 方法 | 長所 | 短所 |
|---|---|---|
| 別ディレクトリへ clone | 手軽 | uv やモデルキャッシュは共有される |
| 環境変数で参照先を分離 | 既存を保護できる | 分離が不完全な可能性 |
| 別のユーザーアカウント | 分離が確実 | 準備が煩雑 |
| 仮想マシン | 最も確実 | 準備コストが高い |

**重要な観点**: 以下がユーザー領域に共有されているため、
単に clone しただけでは「まっさら」になりません。

- uv 本体
- モデルキャッシュ（`platformdirs` 配下）
- ffmpeg（アプリケーションデータ配下）
- GUI 設定（`platformdirs` 配下）
- ジョブディレクトリ
- メモリキャリブレーションのデータ

**これらをどう扱うかを決め、記録してください。**
環境変数（`UTTERAN_MODEL_DIR` など）で分離できるものは分離し、
できないものは「共有された状態での検証」として明記してください。

### 検証項目

**空の状態から、ウィザードだけで文字起こしができる状態に到達すること**が目的です。

1. **初回起動の判定**
   - venv が無い状態でウィザードが起動する
2. **ハードウェア検出と推奨**
   - 検出結果が表示される
   - 推奨プロファイルとその理由が表示される
   - **話者分離が GPU で動くかどうかが読み取れる**
   - プロファイル名を知らなくても選べる表現になっている
3. **uv の扱い**
   - 既に導入済みの場合、何もしないこと
   - **未導入からの導入は、可能なら検証する**
     （既存の uv を壊さない方法で。困難なら「未検証」として記録）
4. **venv の構築**
   - 進捗が表示され、無反応に見える時間がないこと
   - 何をしているかが具体的に分かること
   - 中断できること
   - 中断後に再開できること
5. **ffmpeg**
   - 検出または導入されること
   - GPLv3 の表示があること
6. **モデルの取得**
   - サイズと所要時間が事前に表示されること
   - 「後で」を選べること
7. **トークンの設定**
   - 利用条件への同意が必要である旨が示されること
   - 無効なトークンと未同意が区別されること
8. **完了確認**
   - **実際に文字起こしが動作すること**
   - 失敗時に原因と対処が示されること
9. **完了後**
   - 通常の画面へ遷移すること
   - 2回目の起動でウィザードが出ないこと

### 記録すること

- 各項目の合否
- 実施した検証環境の構成（何を分離し、何を共有したか）
- 所要時間（利用者が待つ時間の実測）
- 詰まった箇所、分かりにくかった箇所
- **実機で検証できなかった項目と、その理由**

**利用者体験の観点で気づいたことも記録してください。**
「動くが分かりにくい」は、5d でインストーラーにする前に直すべき問題です。

### 検証後の後始末

- 検証用に作成した環境を削除する
- 既存の環境が変更されていないことを確認する
  （venv、モデル、設定、ジョブ）
- 削除・確認の手順を記録する

## 発見した問題への対応

### 修正する場合

1. 再現手順を特定する
2. **修正前に、失敗する回帰テストを追加する**
3. 修正する
4. 回帰テストが通ることを確認する
5. 該当文書を更新する

### 修正しない場合

以下は記録のみとしてください。

- `cuda` プロファイルに関するもの（ハードウェア不在）
- 5d で扱うべきもの（インストーラーの構成に関わるもの）
- 影響範囲が大きく、5d の前に入れるべきでないもの

判断に迷う場合は**修正せず記録**を選んでください。

## 実装上の注意

### 機密データ

- 実データを検証に使わない（合成音声を使うこと）
- 文字起こしの内容を記録しない
- `.env` を読み取らない
- **スクリーンショットを撮る場合、他のウィンドウが写り込まないよう注意する**

### 破壊的変更への配慮

- **既存の venv、uv、モデル、ffmpeg、設定、ジョブを壊さない**
- 検証用の環境は明確に分離し、後始末する
- Phase 5a・5b・5c の機能を壊さない

### コミット

- ブランチ `chore/phase5d-preparation`
- 作業単位でコミットする
- `git push` は実行しない
- 実データ、スクリーンショットをコミットしない

---

## 禁止事項

- flaky を「無関係」で片付け、根拠を示さないこと
- 既存の環境を壊す検証を行うこと
- 検証環境の後始末を怠ること
- 実データを検証に使うこと
- 実機未検証の項目を「検証済み」と報告すること
- 利用者体験上の問題に気づきながら記録しないこと

---

## 不明点があった場合

1. `要件定義.md` と Phase 5c の記録を優先する
2. 検証環境の構成は判断してよい。判断と理由を記録する
3. 判断できない場合、安全側（既存を壊さない側）に倒し、記録する
