# utteran — Phase 4a 追加指示（照合走査と履歴のクリーンアップ）

## あなたへの依頼

公開履歴監査の結果を受けて、以下を実施してください。

1. **検出済みの候補が、実際に機密情報かどうかを照合により判定する**
2. 判定結果に応じて、**履歴のクリーンアップを実施する**

作業ブランチは `chore/phase4a-public-readiness` を継続して使用します。

---

## 背景

`docs/Phase4a公開履歴監査.md`（または相当の報告書）により、以下が確認されています。

**問題なしと確認されたもの**

- メディアファイル、`.env`、文字起こし成果物が Git のパスとして登録された形跡なし
- 公開 ref 内の秘密値候補 0 件
- GitHub 側（Issues、PR、Actions ログ、Releases、Wiki、Discussions）すべて 0 件

**判定が保留されているもの**

- メールアドレス形式: コミットメッセージ 10 件、過去差分 7 件
- ユーザー固有の絶対パス候補: 2 件（履歴に残存）＋ 到達不能 blob に 2 件

報告書は「公開連絡先やテスト値かどうかで除外していない」と明記しており、
**機械的に抽出しただけで危険性の判定はされていません。**

### 走査されていない対象

当初の懸念は「入力ファイル名がドキュメントやログに記録されること」でした。
そのファイル名には**メールアドレスと日本語の組織名の両方**が含まれます。

現在の検出器はメールアドレス形式を拾いますが、
**組織名だけが書かれた箇所や、ファイル名そのものの文字列は検出できません。**

---

## Step 1 — 照合走査

### 方針

検出された値を表示せずに判定するため、**照合方式**を使います。

機密文字列のリストを外部から与え、検出値と突き合わせて
**「一致の有無」だけを真偽値で報告**します。

### 実装上の必須要件

**走査スクリプトとリポジトリ内のどのファイルにも、機密文字列をハードコードしないこと。**

スクリプトはコミット対象です。そこに機密文字列を書けば、
それ自体が新たな漏洩になります。

- 照合パターンは**外部ファイルから読み込む**（引数でパスを指定する）
- パターンファイルは `.gitignore` 対象の場所に置く（`output/` 配下など）
- パターンファイルの作成方法を README に記載する（内容は書かない）
- 可能ならパターンをハッシュ化して比較し、平文をメモリ上に長く保持しない

### 照合対象

パターンファイルには以下を含めます。**作成はあなたが行って構いませんが、
内容を報告書やコミットに書かないこと。**

| 分類 | 取得元 |
|---|---|
| 組織ドメイン | `input/` のファイル名から導出 |
| メールのローカル部 | 同上 |
| 組織名（日本語） | 同上 |
| 入力ファイル名の全体および部分文字列 | 同上 |
| Windows のユーザー名 | 環境から取得 |

`input/` のファイル名は読み取って構いませんが、**その内容（音声そのもの）は開かないこと。**

### 走査範囲

前回と同じ範囲を対象とします。

- 全 ref、全コミット、全 Git オブジェクト（到達可能・到達不能の双方）
- コミットメッセージ
- 全差分
- 現在の追跡ファイル

### 報告

以下の形式で報告してください。**一致した値そのものは書かないこと。**

| 分類 | 一致 | 件数 | 位置 |
|---|---|---:|---|
| 組織ドメイン | あり／なし | | コミット、パス |
| メールのローカル部 | | | |
| 組織名 | | | |
| 入力ファイル名 | | | |
| ユーザー名 | | | |

---

## Step 2 — 判定と方針決定

### 一致が 0 件だった場合

- 検出済みのメール形式は、公開連絡先または開発ツールが付与するトレーラー、
  あるいはテスト用のダミー値と判断できます
- **その場合でも、ユーザー固有の絶対パス 2 件は除去する価値があります。**
  ユーザー名が実名を含む可能性があるためです
- Step 3 を実施するかは、この観点で判断してください

### 一致があった場合

- Step 3 を必ず実施してください
- 一致した分類と位置を明確に記録してください

## Step 3 — 履歴のクリーンアップ

**利用者から実施の承認を得ています。**ただし以下を厳守してください。

### 事前準備（必須）

1. **完全なバックアップを取る**
   - `git bundle create` で全 ref を含むバンドルを作成する
   - ミラークローンも別途作成する
   - **バックアップは `output/` 配下など Git 追跡外に置く**
   - バックアップから復元できることを確認してから次へ進む
2. 現在の全 ref とコミットハッシュの一覧を記録する
3. タグとリリースの対応を記録する
   （**リリースが 1 件存在します。**履歴書き換えでタグの SHA が変わります）

### 手法

`git filter-repo` を第一候補とします。

- 導入できない場合、`git filter-branch` を使う（非推奨だが可）
- いずれも困難な場合、**新規リポジトリへのクリーン移行**を代替案として提示する
  （利用者は「作り直しも許容」と述べています）

置換対象:

| 対象 | 手法 |
|---|---|
| コミットメッセージ内のメール形式 | メッセージのコールバックで除去または置換 |
| ファイル内容のユーザー絶対パス | テキスト置換 |
| Step 1 で一致した機密文字列 | テキスト置換 |

**置換ルールファイルにも機密文字列が含まれます。**
`.gitignore` 対象の場所に置き、作業後に削除してください。

置換後の文字列は、意味が通る一般化した表記にしてください
（`<user>`、`<workdir>` など）。

### 実施範囲

- 全ブランチ、全タグを対象とする
- **到達不能オブジェクトはローカルで GC する**
  （`git reflog expire --expire=now --all && git gc --prune=now --aggressive`）

### push は実施しない

**`git push` を実行しないでください。**

書き換え後の force push は利用者が実施します。以下を提示してください。

- 実行すべきコマンド（全ブランチ・全タグの force push）
- 実施後に必要な作業
  - 既存の clone は再取得が必要
  - **リリースとタグの整合確認**。タグの SHA が変わるため、
    リリースの再作成が必要になる可能性がある
  - **GitHub 側に残る到達不能オブジェクトは、force push だけでは消えない。**
    完全な削除には GitHub サポートへのキャッシュ削除依頼が必要になる場合がある
- 代替として、リポジトリを作り直す場合の手順

### 書き換え後の検証

1. **照合走査を再実行し、一致が 0 件になったことを確認する**
2. ワーキングツリーが書き換え前と同一内容であることを確認する
   （最新コミットの tree ハッシュ、またはファイル単位の比較）
3. `ruff check`、`mypy`、モデル不要テストが通ることを確認する
4. 受入試験ハーネスが引き続き合格することを確認する
5. `uv lock --check` が通ることを確認する

**書き換えによって内容が壊れていないことの確認を省略しないでください。**

## Step 4 — 再発防止

1. **照合走査を CI に組み込む**
   - ただしパターンファイルは公開できないため、**現在ツリーに対する
     汎用パターン（メール形式、絶対パス形式、メディア拡張子）の走査**を CI とする
   - 機密文字列との照合は、パターンファイルを持つ利用者がローカルで実行する形にする
   - この使い分けを README に記載する
2. **コミットメッセージのトレーラーの扱いを決める**
   - 検出されたメール形式が開発ツールの付与するトレーラーだった場合、
     今後付与するかを決め、コミット規約として記録する
3. `.gitignore` の穴を塞ぐ
   - **`output/` 以外に出力した場合、JSON・TXT・Markdown の文字起こし成果物が
     追跡候補になります。**現在 `*.srt` と `*.vtt` のみ除外されています
   - 出力先を制限するか、除外パターンを見直すかを判断する
   - `.gitignore` の実効性テスト（`git check-ignore` による検証）を追加する
   - 出力形式や対応拡張子が増えたときに検知できる形にする

## 禁止事項

- 走査スクリプトやコミット対象ファイルに機密文字列を書くこと
- 検出値そのものを報告書、ログ、コミットメッセージに記録すること
- バックアップを取らずに履歴を書き換えること
- `git push` を実行すること
- 書き換え後の内容検証を省略すること
- `input/` の音声そのものを開くこと
- `.env` を読み取ること

## 不明点があった場合

1. 判断できない場合、**安全側（何もしない側）に倒す**
2. 履歴書き換えの範囲に迷う場合、対象を狭めるほうを選ぶ
3. 判断と理由を `AISTATE.md` に記録する
4. 利用者の判断が必要な事項は、報告書の「利用者への確認事項」にまとめる
