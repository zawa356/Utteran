## 報告された症状

利用者が配布版のインストーラーで確認した挙動です。

```
セットアップウィザードを起動
  → トークンが必要というエラー
  → 設定画面でトークンを入力
  → ウィザードに戻る
  → 「トークンがありません」というエラーが再発
```

**設定画面で保存したはずのトークンが、参照されていません。**

あわせて、設定画面で複数の項目を操作すると、一部の変更が元に戻る症状も
報告されています。

---

## E-1 — トークンの保存・参照

### 原因の候補（調査して確認すること）

**`packaging/gui.spec` の hidden imports に `keyring` が含まれていません。**

```python
hidden_imports = (
    collect_submodules("uvicorn")
    + collect_submodules("webview")
    + collect_submodules("fastapi")
)
```

keyring はバックエンドを entry points 経由で**動的に検出**します。
PyInstaller は静的解析のため `keyring.backends.Windows` を収集せず、
exe 内では Windows Credential Manager のバックエンドが見つからない可能性が高いです。

その場合、以下のいずれかが起きます。

- `import keyring` 自体が失敗する
- keyring は import できるが、利用可能なバックエンドがなく
  `keyring.backends.fail.Keyring` が選択され、保存時に例外が出る

**開発環境（`gui.ps1` 経由）では keyring が正常に動くため、
Phase 5c・5d の検証では発覚しませんでした。**

### 症状が表面化しなかった理由

`TokenStore._get_token` が例外を握りつぶしています。

```python
def _get_token(self) -> str | None:
    try:
        return self._keyring().get_password(self.SERVICE, self.USERNAME)
    except Exception:
        return None
```

**keyring が壊れていても「未設定」と区別できません。**
そのため利用者には「保存したのに認識されない」ようにしか見えません。

### 実施内容

**1. 配布版で実際に何が起きているかを確認する**

推測で修正しないでください。実際に exe を実行し、以下を確認してください。

- `import keyring` が成功するか
- 選択されているバックエンドは何か
- `set_password` が成功するか、例外が出るか
- 例外の型とメッセージ

配布版でこれを確認する手段（デバッグログ、診断機能など）を用意してください。

**2. `gui.spec` を修正する**

keyring とそのバックエンドを収集対象に加えてください。
`collect_submodules` だけで足りるか、entry points のメタデータも
必要かを確認してください（`copy_metadata` が要る場合があります）。

**3. keyring が利用できない場合の扱いを決める**

**exe 内で keyring が動かない環境が存在しうる**前提で設計してください。

| 状態 | 現在 | 期待 |
|---|---|---|
| 未設定 | 「未設定」 | 「未設定」 |
| keyring が利用不能 | **「未設定」（区別されない）** | **「保存先が利用できない」と明示** |

- **例外を握りつぶさず、状態を区別してください**
- keyring が利用できない場合、利用者に何が起きているかを伝える
- 代替手段（環境変数、`.env`）の案内を検討する

**4. GUI と CLI が同じ場所を参照していることを確認する**

`TokenStore` は `SERVICE = "utteran"` / `USERNAME = "huggingface"` を使っています。
CLI 側の実装と一致しているかを確認してください。

さらに、**配布版では以下の点も確認が必要です。**

- GUI exe と、プロファイル venv の CLI が、同じ資格情報にアクセスできるか
- CLI 側のトークン優先順位（環境変数 > `.env` > キーリング）が、
  配布版で意図どおり働くか
  （**リポジトリがない配布版では `.env` が存在しません。**
  この前提で問題が出ないかを確認すること）

**5. 回帰テストを追加する**

- keyring が利用不能な状態を注入し、状態が区別されることを確認する
- **`gui.spec` の hidden imports に keyring が含まれることを検証するテスト**
  （同じ抜けが再発しないようにする）

`gui.spec` には既に「推論コアが混入していないか」を検証する仕組みがあります。
**必要なモジュールが含まれているかの検証も、同様に自動化してください。**

## E-2 — 設定の巻き戻り

### 原因の候補

`PUT /api/settings` は設定オブジェクト**全体**を受け取って置き換えます。

```python
@app.put("/api/settings")
def put_settings(payload: SettingsPayload) -> dict[str, object]:
    saved = selected_settings.save(GuiSettings.from_dict(payload.model_dump()))
```

フロントが項目ごとに個別に PUT し、それぞれが
「変更した項目＋画面が保持する他項目の値」を送っている場合、
**後の PUT が前の変更を上書きします。**

### 実施内容

1. **フロントの送信タイミングと内容を確認する**
   - どの操作で PUT が走るか
   - 送信されるペイロードに、変更していない項目が含まれるか
   - 複数の PUT が並行するか
2. **原因を特定してから修正する**

修正の方向としては、以下が考えられます。判断してください。

| 案 | 内容 |
|---|---|
| 部分更新 | 変更した項目のみを送る（PATCH 相当） |
| 送信の集約 | 画面の状態を集約し、保存操作を明示的にする |
| 応答での同期 | PUT の応答で画面の状態を更新し、ずれを防ぐ |

**トークンの保存が設定の保存と別経路である点にも注意してください。**
`PUT /api/token` と `PUT /api/settings` が別々に走ることで、
片方が他方を巻き戻していないかを確認すること。

3. **複数項目を連続・同時に操作する回帰テストを追加する**

## E-3 — ウィザード内でのトークン入力

### 背景

現在、ウィザードでトークンが必要になると「設定画面で保存してください」と案内し、
利用者を別画面へ飛ばしています。

**ウィザードは初回導入の流れです。**途中で別画面へ移動させるのは
体験として良くありません。E-1 の不具合と組み合わさって、
「設定で入れたのにウィザードで認識されない」という混乱を生みました。

### 実施内容

**ウィザードのステップ内で、トークンを入力・保存できるようにしてください。**

要件:

- トークンの取得手順を案内する
  （Hugging Face のアカウント作成、**モデル利用条件への同意**、
  トークンの発行。それぞれのリンクを示す）
- **入力欄はマスク表示**とし、保存済みの値を表示しない
- 保存後、**実際に取得できるかを確認する**
- **トークン無効と利用条件未同意を区別**してエラーを出す
  （Phase 1 で実装済みの分類を使う）
- 「後で行う」を選べる（話者分離を使わない利用者のため）
- 保存に失敗した場合（keyring が利用不能など）、原因と対処を示す

**設定画面のトークン入力も残してください。**後から変更する経路が必要です。
ただし**実装を共通化**し、片方だけ直る状態を作らないこと。

## E-4 — テーマのシステム追従

### 要件

現在はダーク／ライトの2択で、既定はダークです。これを3択にします。

| 値 | 挙動 |
|---|---|
| `system` | **OS の設定に追従（新しい既定）** |
| `light` | 常にライト |
| `dark` | 常にダーク |

### 実装上の注意

- **`prefers-color-scheme` メディアクエリで実現できるかを確認してください**
  pywebview のウィンドウ内で、OS のテーマ設定が正しく伝わるかは
  環境依存の可能性があります
- **OS の設定を実行中に変更した場合、追従するか**を確認する
  （再起動が必要でも構いませんが、その旨を記録してください）
- Windows のタイトルバーやウィンドウ枠の扱い
  （pywebview 側の設定が必要かを確認する）
- 既存の利用者の設定を壊さないこと
  （`dark` を明示的に選んでいた人が `system` に変わらないようにする）

### 既定値の変更

**既定を `system` に変えると、既存の設定ファイルとの整合が問題になります。**

- 設定ファイルにテーマの記録がない場合は `system`
- 記録がある場合はそれを尊重する
- 移行の扱いを決め、記録してください

CSS 変数によるテーマ管理は Phase 5a で実装済みです。
**色をコンポーネントに直書きしないという原則を維持してください。**

## 実装上の注意

### 機密データ

- **トークンをログ、API レスポンス、画面に出さない**
- デバッグのために一時的に出力する場合、**必ず削除してからコミットする**
- 実データを検証に使わない
- スクリーンショットに他のウィンドウが写り込まないよう注意する

### 破壊的変更への配慮

- 既存の venv、モデル、設定、ジョブを壊さない
- 既存利用者のテーマ設定を勝手に変えない
- Phase 5a〜5d の機能を壊さない
- CLI 側のトークン優先順位を変えない

### コミット

- ブランチ `fix/phase5e-gui-settings`
- 項目単位でコミットする
- `git push` は実行しない
- ビルド成果物をコミットしない
- **デバッグ用の出力を残さない**

## 禁止事項

- 配布版で確認せずに E-1 を「修正した」と報告すること
- 原因を特定せずに修正から入ること
- keyring の例外を握りつぶしたままにすること
- トークンをログや画面に出すこと
- ウィザードと設定画面でトークン入力を二重実装すること
- 既存利用者の設定を勝手に変更すること
- `要件定義.md` を更新せずに仕様を変えること
