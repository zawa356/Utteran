# utteran — Phase 5k 実装指示（デバイス検出のハング対策）

## あなたへの依頼

**NVIDIA GPU を持たない PC で、デバイス検出が無限にハングする不具合**を修正してください。

作業ブランチは `fix/phase5k-device-probe-timeout` を新規作成して使用します。

---

## 判明した事実

### 症状

Intel Core i7-1165G7 / Iris Xe / NVIDIA なし の PC で、
`setup.ps1` が以下から進みません。**15分以上経過しても完了しません。**

```
==> Verifying profile 'intel'
==> Inspecting runtime devices (the first probe can take a while)
```

### 切り分け結果

該当 PC で、各プローブを単体実行した結果です。

| 呼び出し | 結果 |
|---|---|
| `openvino.Core().available_devices` | `['CPU', 'GPU']` **正常に返る** |
| `onnxruntime.get_available_providers()` | 正常に返る |
| **`torch.xpu.is_available()`** | **ハング。Ctrl+C でも復帰しない** |
| **`ctranslate2.get_cuda_device_count()`** | **ハング。Ctrl+C でも復帰しない** |

### 重要な点

**1. これは Intel 固有の問題ではありません。**

`ctranslate2.get_cuda_device_count()` は CUDA デバイス数を数えるだけの呼び出しで、
XPU とは無関係です。**NVIDIA GPU が存在しない環境**で、
`nvcuda.dll` の解決を試みてドライバ層でブロックしていると考えられます。

`ctranslate2` は faster-whisper の実行基盤であり、**`cpu` プロファイルにも含まれます。**

**したがって、NVIDIA GPU を持たない一般的な PC すべてで、
同じ場所で固まる可能性があります。**

**2. Ctrl+C で復帰しません。**

Python の例外処理では抜けられない、**ネイティブ層でのブロック**です。
スレッドを分けても、そのスレッドを終了させることはできません。

**3. 開発機では再現しません。**

これまでの検証は NVIDIA GPU 搭載機と Intel Arc 搭載機で行われており、
どちらもハングの条件を満たしませんでした。

## J-0 — プローブの分離とタイムアウト（最優先）

### 設計

**デバイスプローブを別プロセスで実行し、タイムアウトで打ち切ってください。**

同一プロセス内で呼ぶ限り、ネイティブ層のハングからは復帰できません。
**プロセスを分けて、応答がなければ強制終了する**のが唯一の確実な方法です。

対象は、ネイティブライブラリを呼ぶすべてのプローブです。

| プローブ | 呼び出し |
|---|---|
| CTranslate2 | `get_cuda_device_count()`、`get_supported_compute_types()` |
| PyTorch CUDA | `torch.cuda.*` |
| PyTorch XPU | `torch.xpu.*` |
| OpenVINO | `Core().available_devices` |
| ONNX Runtime | `get_available_providers()` |
| Vulkan | 外部プロセスを起動している場合はそれも |

**「今は動いているから対象外」としないでください。**
環境が変われば、どれもハングしえます。

### 要件

- **プローブごとにタイムアウトを設ける**（既定値を決め、根拠を記録する）
- タイムアウトしたら、そのプロセスを**確実に終了させる**
  （プロセスツリーごと。Phase 2 の受入試験で解決した手法を使うこと）
- 他のプローブは継続する。1つのハングで全体を止めない
- **タイムアウトを「判定不能」として扱い、「利用可能」と誤認しない**
- タイムアウトした事実を、**構造化ログに記録する**
  （Phase 5j で整備したログ基盤を使うこと）
- タイムアウト値を設定で変更できるようにする

### 進捗表示

**現在は「Inspecting runtime devices」の一行だけで、何を実行中か分かりません。**

- 実行中のプローブ名を表示する
- 完了したものと残りが分かる
- タイムアウトしたら、その旨を表示して次へ進む

`setup.ps1` と GUI の両方に反映してください。

### 結果のキャッシュ

**毎回プローブを実行するのは現実的ではありません。**
特にタイムアウト待ちが発生する環境では、起動のたびに数十秒かかります。

- プローブ結果をキャッシュする
- **ハードウェア構成やドライバが変わった場合に無効化する**
  （何をキーにするかを判断し、記録すること）
- 明示的に再取得する手段を用意する（`devices --refresh` など）
- キャッシュの保存場所を決める

**キャッシュにより、ハングした環境が「毎回固まる」状態を避けられます。**

## K-1 — プロファイル推奨の見直し

### 問題

該当 PC は Intel Iris Xe を搭載していますが、以下の状態です。

- **OpenVINO は動作する**（`['CPU', 'GPU']` を返す）→ ASR は高速化できる
- **torch XPU はハングする** → 話者分離は XPU で動かない

現在の推奨ロジックは、GPU ベンダーが Intel であれば `intel` プロファイルを
推奨します。**しかしこの環境では、`intel` プロファイルの利点の半分しか得られません。**

### 実施内容

1. **推奨ロジックを、ベンダー判定から実際の利用可否判定へ改める**
   - OpenVINO が使えるか
   - torch XPU が使えるか
   - **両者を独立して判定する**
2. **推奨の提示に、何が使えて何が使えないかを含める**
   - 「ASR は GPU で高速化できます。話者分離は CPU 実行になります」のように
   - Phase 5c で定めた「利用者にとっての意味を提示する」方針に沿うこと
3. **判定不能な項目がある場合、それを伝える**
   - 「XPU の判定ができませんでした」と正直に示す
   - 「使えない」と断定しない

### Iris Xe と Arc の違い

`torch.xpu` は Intel GPU 向けですが、**Iris Xe（Gen12）と Arc（Xe-HPG）では
対応状況が異なります。**

- Iris Xe で XPU が使えるのか、ランタイムを追加すれば使えるのかを調査する
- 使えないなら、その旨を推奨に反映する
- 使えるようにする手段があるなら、案内する
- **調査結果を記録する**（推測で結論を出さないこと）

## K-2 — `cpu` プロファイルでの確認

**`ctranslate2` は `cpu` プロファイルにも含まれます。**

該当 PC で `cpu` プロファイルでも同じ場所で固まるかを確認してください。

```powershell
$env:UV_PROJECT_ENVIRONMENT = ".venvs\win-cpu"
uv run --no-sync python -c "import ctranslate2; print(ctranslate2.get_cuda_device_count())"
```

**固まる場合、全プロファイル共通の不具合として扱ってください。**
「Intel 環境の問題」ではなく「NVIDIA を持たない環境の問題」になります。

その場合、**README に既知の問題として記載**するか、
修正で完全に解消するかを判断してください。

## K-3 — CTranslate2 のハング原因

**なぜ NVIDIA なしの環境でハングするのかを調査してください。**

タイムアウトで回避はできますが、原因が分かれば別の対処があるかもしれません。

- CTranslate2 のバージョンによる差
- `nvcuda.dll` の探索経路
- 環境変数（`CUDA_VISIBLE_DEVICES` など）で回避できるか
- 呼び出し順序（`get_supported_compute_types` を先に呼ぶなど）で変わるか

**回避策が見つかっても、タイムアウトの実装は省略しないでください。**
別の環境で別のハングが起きる可能性があります。

## テスト

- プローブのタイムアウト（ハングするプローブを注入すること）
- タイムアウト後のプロセス終了
- 1つがタイムアウトしても他が継続すること
- **タイムアウトが「利用可能」と判定されないこと**
- キャッシュの保存、読み込み、無効化
- 推奨ロジック（OpenVINO 可・XPU 不可の組み合わせを含む）

**「判定不能を利用可能と誤認しない」ことを、必ずテストで守ってください。**
誤認すると、使えないデバイスが選択され、実行時に失敗します。

## 実装上の注意

### 破壊的変更への配慮

- 既存の venv、モデル、設定、ジョブを壊さない
- Phase 5a〜5j の機能を壊さない
- **Phase 5j で整備したログ基盤を活用すること**
  （新たなログ機構を作らない）

### 機密データ

- プローブ結果やキャッシュに、個人を特定する情報を含めない
- 実データを検証に使わない

### コミット

- ブランチ `fix/phase5k-device-probe-timeout`
- 項目単位でコミットする
- `git push` は実行しない

---

## 禁止事項

- ネイティブ呼び出しを同一プロセス内のままにすること
- タイムアウトを「利用可能」として扱うこと
- タイムアウト後にプロセスを残すこと
- 該当 PC で確認せずに完了と報告すること
- 開発機だけで検証を済ませること
- `要件定義.md` を更新せずに仕様を変えること

1. `要件定義.md` と既存実装の方針を優先する
