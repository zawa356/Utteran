## 背景

R-1 の対策別測定で、以下が判明しました。

| 条件 | 処理時間 | セグメント | 最大連続反復 |
|---|---:|---:|---:|
| C0 対策なし | 289.9秒 | 571 | 150 |
| C6 既定の組み合わせ | 86.5秒 | 280 | 2 |

**ハルシネーションは品質だけでなく処理時間も大きく損なっていました。**
C6 は C0 の約 3.35 倍高速です。

**このため、これまでに測定した whisper.cpp の性能値はすべて対策前のものであり、
実力を過小評価しています。** auto の構成順序も、対策前の測定値
（Vulkan 20.488秒 vs ovvk 32.564秒）に基づいて決定されています。

対策の効き方が構成によって異なる可能性があるため、**順位が変わる可能性があります。**
再測定して確認します。

## Step 1 — R-7: 対策適用後の性能再測定

### 計測に関する注意

**この Step は長時間の計測を含みます。**

- 計測中は他の重い処理を実行しないこと
- 計測の開始時刻と終了時刻を記録すること
- 異常値が出た場合は記録のうえ再測定すること

利用者には「計測中は端末を空けておく」よう事前に伝えてあります。

### 1-A. 前提の確認

測定前に、以下を確認してください。

- R-1 で決定した既定値（`no_context = true`、decoder 閾値）が適用されていること
- 反復抑制ロジックが**有効**な状態であること（利用者の実使用条件で測定するため）
- VAD は既定 opt-in のため**無効**の状態で測定すること
  （VAD 有効時の測定は別条件として追加する）

### 1-B. 構成別の再測定

`utteran benchmark` を使用してください。R-3 で実装済みの機能を使うことで、
測定手順が再現可能になります。

測定条件:

- 素材: 180秒の fixture（受入試験と同一のもの。実データの内容は記録しない）
- モデル: large-v3-turbo-q5_0
- ウォームアップ 1 回 + 計測 3 回、中央値を採用
- 対象: whisper.cpp の 4 構成 + faster-whisper
- 単語タイムスタンプあり / なしの両方

| 構成 | TSあり | TSなし |
|---|---|---|
| whisper.cpp / cpu | | |
| whisper.cpp / openvino | | |
| whisper.cpp / vulkan | | |
| whisper.cpp / openvino_vulkan | | |
| faster-whisper / cpu | | |

さらに、以下も測定してください。

- **VAD 有効時**の Vulkan 構成（VAD が処理時間に与える影響の確認）
- 24分46秒の実ファイルでの Vulkan と ovvk の 1 点測定
  （短い fixture と長い音声で傾向が変わらないかの確認）

### 1-C. auto 順序の再判定

1. 再測定の結果、Vulkan と ovvk の優劣が変わっていないかを確認する
2. 変わっている場合、auto の順序を実測に基づいて再決定する
3. **有意差がない場合は、IR 変換が不要な Vulkan を上位に維持する**
   （利用者の手間が少ないほうを既定にする方針を継続）
4. 決定と根拠を `要件定義.md` と `AISTATE.md` に記録する
5. 順序を変更する場合、`devices` の auto 表示と理由の文言も追従させる

### 1-D. 文書の更新

**README の性能表を、対策後の値に差し替えてください。**

- 対策前の測定値をそのまま残すと、利用者が誤った期待を持ちます
- 対策前後の比較を載せる場合、どちらが現在の実力かを明示すること
- 測定条件（モデル、量子化、音声長、測定方法、対策の適用状態）を必ず併記すること
- 受入試験報告に記載された対策前の性能値については、
  「対策前の測定値であり現在は改善している」旨の注記を追加する

## Step 2 — R-4: 受入試験ハーネスの統合（完遂）

### 現状

`AISTATE.md` によれば、以下まで完了しています。

- G 系 118 ケースと Phase 3 の P14 系 3 ケースを単一の `cases.json` へ統合
- UTF-8 読み取り、グループ指定、耐久グループの既定除外、README

**未完了**: P0〜P13 / P15 / P16 が宣言的ケースへ未移植。統合ハーネス全件の実行も未完了。

### 設計方針

**このハーネスは、単なるテスト実行器ではなく、将来 GUI が環境を自動判断するための
基盤になります。** その前提で設計してください。

ただし**スコープを膨らませすぎないこと。** GUI そのものを作るのではなく、
「後から GUI が利用できる形」を満たせば十分です。具体的には以下です。

**1. ケース定義にメタ情報を持たせる**

各ケースに以下を持たせてください。

| 項目 | 内容 |
|---|---|
| `id` | 受入試験の番号を維持する（`P6-3` など）。追跡性のため |
| `group` | グループ識別子 |
| `requires` | 実行に必要な環境条件（プロファイル、バックエンド、モデル、ビルド構成、デバイス） |
| `destructive` | 環境を変更するケースかどうか |
| `estimated_seconds` | 所要時間の目安 |
| `description` | 何を確認するケースか |

**2. 実行前に、環境から実行可否を判定する**

- `requires` と、`devices --json` / `models list --json` / `native status` の結果を
  突き合わせ、実行可能なケースを判定する
- 実行不能なケースは「スキップ」として理由付きで記録する
  （失敗として扱わない）
- **これが将来 GUI の「この環境で何が使えるか」判定の土台になります**

**3. 破壊的なケースを分離する**

`setup.ps1` のプロファイル作成・削除、`native clean` / `build`、
`models remove` などは環境を変更します。

- `destructive: true` として区別する
- **既定では実行しない。**明示的な指定でのみ実行する
- 実行する場合、事前に状態を記録し、終了後に復元する手順を持つ

**4. 結果を機械可読で出力する**

- 既存の `results.jsonl` を維持する
- あわせて、実行後のサマリーを JSON で出力する
  （合格・失敗・スキップの内訳、スキップ理由、所要時間）
- **文字起こし本文が混入しないことを引き続き保証する**

**5. Python API として呼べるようにする**

- CLI からだけでなく、`import` して呼べる形にする
- 将来 GUI がサブプロセス起動ではなく直接利用できるようにするため
- 複雑な抽象化は不要。実行関数と結果の型が定義されていればよい

### 移植作業

P0〜P13 / P15 / P16 を宣言的ケースへ移植してください。

**移植の難易度に応じて分類し、無理に全部を自動化しないでください。**

| 分類 | 対象 | 扱い |
|---|---|---|
| 完全自動化 | CLI の終了コード、JSON 構造、出力書式、設定優先順位、統計判定 | 宣言的ケースへ移植 |
| 条件付き自動化 | 破壊的操作を伴うもの（プロファイル、ビルド、モデル削除） | `destructive: true` として移植。既定除外 |
| 自動化困難 | 対話メニュー、外部 UI 起動、人工的な障害注入 | **`docs/` に手動確認手順書として残す** |

自動化困難なものを無理に自動化すると、脆いテストが増えて保守できなくなります。
手順書として残すのは妥当な選択です。**ただし、どのケースを手順書に回したかを
明示的に記録してください。**「移植を忘れた」と区別がつくようにするためです。

### 実行と確認

1. 統合後、**全ケースを実行する**（破壊的グループを含む。実行前に状態を記録すること）
2. 合格を確認する
3. NVIDIA 依存のケースはスキップ扱いとし、理由を明示する
4. 長時間耐久グループは既定除外のまま、明示指定で実行できることを確認する
5. 実行結果のサマリーを `docs/` に記録する

### ドキュメント

ハーネスの README に以下を記載してください。

- 実行方法とグループ・タグの指定方法
- ケース定義のスキーマ
- 環境依存の値をどこから取得しているか
- スキップの判定方法
- 破壊的ケースの扱いと復元手順
- グループ別の所要時間の目安
- Python API の使い方
- 手動確認手順書へのリンク

## 実装上の注意

### 機密データ

- 実データの文字起こし内容を、報告、AISTATE、コミットメッセージ、
  ハーネスの結果ファイルに含めない
- `.env` を読み取らない

### 破壊的変更への配慮

- faster-whisper 経路の挙動を変えない
- 破壊的ケースの実行前に環境の状態を記録し、終了後に復元する
- 既定プロファイル、導入済みモデル、ネイティブビルド成果物を失わないこと

### コミット

- ブランチ `fix/phase3d-remediation` を継続使用
- Step 単位でコミットする
- 測定結果の記録は独立したコミットとする
- `git push` は実行しない
- 実データをコミットしない

---

## 禁止事項

- 対策前の性能値を、現在の実力として README に残すこと
- 単発測定だけで auto 順序を決めること
- 自動化困難なケースを無理に自動化し、脆いテストを増やすこと
- 移植しなかったケースを、記録せずに省略すること
- 破壊的ケースを既定で実行すること
- 「今回だけ通る」ハーネスにすること
- 動作確認していないものを「完了」と報告すること

---

## 不明点があった場合

1. `要件定義.md` と `AISTATE.md` の記録を優先する
2. 受入試験報告の記述を参照する
3. 判断できない場合、安全側に倒し、判断と理由を記録する
4. 設計の変更を伴う判断は、実装前に `要件定義.md` へ反映する
