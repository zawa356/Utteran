# utteran — レジューム挙動の調査と是正 指示書

## あなたへの依頼

利用者から報告された2つの挙動について、**事実を確認**してください。

1. 同じ入力・同じ設定で2回実行したときの、出力ファイルの上書き挙動が不明瞭
2. 別のモデルを指定して実行したのに、キャッシュが使われて即座に終了したように見える

あわせて、`.gitattributes` の整備も行います。

作業ブランチは `fix/resume-behavior-investigation` を新規作成して使用します。

---

## 前提: 不具合と決めつけないこと

**これらは利用者の操作ミス、または仕様の理解の相違である可能性があります。**

報告は「なんか怪しい」という感覚に基づくもので、再現手順は特定されていません。
**バグの存在を前提に修正から入らないでください。**

判定は以下の3分類で行ってください。

| 判定 | 意味 | 対応 |
|---|---|---|
| **実装の不具合** | 仕様と異なる動作をしている | 修正する |
| **仕様の欠陥** | 仕様どおりだが、仕様自体が望ましくない | 仕様変更を提案する |
| **操作の誤り** | 仕様どおりで、利用者の操作が想定と違った | **修正しないが、下記を行う** |

### 「操作の誤り」だった場合にやること

**そのまま「利用者のミスでした」で終わらせないでください。**

利用者が誤解したという事実は、**表示や案内が不十分であることの証拠**です。
以下を検討し、実施の可否を判断してください。

- どの表示を見れば正しく判断できたか
- その表示は十分に目立つか、分かりやすい表現か
- 誤解を防ぐために何を追加・変更すべきか

たとえば「全ステージをスキップしました」という情報が、
どのモデルの結果を再利用しているのかまで示していれば、
利用者は誤解しなかったかもしれません。

## 作業環境と制約

**作業機は NVIDIA GPU 搭載機（GTX 1070 Ti）です。**

| 項目 | 制約 |
|---|---|
| プロファイル | **`cuda` のみ使用する** |
| ASR モデル | **`large-v3` と `large-v3-turbo` のみ使用してよい** |
| CPU 実行 | **禁止**（時間がかかりすぎるため） |
| 話者分離 | 調査の焦点は ASR のキャッシュ挙動なので、原則 `--no-diarization` |

### 入力データ

`input/` に実際の会議録音があります。**処理に使用して構いません。**

ただし以下を厳守してください。

- **文字起こしの本文、固有名詞、話者名を、いかなるファイルにも書き込まない**
  （報告書、`AISTATE.md`、`変更履歴.md`、コミットメッセージ、テストコード、ログ）
- 判定は**メタデータと統計量のみ**で行う（後述）
- 元のファイルを変更・削除・移動しない

音声が長く1回の試行に時間がかかる場合、**先頭 5〜10 分を切り出したクリップを
`output/_investigation/` に作成**して使って構いません。
切り出したファイルも実データとして扱ってください。

### 既存キャッシュの削除

**`input/` のデータは過去に処理済みで、ジョブキャッシュが残っています。**
調査の前に、対象のジョブを削除する必要があります。

手順:

1. `utteran jobs list` で既存ジョブを確認し、**件数と job_id だけを記録**する
   （入力ファイル名は記録しない）
2. 対象ジョブを削除する
3. 削除後、`utteran jobs list` で消えたことを確認する

**注意**: 現在の `jobs clean` は `--all` / `--failed` / `--older-than` しかなく、
**個別のジョブを指定して削除する手段がありません。**

- `--all` は他のジョブも消えます。影響を確認してから実行してください
- ジョブディレクトリを直接削除する場合、その手順を記録してください
- **`jobs clean` に個別指定のオプションを追加すべきか**を判断し、
  必要なら本作業で実装してください（調査の副産物として妥当な改善です）

## 判定方法

**会議の内容を一切見ずに判定できます。**

出力 JSON には処理条件が記録されています。

```json
{
  "processing": {
    "asr": { "backend": "...", "model": "...", "device": "..." },
    "diarization": { ... },
    "created_at": "..."
  }
}
```

**`processing.asr.model` を見れば、その出力がどのモデルで生成されたかが分かります。**

判定に使う情報は以下だけです。

| 情報 | 取得元 |
|---|---|
| 使用されたモデル | 出力 JSON の `processing.asr.model` |
| 生成日時 | 出力 JSON の `created_at`、ファイルの更新日時 |
| ステージの状態と config_hash | `utteran jobs show <job_id>` |
| セグメント数、単語数、総文字数 | 出力 JSON から算出 |
| 所要時間 | 実行時の計測 |
| 出力ファイルの一覧と数 | ディレクトリの内容 |

**本文そのものを比較する必要はありません。**
統計量が完全に一致すれば、同じ結果が再利用されたと判断できます。

## 調査 1 — 同一条件での再実行と上書き

### 確認すること

現在の仕様には、競合しうる2つの規則があります。

- **出力ファイル名の衝突時は連番を付ける**（`<stem>_1.<ext>`）
- **レジュームにより、同一条件の再実行は export のみ、または全ステージをスキップする**

同じ条件で2回実行したとき、**同じファイルを上書きするのか、連番が付いて増えるのか**が
仕様上あいまいです。

### 手順

1. 対象のジョブキャッシュを削除する
2. 1回目を実行する
   - `--asr-model large-v3-turbo --no-diarization --format srt,json`
   - 出力ファイルの一覧、更新日時、`processing.asr.model` を記録する
   - `jobs show` で各ステージの状態と config_hash を記録する
3. **同じコマンドで2回目を実行する**
   - 所要時間を記録する
   - 出力ファイルが増えたか、上書きされたかを確認する
   - 更新日時が変わったかを確認する
   - `jobs show` の内容が変わったかを確認する
4. **出力ファイルを削除してから3回目を実行する**
   - export ステージが再実行されるかを確認する
   - ASR が再計算されないことを確認する
5. **出力先だけを変えて4回目を実行する**
   - 新しい場所に出力されるか
   - export のみが実行されるか

### 判定

- 現在の動作が仕様どおりか
- 仕様どおりだとして、利用者にとって望ましいか
- **どちらの動作が正しいと考えるか**を、理由とともに提案する

## 調査 2 — 別モデル指定時のキャッシュ利用

**こちらが重要です。**仕様どおりであれば、モデルを変えれば ASR 以降が
再計算されるはずです。即座に終了したという報告が事実なら、
**古いモデルの結果が新しいモデルの結果として提示されている**ことになります。

### 想定される原因

以下を1つずつ確認してください。**推測で結論を出さないこと。**

| 仮説 | 確認方法 |
|---|---|
| A. CLI の `--asr-model` が Config に反映されていない | `config show` や実行ログで、実際に使われた値を確認 |
| B. `config_hash` の算出対象からモデルが漏れている | モデルを変えて `jobs show` の config_hash を比較 |
| C. モデル名の正規化で、異なる指定が同じ値になっている | 解決後のモデル ID を確認 |
| D. ASR は再計算されたが、export が古い結果を出している | 出力 JSON の `processing.asr.model` を確認 |
| E. 操作の誤り（指定方法が想定と違った） | 実行したコマンドを再現して確認 |

### 手順

1. 対象のジョブキャッシュを削除する
2. `large-v3-turbo` で実行する
   - 所要時間、`jobs show` の config_hash、出力 JSON の `processing.asr.model`、
     セグメント数・単語数・総文字数を記録する
3. **`large-v3` に変えて実行する**（他の条件は同じ）
   - 所要時間を記録する
   - `jobs show` の ASR ステージの config_hash が**変わったか**
   - 出力 JSON の `processing.asr.model` が `large-v3` に**なっているか**
   - セグメント数・単語数・総文字数が変わったか
4. **再度 `large-v3-turbo` に戻して実行する**
   - 2回目の結果と一致するか（キャッシュが正しく効いているか）
5. モデル指定の方法を変えて試す
   - `--asr-model large-v3` と `--asr-model faster-whisper:large-v3` の双方
   - **GUI からモデルを選択した場合**も確認する（Phase 5a で実装済み）

### 判定基準

**明確に不具合と言えるのは以下の場合です。**

- モデルを変えたのに ASR ステージの `config_hash` が変わらない
- 出力 JSON の `processing.asr.model` が、指定したモデルと異なる
- 統計量が完全に一致する（同じ結果が再利用されている）

**上記が起きていなければ、実装は正しく動作しています。**
その場合は、利用者がなぜ「即座に終了した」と感じたのかを検討してください。

- `large-v3-turbo` は高速なので、正常でも短時間で終わる可能性がある
- スキップされたステージと実行されたステージの表示が分かりにくい可能性がある
- どのモデルで処理したのかが、実行後の表示から分からない可能性がある

## 是正

調査結果に応じて対応してください。

### 実装の不具合だった場合

1. 再現する最小手順を特定する
2. **修正前に、失敗を再現する回帰テストを追加する**
3. 修正する
4. 回帰テストが通ることを確認する
5. **受入試験ハーネスに、このケースを追加する**

**現在の受入試験には `--asr-model` を変えた再実行のケースがありません。**
`--asr-device` を変えるケースはありますが、モデル変更は試験されていません。
これは試験の穴なので、判定結果にかかわらず追加してください。

### 表示・案内の改善

判定が「操作の誤り」であっても、以下を検討してください。

- 実行完了時に、**使用したモデルとデバイスを表示する**
- スキップされたステージと実行されたステージを明確に区別して表示する
- 「キャッシュを再利用しました」と分かる表現にする
- GUI でも同様の情報を表示する（Phase 5a の完了画面）

過剰にならない範囲で、判断して実施してください。

## `.gitattributes` の整備

Phase 5a の作業後、**CRLF/LF の差分表示が残る**という報告があります。
Intel 機と CUDA 機で改行コードの扱いが異なるためと考えられます。

このままだと、機械を移動するたびに全ファイルが変更扱いになります。

### 実施内容

1. **現状を調査する**
   - 追跡ファイルの改行コードの実態
   - `core.autocrlf` の設定（両方の機械）
   - 差分が出ているファイルの種別
2. **方針を決める**
   - **`.ps1` は特に注意が必要です。**Phase 4a で UTF-8 BOM を CI で検証しており、
     改行コードの自動変換が BOM の扱いに影響しないことを確認すること
   - バイナリ相当のファイルが誤変換されないようにする
3. `.gitattributes` を追加する
4. 必要なら `git add --renormalize` を実施する
   - **実施する場合、全ファイルが変更されるコミットになります。**
     内容が変わっていないことを確認してから行うこと
5. **CI の BOM 検証と PowerShell 構文検証が引き続き通ることを確認する**

## 報告

- 実行した条件（モデル、デバイス、オプション）
- 各試行の結果（メタデータと統計量のみ）

## 禁止事項

- 再現確認をせずに修正から入ること
- 「操作の誤り」で終わらせ、表示の改善を検討しないこと
- 会議の本文、固有名詞、話者名をファイルに書き込むこと
- CPU での実行（時間がかかりすぎる）
- `large-v3` / `large-v3-turbo` 以外のモデルの使用
- `input/` のファイルを変更・削除すること
- `git push` を実行すること
- `--renormalize` の影響を確認せずにコミットすること

## 不明点があった場合

1. `要件定義.md` の記述を優先する
2. 仕様が曖昧な場合、それ自体が発見です。記録して提案してください
3. 判断できない場合、安全側に倒し、記録する
