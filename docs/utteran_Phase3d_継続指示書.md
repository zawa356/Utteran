## Step 1 — R-1: 反復の原因切り分けと対策別効果測定

### 1-A. flash attention と DTW の切り分け

`AISTATE.md` に「単語TS切替では DTW と flash attention が同時に変わるため、
既存 P14 だけでは一方を根因と断定できない」と記録されています。指摘は正しいですが、
**切り分けは可能です。**

以下の3条件で測定し、どちらが結果を変えているかを特定してください。

| 条件 | flash attention | DTW | 備考 |
|---|---|---|---|
| B1 | 有効（既定） | なし | 現在の「単語TSなし」経路。反復が発生する条件 |
| B2 | **無効**（`--no-flash-attn`） | なし | **切り分け用の新条件** |
| B3 | 無効 | あり（`--dtw`） | 現在の「単語TSあり」経路 |

B2 が B1 に近ければ DTW が要因、B3 に近ければ flash attention が要因です。

**B2 の条件は通常の実行経路には存在しません。** 測定のためだけに一時的に
実行できる手段（デバッグ用の設定または環境変数）を用意して構いませんが、
恒久的な利用者向け機能として公開する必要はありません。判断を記録してください。

素材は、受入試験の P14 で反復が再現した実ファイル（約24分46秒）を使用します。

### 1-B. 対策別の効果測定

Phase 3d で設定化した各対策を、**1つずつ**適用して効果を測定します。
まとめて適用しないでください。

測定条件（B1 をベースラインとする）:

| 条件 | 内容 |
|---|---|
| C0 | 対策なし（B1 と同じ。ベースライン） |

| C2 | VAD のみ |

その場合、その旨を記録してください。

## Step 2 — R-6: 文書への反映

### auto 順序変更の背景説明

R-2 の再測定で、Vulkan 20.488秒（8.787x）に対し ovvk 32.564秒（5.528x）という
結果が出ています。**ovvk が 59% 遅い**という明確な差です。

一方、参考実装の別ハードウェア（Core Ultra 7 255H + Arc 140T、large-v3）では
ovvk が最速でした。**構成の優劣は環境とモデルに依存します。**

README に以下を記載してください。

- 本機での実測値と測定条件（モデル、量子化、音声長、測定方法）
- 参考実装の別環境では逆の結果だったこと
- **したがって、OpenVINO IR を用意する価値は環境依存であること**
- IR 変換には OpenAI の PyTorch 重み（large-v3 で約3GB）の追加ダウンロードと
  変換作業が必要であること
- **自環境での判断には `utteran benchmark` を使うこと**

「IR を用意しなくても Vulkan で十分な場合がある」という情報は、
利用者の手間を大きく減らします。目立つ形で書いてください。

## Step 3 — R-5: 音声長とメモリ消費の関係

### 目的

受入試験の長時間耐久は約24分46秒での確認にとどまっており、
**2時間級の音声でのメモリ挙動が不明**です。Arc 140T は共有メモリ構成のため、
`要件定義.md` 13章の既知課題（長時間音声での pyannote のメモリ消費）が
この環境で顕在化するかが未確認です。

### 実施内容

1. 実ファイルを連結して、**約 25分 / 50分 / 100分 / 150分**の音声を生成する
   - `output/_testdata/` に置き、git 追跡対象外であることを確認する
   - **連結した音声も実データです。文字起こし内容を記録しないこと**

2. 各長さで測定する

| 測定対象 | デバイス | 記録項目 |
|---|---|---|
| ASR | Vulkan（auto の選択先） | 所要時間、ピーク RAM |
| 話者分離 | XPU | 所要時間、ピーク RAM |
| 話者分離 | CPU | 所要時間、ピーク RAM（25分と50分のみでよい） |

3. **メモリ消費が音声長に対してどう推移するかを分析する**
   - 線形か、それ以上か、頭打ちになるか
   - 2時間級（約120分）および150分で問題が発生する見込みがあるか

4. メモリ不足が発生した場合
   - エラーメッセージが理解可能か確認する
   - 中間結果が保持され、再開が可能か確認する
   - **不具合としては扱わない**（要件定義13章の既知課題）
   - ただしエラーメッセージが不親切なら修正する
   - 発生した長さと、その時点のメモリ使用量を記録する

5. 結果を README に記載する（利用者が自環境の限界を判断できるように）

### 時間配分

150分の話者分離は、24分で294秒だった実績から外挿すると30分前後かかる見込みです。
全体で数時間規模になります。

**時間が不足する場合、150分を省略し、100分までの傾向から外挿してください。**
省略した場合はその旨を明記すること。

## Step 4 — R-4: 受入試験ハーネスの統合

**この Step は計測を伴いません。Step 1・Step 3 の計測完了後に実施してください。**

### 問題の所在

Phase 3 の受入試験で、Phase 1/2 のハーネス 98 ケース中 **47 件が「受入器不整合」で
失敗**しています。分類は妥当ですが、このままでは Phase 1/2 の回帰試験が使えません。
次に大きな変更を入れたとき、既存機能の回帰を検出できなくなります。

報告されている不整合の原因:

- 旧ジョブルートの固定前提
- `auto` が CPU を選ぶ前提
- 旧 `--device` オプションの前提
- 旧終了コードの期待値
- 文字化けした期待文字列

### 実施内容

1. 47 件の失敗を個別に確認し、修正する
2. **環境依存の値を固定で持たず、実行時に取得する形へ改める**
   - ジョブルート、モデル保存先、既定プロファイル、auto の選択結果など
   - `utteran config show --json` や `devices --json` から取得する
3. `auto` の選択結果に依存する期待値を、環境非依存の判定に置き換える
4. 文字化けした期待文字列を修正し、**UTF-8 で扱われることを保証する**
5. **Phase 1/2 のケース（G 系）と Phase 3 のケース（P 系）を統合し、
   単一のハーネスからグループ指定で実行できるようにする**
6. 統合後、全ケースを実行して合格を確認する
   - NVIDIA 依存のケースはスキップ扱いとし、理由を明示する
   - 長時間耐久など、実行に時間がかかるケースはグループとして分離し、
     既定では実行しない形にする

### 完了の基準

**次のフェーズ以降で、回帰試験としてそのまま使えること。**
「今回だけ通った」状態にしないでください。

以下をハーネスの README または docstring に記載してください。

- 実行方法とグループの指定方法
- 環境依存の値をどこから取得しているか
- スキップされる条件
- 所要時間の目安
